# الصلاحيات: حالة التنفيذ وخطة الإكمال

**الحالة: غير مكتملة، لا تُنشر.** هذا المستند يصف ما نُفّذ وما لم يُنفّذ، وليس تصريحًا بترقية الإنتاج.

## قواعد التصميم

- مدير النظام هو `MANAGER` وبريده ضمن `ADMIN_EMAILS`؛ يتجاوز جميع الاستثناءات. `/admin` و`/setup` له وحده.
- الافتراضي مسموح للأدوار الثلاثة؛ استثناء الحساب يعلو استثناء الدور. `/dashboard` لا يُمنع. مفاتيح غير معروفة تُتجاهل.
- عند تعذر قراءة جدول الصلاحيات يُمنع الوصول المقيّد مؤقتًا لغير أدمن النظام، مع لوحة قيادة آمنة وتنبيه. يبقى الأدمن قادرًا على الدخول للإصلاح. لا يفتح هذا `/admin` لغير الأدمن.
- السجل الحالي في التطبيق هو رسالة تنفيذ في سجل الخادم، **وليس سجل تدقيق داخليًا**. يلزم تصميم سجل تدقيق دائم في مرحلة لاحقة.

## الموجود الآن

- جدول SQL يدوي منفصل؛ طُبق على قاعدة PGlite المحلية المعزولة فقط، وليس الإنتاج.
- قراءة القالب والاستثناءات، وأولوية الحساب، وواجهة إدارية أولية تتحقق من هوية الأدمن عند كل حفظ. اللوحة تعرض مفاتيح الصفحات والكتابة المفعّلة في البيع والمخزون والمالية؛ تمنع بقية المفاتيح من الحفظ حتى يكتمل تنفيذها.
- حراسات صفحات البيع والمخزون، وحراسات لأفعال البيع والمخزون المربوطة بمفاتيح الكتابة، وحراسة واجهة البحث عن سيريالات البيع.
- بعد موافقة المستخدم على تعديل الكود المالي، أضيفت حراسات صفحات المالية وربط إجراءاتها بمفاتيح الكتابة. مفتاح `/finance#write` يقفل كتابة وحدة المالية كلها، وتبقى مفاتيح الكتابة الخاصة بكل صفحة مستقلة. لم تتغير خوارزميات الحسابات.
- أضيفت مفاتيح مستقلة للتحصيل والرد والمرتجع، واعتماد وصرف ومراجعة المصروف، وتسجيل الجرد وتأكيده وإلغائه وطلبه من صاحب العهدة، والتحويل واعتماد ورفض التسوية، وفتح وإقفال العهد وطلبات العهدة والجرد الموجّه، وطلب وإلغاء التسوية، وإنشاء وتعديل البنود. النماذج تُحذف من العرض عند المنع وتُحرس الإجراءات خادميًا، مع بقاء قفل الصفحة والكتابة العام أعلى منها.
- بعض عناصر لوحة القيادة لها إخفاء بصري تجريبي؛ CSS لا يحمي البيانات المرسلة إلى المتصفح ولا يعدّ حارسًا أمنيًا. هذه المفاتيح غير متاحة للتحرير من اللوحة الحالية.
- اختُبر في المعاينة أن الأدمن وحده يفتح الإدارة، ومنع صفحة البيع بقالب الدور، واستثناء السماح للحساب، وتجاوز الأدمن، وإعادة القيم الافتراضية، ورفض API عند منع صفحة البيع. كما رُفض طلب كتابة مباشر عند قفل الكتابة، ورُفضت محاولة موظف استدعاء إجراء تغيير الصلاحية ومحاولة تقييد حساب الأدمن.

## اللازم قبل الاكتمال والنشر

1. حصر جميع الصفحات والعناصر الداخلية والحقول والأزرار وربطها بدقة، مع عدم إرسال البيانات الحساسة للمستخدم عند منعها، وعدم الاكتفاء بـ CSS. إضافة اختبارات فعلية لكل مسار.
2. إكمال تأمين كل إجراءات الخادم وواجهات API بحسب صفحتها وعناصرها؛ اختبار المنع بطلب مباشر لا عبر الواجهة فقط. اختُبر مسار بيع ومسار تسجيل مصروف والتحصيل واعتماد المصروف وتسجيل الجرد بطلبات مباشرة؛ بقية مسارات الكتابة ما زالت تحتاج اختبارات مباشرة.
3. المالية: أضيفت حراسات الصفحات والإجراءات بعد الموافقة، واختُبر في قاعدة معاينة اصطناعية منع صفحة مصروف جديد وقفل الكتابة الخاص بها والقفل المالي العام، وكذلك إخفاء اعتماد مصروف وتسجيل جرد ورفض طلبيهما المباشرين. اختُبر إخفاء قسم التحويل، وإخفاء إنشاء وتعديل البنود، ومنع فتح حساب بطلب مباشر؛ كما اختُبرت طلبات التحويل وقرارات التسوية مباشرة في الاختبارات اللاحقة أدناه. يلزم اختبار بقية الإجراءات والعناصر وتقاطعاتها؛ لم تُختبر بيانات الإنتاج ولم يُشغَّل SQL عليها.
4. تحسين اللوحة لتغطية جميع المفاتيح المدعومة وإظهار الحالات والتوارث وإجراء اختبارات حفظ/رفض شاملة، مع المحافظة على عدم تقييد أدمن النظام.
5. استكمال مراجعة fail-closed، والفصل بين الإخفاء البصري والتحكم في الوصول والبيانات، ثم اختبار دورة الحياة كاملة على بيانات اصطناعية.
6. بعد موافقة منفصلة فقط: مراجعة وتشغيل `prisma/manual-access-control-upgrade.sql` في الإنتاج قبل نشر الكود، والتحقق من النتيجة. لا يُجرى أي دمج أو نشر قبل الإذن المطلوب.

### متابعة إخفاء النماذج وروابط الصفحات الديناميكية
- أُخفي نموذج البيع الجديد قبل التفرع لكل من واجهتَي البيع، ونماذج إنشاء صنف ورصيد افتتاحي وتوريد، عند قفل كتابة صفحتها. وفي إعدادات البيع وكتالوجه ومصروف جديد تُخفى أدوات الكتابة مع بقاء القراءة المتاحة. الحراسة الخادمية للإجراءات تبقى أساسية؛ الإخفاء وحده ليس حراسة.
- رُبط فحص الروابط الديناميكية في سياق الصلاحيات بالصفحة المسجلة (مثلاً `/sales/123` ← `/sales`)، بدل اعتبار رقم الفاتورة مفتاحًا مجهولًا؛ لا يعني ذلك أن كل رابط في كل واجهة أصبح مشروطًا بالفعل.
- اختبار HTTP المحلي ببيانات اصطناعية أثبت إخفاء نموذج بيع جديد ونموذج صنف جديد ونموذج مصروف جديد عند منع كتابة الصفحة؛ وأثبت تبدّل خاصية فتح الفاتورة في مبيعات اليوم عند منع `/sales`. أعيدت صلاحيات الاختبار إلى inherit. بقية النماذج لم تُختبر HTTP في هذه الجولة. اختبار `check:write-visibility` ثابت المصدر ولا يغني عن اختبار واجهة أو أفعال HTTP.
- لا تزال أجزاء الداشبورد المخفية بـCSS مرسلة للعميل؛ مفاتيحها غير مفعلة في لوحة الإدارة حتى يكتمل منع البيانات خادميًا. مراجعة الروابط والنماذج وAPIs الأخرى ما زالت مطلوبة، ولا يُعد ذلك اكتمالًا للتغطية.

### تدقيق واجهات API
- جرد المسارات الحالية أربعة: البحث عن سيريالات البيع، وصحة النظام العامة للمراقبة، وتسجيل الخروج، وتنظيف جلسة غير صالحة. المساران الأخيران متعلقان بالجلسة وليسا عمليات إدارة؛ يظل فحص الصحة عامًا حتى تعمل المراقبة الخارجية.
- API السيريالات يتحقق من الجلسة وسلامة كلمة المرور وصلاحية صفحة بيع جديد وقفل كتابتها قبل البحث. حارس API نفسه يرفض غياب الجلسة أو مفتاح صفحة غير معروف، وإجابات الرفض لا تُخزّن. تظل فحوص صلاحية المستودع والصنف في محرك البحث كما هي.
- حذف فحص الصحة أعداد الجداول من استجابته العامة ورسائل أخطاء قاعدة البيانات الخام؛ يواصل فحص الجداول وإرجاع 200 أو 503، مع منع التخزين. هذا تغيير في شكل الاستجابة: أي مستهلك خارجي يعتمد على `counts` يحتاج تعديلًا؛ شاشة الإعداد الحالية لا تستخدمه. لم يُختبر سيناريو تعطل قاعدة البيانات HTTP في هذه الجولة.
- تحقق HTTP المحلي باستخدام حساب محاسب اصطناعي من إعادة توجيه غير المسجّل، ومن رفض السيريالات لقفل الصفحة أو الكتابة، ومن عودة الوصول إلى مرحلة تحقق المدخلات عند سماح استثناء الحساب. لم يُختبر بحث ناجح بنتائج سيريالات؛ أُعيدت الصلاحيات المستخدمة إلى inherit. اختبارات `check:api:access` ثابتة المصدر و`check:auth:http` تشمل المسبار العام وغير المسجّل.

### صلاحيات كتالوج البيع المستقلة
- فُصلت إجراءات إضافة وتعديل وتغيير حالة التصنيف والنوع والحقل إلى تسعة مفاتيح مستقلة، وتستخدم النماذج وحارس كل إجراء المفتاح نفسه. قفل صفحة الكتالوج أو كتابتها يعلو أذونات عملياتها، واستثناء الحساب يعلو قالب الدور للمفتاح نفسه؛ يبقى الأدمن غير قابل للتقييد.
- أُنشئ مدير غير أدمن ببيانات اصطناعية في قاعدة المعاينة المؤقتة لاختبار حالة الحظر دون المساس بالإنتاج. HTTP أثبت إخفاء إنشاء التصنيف ورفض POST مباشر له مع بقاء إنشاء النوع والحقل، وإخفاء تعديل التصنيف ورفض POST له مع بقاء تغيير الحالة والإنشاء؛ كما أثبت تجاوز الأدمن واستثناء الحساب وقفل الكتابة الأب. أُعيدت صلاحيات التجربة إلى inherit. لم تُختبر العمليات السبع الأخرى منفردة عبر HTTP؛ توجد اختبارات ثابتة لمطابقة جميع مفاتيح الإجراءات والنماذج، واختبارات للسياسة.
- `check:write-visibility` 3/3، `check:finance:access` 24/24، `check:navigation` 9/9، `check:commerce` 16/16 وTypeScript نجحت. حاولنا `check:catalog:sales` لكنه لم يبدأ الاختبار فعليًا بسبب فشل `prisma generate` في الوصول إلى `binaries.prisma.sh` المحجوب في البيئة؛ لم يُعدّل الاختبار أو يُتجاوز.

### فصل المرتجع الجزئي عن إلغاء الفاتورة
- أصبح `/sales#return` للمرتجع الجزئي وحده، وأضيف `/sales#cancel` لإلغاء كامل الباقي. يتحقق الإجراء الخادمي من نوع العملية بعد تحليل المدخلات، ثم يختار المفتاح بنفسه قبل استدعاء محرك البيع؛ لا يعتمد على مفتاح يرسله العميل. لم تتغير سياسة الدور الأصلية في المحرك: تسمح للمدير وللمحاسب الذي يملك `canCancelSales`، بينما تعرض الواجهة النموذج للمدير فقط؛ لذلك يستطيع المحاسب المؤهّل الوصول إلى الإجراء مباشرة ما لم تمنعه الصلاحية الجديدة. هذا التفاوت بحاجة إلى قرار/معالجة مستقلة، ولا يجوز وصفه بأنه منع خادمي للمحاسب.
- تخفي الواجهة الاختيار الممنوع، وتبدأ بوضع الإلغاء إذا كان وحده مسموحًا، وتخفي النموذج عند منع الاثنين. قفل صفحة المبيعات وكتابتها يعلوان المفتاحين. HTTP محلي بمدير اصطناعي غير أدمن وفاتورة اختبار أثبت إخفاء كل اختيار ورفض POST المباشر لكل عملية، وبقاء الاختيار الآخر، وإخفاء النموذج عند منع كليهما؛ أُعيدت الصلاحيات inherit. لم تُنفذ عملية مرتجع أو إلغاء ناجحة في هذا الاختبار.
- مهم للتوافق: معنى المفتاح السابق `/sales#return` كان يشمل الإلغاء أيضًا أثناء التطوير؛ بعد الفصل، منع هذا المفتاح وحده لا يمنع الإلغاء. إذا وُجدت إعدادات من هذا الإصدار التجريبي في أي قاعدة أخرى، يجب مراجعتها وإضافة منع `/sales#cancel` عند الحاجة قبل الاستخدام؛ لا ترقية أو تغيير على الإنتاج دون موافقة.
- نجحت `check:write-visibility` 4/4، `check:finance:access` 25/25، `check:commerce` 16/16، `check:navigation` 9/9 وTypeScript. لا تزال حماية بيانات أقسام الداشبورد خادميًا غير مكتملة ولم يُفعّل لها مفتاح جديد في هذه الجولة.

### تنبيه التعذر وعنصر الداشبورد الآمن
- صار فشل قراءة مخزن الصلاحيات يُظهر تنبيهًا في مساحة العمل لجميع الأدوار، بالإضافة إلى تنبيه لوحة الأدمن، مع استمرار سياسة الفتح المؤقت. لا تُفتح صفحات الإدارة لغير الأدمن بسبب هذا الفشل.
- أُتيح مفتاح تلميح معاملات اليوم `/dashboard#focus-hint`: يحجب عرض التلميح بشروط الرندر بدل الاعتماد على CSS فقط، مع منع إعادة تفعيله من إعدادات العرض. صفحة `/dashboard` نفسها تظل دائمًا مفتوحة، وأصبحت لوحة الأدمن تعرض عناصر الصفحة الدائمة المنفذة دون تقديم خيار لإخفاء الصفحة. هذا التلميح نص إرشادي، وليس حماية لبيانات مؤشرات الداشبورد الأخرى.
- HTTP محلي ببيانات اصطناعية: عند غياب جدول الصلاحيات ظهر التحذير للموظف واستمر فتح صفحة البيع، ورُفض وصوله للإدارة وظهر التحذير للأدمن؛ الخطأ سُجل `P2010` ولم يُعامل كحالة سليمة. كما أثبت اختبار آخر إخفاء التلميح وعودة ظهوره باستثناء الحساب وبقاء الداشبورد مفتوحًا.
- بعد إيقاف خادم PGlite السابق تبيّن تعطل قاعدة المعاينة المؤقتة وعدم قابليتها للفتح؛ لم تُمس بيانات إنتاج. أُنشئت قاعدة اصطناعية جديدة مستقلة `/tmp/pglite-preview-recovery-20261107` وطُبّق عليها ملف الصلاحيات فقط، وتعمل المعاينة عليها دون تفعيل المالية. بيانات التجارب القديمة ليست في القاعدة الجديدة. لا تُفتح قاعدة PGlite نفسها في عملية ثانية أثناء تشغيل المعاينة.
- نجحت اختبارات إظهار/حجب الكتابة 6/6، الصلاحيات والمالية 26/26، التنقل 9/9، أقسام الداشبورد 5/5 وTypeScript. أقسام الداشبورد المالية وقوائم الفواتير ما زالت غير مفعلة لصلاحيات العناصر لأن حماية بياناتها في كل المواضع لم تكتمل.

### تجربة عزل بطاقة المصروفات وتصحيح إعداد الخصم
- في قاعدة مالية اصطناعية مستقلة أُنشئ مصروف ذو وصف اختباري فريد. محاولة حجب بطاقة مصروفات اليوم وإيقاف استعلامها لم تمنع إرسال الوصف في استجابة الداشبورد، إذ تكرر في مؤشر مصروفات الشهر والسجل الحي داخل بيانات RSC. لذا أُلغيت محاولة التفعيل وبقي `/dashboard#part-today-expenses` غير متاح بلوحة الإدارة؛ لا يمكن الادعاء أن إخفاء البطاقة يحمي بيانات المصروفات. تغطية هذه المواضع تحتاج تصميمًا يمنع التسريب دون إخفاء مؤشرات أخرى على نحو غير مقصود.
- صُحح خلل سابق في إجراء حفظ إعداد الخصم: صار يمرّر `managerPercent` المرسل من النموذج إلى تحقق ومحرك الإعداد، بجانب `percent`. HTTP على قاعدة اصطناعية أثبت حفظ 1% للموظف و2% للمدير وظهورهما بعد إعادة تحميل الصفحة؛ لم تتغير إعدادات إنتاج. اختبار المصدر يحرس تمرير الحقلين.
- الاختبارات: `check:write-visibility` 7/7، `check:finance:access` 27/27، `check:commerce` 16/16، وTypeScript و`git diff --check` ناجحة. أُعيد تشغيل المعاينة بلا المالية على قاعدة اصطناعية جديدة `/tmp/pglite-preview-normal-20261107b`؛ بيانات التجربة المالية والخصم ليست في قاعدة المعاينة الجديدة.

### عزل تفاصيل المصروفات على مستوى الداشبورد
- أضيف المفتاح المستقل `/dashboard#expense-details` إلى لوحة الأدمن. منعه يمنع تحميل بطاقة تفاصيل اليوم، ويزيل بطاقة مصروفات الشهر التي تحتوي أوصافًا فردية، ويستبعد حركات المصروفات من السجل الحي قبل تمرير المحتوى للعميل. يؤثر المنع على هذه المواضع معًا، ولا يمنع ملخصات أو إجماليات المصروفات في المؤشرات الأخرى ولا يمنع صفحات المالية. صلاحية البطاقة المفردة `/dashboard#part-today-expenses` لا تزال غير مفعّلة، لأن حجب البطاقة وحدها لا يحمي الوصف المتكرر.
- على قاعدة مالية اصطناعية مخصصة، أُنشئ مصروف بوصف فريد؛ ظهر الوصف 7 مرات في استجابة HTML/RSC قبل المنع، ثم لم يظهر في الاستجابة الكاملة لأربع حالات: الداشبورد الافتراضي والشامل وطلب قسم المصروفات الشهرية وقسم السجل الحي. اختُبر منع دور الموظف والمحاسب واستثناء حساب الموظف وتجاوز الأدمن، وبقاء صفحة المصروفات للموظف وفق صلاحياتها الخاصة. هذه نتيجة لحالة اختبار واحدة وليست إثباتًا شاملًا لعدم تسريب كل أنواع بيانات المصروفات في المستقبل. أُعيدت الصلاحيات inherit.

### اختبارات طلبات العهدة والجرد والتسوية
- أضيف `check:finance:staff:http`، بقاعدة مالية اصطناعية وخادم مؤقت، لفحص خمسة مفاتيح منفردة: طلب العهدة، قرار طلب العهدة، تسجيل الجرد الموجّه، طلب التسوية وإلغائها. أثبت إخفاء النموذج ورفض POST المباشر عند منع الدور، وعودة النموذج ووصول الطلب إلى التحقق عند استثناء الحساب، ثم أولوية قفل كتابة المالية على الاستثناء؛ واختبر تجاوز الأدمن لقرار العهدة. لا يثبت تنفيذ جميع هذه العمليات بنجاح ولا تفاعل المتصفح.
- أُصلح حقل سبب إلغاء التسوية لأنه كان بلا `name`، ما يمنع إرسال السبب من النموذج رغم إدخاله. اختبر HTTP وجود الاسم وإلغاء طلب اصطناعي بنجاح واختفاء نموذج الإلغاء بعده. الاختبار يصنع FormData، وليس تفاعل متصفح.
- حُجب رابط طلب تسوية جديدة من صفحة التسويات عند منع صفحة الطلب أو كتابتها أو إجراء الطلب، ويعود بسماح استثناء الحساب ما لم يقفله قفل أعلى. اختُبر الرابط واستثناء الحساب وقفل كتابة صفحة الطلب HTTP، وليس جميع روابط المالية.
- **مسألة سياسة معلّقة:** `listCustodyRequests` يرشّح طلبات العهدة للمحاسب حسب فرعه فقط، بينما `decideCustodyRequest` يسمح للمدير والمحاسب بالبت دون فحص فرع الطلب. في الاختبار الاصطناعي لم يرَ محاسب بلا فرع طلبًا معلقًا، لكنه استطاع رفضه بطلب مباشر بعد أخذ النموذج من الأدمن؛ المدير والمحاسب في الفرع رأياه. هذا تفاوت بين العرض والإنفاذ، وليس قرارًا بأن أي نطاق هو الصحيح. لم يتغير المحرك؛ يلزم تحديد سياسة نطاق المحاسب ثم توحيد القراءة والكتابة واختبار الفروع قبل النشر.
- نجح الاختبار HTTP 1/1، و`check:finance:engine` 34/34، و`check:write-visibility` 16/16، وTypeScript و`git diff --check`. لا ترقية إنتاج أو نشر.

### قرار نطاق المحاسب في طلبات العهدة
- بناءً على قرار المستخدم «فرعه فقط»، أصبح المحاسب يرى ويبتّ في طلبات العهدة المسجلة في فرعه فقط؛ المحاسب بلا فرع لا يرى طلبات معلقة ولا يستطيع البت فيها. المدير يحتفظ بنطاقه السابق لجميع الفروع. هذا القرار خاص بطلبات العهدة، وليس تغييرًا عامًا لنطاق كافة عمليات المالية أو المبيعات.
- يُقرأ نطاق الطلب من `finance.custody_requests.branch_id` لا فرع مقدّمه الحالي، كي لا ينتقل الطلب ضمنيًا إلى فرع آخر عند نقل الموظف. تُعرض تسمية فرع الطلب نفسه في نموذج القرار. يُتحقق من الفرع داخل المعاملة بعد قفل الطلب وقبل الموافقة أو الرفض، حتى إن سمحت قاعدة الصلاحيات للحساب؛ ويُعاد التحقق عند استرجاع نتيجة طلب سبق تنفيذه بعد تغيير فرع المحاسب. لم تُغيّر خوارزمية الحساب النقدي أو تُضف ترقية قاعدة.
- اختبار HTTP اصطناعي أثبت حجب الطلب خارج الفرع وعن المحاسب بلا فرع، ورفض الموافقة والرفض بطلب مباشر في الحالتين (حتى مع استثناء سماح)، ونجاح رفض محاسب لطلب فرعه وموافقة محاسب آخر على طلب فرعه وموافقة المدير على طلب الفرع الآخر. واختبار المحرك أثبت ثبات النطاق عند نقل مقدّم الطلب، وسلامة حالة الطلب وعدم فتح حساب بعد محاولة غير مصرح بها، وإعادة النتيجة داخل الفرع ثم رفض إعادتها بعد نقل المحاسب. لا يختبر تفاعل المتصفح أو جميع حالات التنافس.
- موضوع منفصل يحتاج مراجعة قبل النشر: عند نقل صاحب الطلب نفسه بعد تقديمه، ظل الطلب مرتبطًا بفرع إنشائه؛ لم تُحدَّد هنا سياسة الموافقة على فتح عهدة لموظف نُقل لاحقًا. لا يُستنتج من هذه الجولة تطبيق نطاق الفرع على بقية معاملات المحاسب.
- نجح `check:finance:staff:http` 1/1، واختبار `new-account-helpers` 5/5، و`check:finance:engine` 34/34، و`check:finance:access` 34/34، وTypeScript و`git diff --check`. لم يُدمج أو يُنشر شيء ولم تُمس قاعدة الإنتاج.

- كُشف اصطناعيًا أن جردًا للعهدة المقفلة كان يُنشأ ويُؤكد، منشئًا حركة تعديل ورصيدًا جديدًا على حساب مقفل. أضيفت حراسة داخل المعاملة لإنشاء وتأكيد الجرد وطلب الجرد الموجّه وتسجيله. تبقى الجرود القديمة قابلة للإلغاء، ويُستبعد الحساب المقفل من خيارات الجرد وتُحجب واجهة التأكيد للطلبات القديمة مع تنبيه. يظل فحص الخادم هو الحماية الأساسية.

- **نتائج تدقيق سابقة قبل الإصلاح الجزئي في القسم التالي:** كان الإقفال لا يفحص إلا الرصيد الدفتري صفرًا؛ أثبت اختبار اصطناعي أنه يقبل إقفال عهدة لها تحصيل نقدي غير مسوّى بقيمة متوقعة 100، ثم لا يعود ملخص التسوية يختارها. الفهرس الدائم يمنع فتح عهدة بديلة بنفس الفرع. وكان يقبل أيضًا وجود طلبات تسوية أو جرد مفتوحة؛ أصبحت قابلة للإلغاء لكن ذلك لم يكن معالجة شاملة للفترة أو التاريخ. لم تُدقق جميع مسارات الصرف والتحصيل وتصحيح السجلات والحركات أو التزامن. يلزم تصميم ومراجعة سياسة الإقفال والبيانات التاريخية والهجرة قبل النشر؛ لا تُشغّل أي ترقية على الإنتاج. هذه الجولة لا تجعل النظام جاهزًا للإنتاج.

### متابعة شروط الإقفال والصرف
- حلًا جزئيًا للخطر المذكور في القسم السابق، يقفل المحرك صف الحساب للتحديث ثم يرفض الإقفال إن وجد طلب تسوية أو جرد مفتوحًا، أو إن وُجدت تحصيلات أو مصروفات غير مسوّاة في الفترة حسب حساب `settlementPeriod` الحالي؛ يُفحص كل إجمالي مستقلًا حتى لو كان صافي الاثنين صفرًا. لا يكفي الرصيد الدفتري صفرًا وحده. بعد إلغاء الطلبات أو تسوية الفترة يمكن إعادة محاولة الإقفال؛ لا تتغير السجلات عند الرفض.
- اختبار `check:finance:closure` بقاعدة اصطناعية أثبت رفض الإقفال لطلب تسوية مفتوح ثم لجرد مفتوح، ونجاحه بعد إلغائهما، ورفضه لتحصيل غير مسوّى ولتحصيل ومصروف متساويين، ثم نجاحه بعد تسوية اصطناعية مؤكدة. كما فحص replay وعدم إنشاء أثر عند الرفض. لا يثبت هذا كفاية تعريف الفترة أو سلامة الإقفال في جميع مسارات المبيعات والتزامن.
- مُنع الصرف النقدي الجديد من حساب مقفل داخل المعاملة، وكذلك رد النقد إليه عبر hook الرد، والتحصيل عبر hook المحرك الاختباري. الاختبار المباشر فحص الرفض وعدم إنشاء حركة أو تغيير حالة المصروف، وأبقى مسار إثبات دفع تاريخي سابق للافتتاح دون حركة. و`check:finance:expenses:http` نجح 1/1 بعد إضافة POST صرف مباشر لحساب مقفل والتحقق من بقاء المصروف معتمدًا. لم يُختبر الرد عبر HTTP في هذه الجولة، وhook التحصيل ليس مسار التحصيل الفعلي في المبيعات.
- صُححت رسالة نموذج فتح الحساب التي كانت تعد بفتح عهدة بديلة رغم الفهرس الدائم؛ صارت تنبّه إلى ضرورة المراجعة بدل الوعد بالنجاح. أضيف تنبيه لشروط الإقفال في النموذج. لا تغيّر قاعدة البيانات أو تزيل الفهرس.
- **خطر متبقٍ:** حساب الفترة ينسب التحصيلات لمنشئ الفاتورة، لا بالضرورة لمن استلم التحصيل. مسار تحصيل المبيعات الفعلي ينشئ التحصيل دون استدعاء hook الحساب؛ يمكن أن يحدث تحصيل لاحق بعد إقفال العهدة دون أن يختاره ملخصها. أُنشئ صف تحصيل اصطناعي لاحق في اختبار المحرك لتوضيح المشكلة، وليس اختبار HTTP للمسار الفعلي. يلزم تصميم إسناد التحصيلات والفترات والتعامل مع الحركات اللاحقة للإقفال، واختبارات PostgreSQL للتزامن، ومراجعة التصحيحات التاريخية والفهرس قبل النشر. لا يُعد الحارس الجديد حلًا شاملًا.
- نجح اختبار الإقفال 1/1، والتسويات 6/6، ومحرك المالية التطبيقية 3/3، وصلاحيات المالية 35/35، وإظهار الكتابة 17/17، وTypeScript و`git diff --check`. بيانات اصطناعية فقط؛ لا دمج أو نشر أو ترقية إنتاج.

### تصحيحات العهد المقفلة وروابط التقرير والرد
- كشف اختبار PGlite اصطناعي أن تأكيد تصحيح مصروف نقدي سابق وتصحيح افتتاح دفتري من نوع `BOOK` كانا ينشئان حركة ويغيّران رصيد عهدة مقفلة. مُنع المساران بعد قفل الحساب، وتبقى مراجعة المصروف مفتوحة ويمكن إغلاقها بسبب دون تصحيح. اختُبر عدم إنشاء تصحيح أو حركة جديدة وبقاء الرصيد صفرًا. لا توجد واجهات لهذه العمليات في الجولة المدققة، لذا الاختبار مباشر للمحرك لا HTTP.
- لم تُمنع تلقائيًا الملاحظة التاريخية `COUNT_COVERED` التي لا تنشئ حركة مالية: اختُبرت على عهدة مقفلة مع بقاء رصيدها صفرًا. إبقاء هذا السلوك ليس اعتمادًا لسياسة تاريخية شاملة؛ يلزم مراجعة التصحيحات وآثارها قبل النشر.
- استُبعدت الحسابات المقفلة من خيارات رد النقد في تفاصيل الفاتورة قبل تمريرها للعميل. اختبر HTTP وجود خزنة مفتوحة وعدم إرسال اسم صاحب عهدة مقفلة، ثم أرسل طلب رد مباشر لها في فاتورة اصطناعية ذات مبلغ مستحق؛ رُفض الطلب وبقي عدد سجلات الرد الظاهرة دون زيادة. هذا يُكمّل فحص المحرك داخل المعاملة، ولا يغطي جميع معاملات أو تنافس المبيعات.
- فُلتِرت روابط مؤشرات تقرير المالية إلى سجل المصروفات والتسويات ورابط العودة للمالية وفق صلاحية صفحاتها؛ تبقى المؤشرات نفسها ظاهرة إذا كان التقرير مسموحًا. HTTP اختبر المنع واستثناء الحساب وتجاوز الأدمن. إخفاء الروابط لا يحجب إجماليات المصروفات أو الأرصدة التي يعرضها التقرير؛ صفحة التقرير مستقلة وتحتاج مراجعة نطاق بياناتها قبل النشر.
- تحذير صلاحيات مهم: منع صفحة `/finance` وحده لا يمنع إرسال أسماء وأرصدة حسابات مفتوحة لازمة لنموذج رد المبيعات عند السماح بالرد وقراءة الفاتورة؛ أثبت HTTP استمرار ظهور خيار خزنة الفرع في هذا الوضع. كذلك لا يمنع صفحة التقارير المستقلة. لا يُعتبر منع الصفحة حماية شاملة للأرصدة؛ حُسمت سياسة الرد والتقرير لاحقًا كما هو موضح في القسم التالي، دون ادعاء عزل شامل.
- نجح `check:finance:closure` ‏2/2، و`check:finance:access:http` ‏1/1 بذاكرة 3072 ميجابايت، وصلاحيات المالية 35/35، وإظهار الكتابة 17/17، وTypeScript و`git diff --check`. فشلت محاولة HTTP واحدة في آخر اختبارها دون إظهار السبب في غلاف الخطأ؛ عُدّل الغلاف لإظهار السبب ثم نجح تشغيلان لاحقان. لم تُجرَ ترقية إنتاج أو دمج أو نشر، والنظام ما زال غير جاهز للإنتاج للأسباب أعلاه وفي الأقسام السابقة.

### سياسة عرض رصيد رد المبيعات والتقرير
- قرر المستخدم بقاء تقرير المالية مستقلًا، حتى عند منع صفحات المالية أو المصروفات؛ يظل عرض بياناته خاضعًا لصفحته ودور المستخدم، ولا يُستنتج من منع صفحة أخرى إخفاء إجماليات التقرير. روابط الوجهات المحظورة تُحجب كما في القسم السابق.
- قرر المستخدم إضافة صلاحية مستقلة للأرصدة مع مسار رد آمن عند حجبها. أضيف `/sales#refund-balances` للوحة الأدمن؛ هو خاص بأرصدة الحسابات في نموذج رد المبيعات وليس قفلًا شاملًا للأرصدة في النظام. عند المنع يستعلم الخادم عن معرّفات الحسابات المفتوحة وأسمائها دون حساب أرصدتها، ولا يمرر خاصية الرصيد إلى HTML/RSC أو مكوّن العميل. يظل الرد خاضعًا لصلاحية `/sales#refund` وقفل صفحة/كتابة المبيعات والدور. نتيجة اللوحة لهذا المفتاح تراعي أن نموذج الرد نفسه قد يكون ممنوعًا.
- إذا كان الرصيد محجوبًا، لا يُسمح للمستخدم بتأكيد رصيد سالب لم يره: يرفض الخادم طلب إقرار السالب المباشر، ويرفض أي رد سيجعل الرصيد سالبًا برسالة عامة دون إرسال الأرقام؛ ينجح الرد إذا كفى الرصيد. عند ظهور الرصيد تبقى مراجعة السالب السابقة كما هي. لا يغيّر الإجراء حمولة الطلب بصمت، ويحافظ replay على عدم التكرار في الاختبار. قد يكشف نجاح أو فشل عملية مُجازة معلومة تقريبية عن كفاية الرصيد؛ المفتاح ليس ضمانًا ضد الاستنتاج أو حماية للأرصدة في مصادر أخرى.
- HTTP اصطناعي `check:finance:access:http` اختبر علامة رصيد مميزة في كامل HTML/RSC قبل المنع واختفاءها عنده، وبقاء اختيار الحساب ونموذج الرد، واستثناء الحساب وتجاوز الأدمن، ورفض محاولة فرض إقرار سالب برسالة مناسبة، ورفض خصم يؤدي للسالب دون كشف الرصيد، ونجاح رد برصيد كافٍ وإعادة الطلب دون تكرار. اختبر سابقًا حجب الحسابات المقفلة ورفض POST إليها. لم يُختبر تفاعل متصفح، ولا تُستنتج حماية كل بيانات المالية أو اختبار تزامن PostgreSQL من هذه الحالات.
- نجحت اختبارات HTTP ‏1/1، والصلاحيات 36/36، وإظهار الكتابة 17/17، وسياسات التجارة 16/16، وإقفال العهد 2/2، وTypeScript و`git diff --check`. سياسة fail-open باقية كما هي، وعيوب الإقفال والفهرس وإسناد التحصيلات والمراجعة الشاملة باقية؛ النظام غير جاهز للإنتاج. لا دمج أو نشر أو SQL إنتاج.

### اختبار HTTP لإقفال العهدة
- أصبح نموذج الإقفال داخل عنصر `details` مغلق افتراضيًا بدل بنائه فقط بعد نقرة JavaScript؛ يمكن فتحه وإلغاؤه من الواجهة. النموذج موجود في HTML للمصرّح لهم عندما تكون العهدة مفتوحة ورصيدها الدفتري صفرًا، لكن حجب النموذج لا يُعتمد عليه للحماية: إجراء الخادم والمحرك يعيدان فحص الصلاحيات والشروط. لم يُختبر التفاعل المرئي بمتصفح في هذه الجولة.
- وسّع `check:finance:account-open:http` بقاعدة PGlite اصطناعية لاختبار نموذج الإقفال وPOST الفعلي: منع مفتاح العملية، واستثناء المحاسب، وأولوية منع الكتابة والصفحة، ومنع مدير غير أدمن وتجاوز أدمن النظام في عرض النموذج. أُرسلت محاولة موظف مباشرة مع استثناء سماح؛ صفحة الموظف لا تعرض حالة النموذج، لكن الإقفال اللاحق للمحاسب على الحساب نفسه نجح، ما يؤكد عدم إقفاله في المحاولة. رُفض إقفال عهدة لها جرد مفتوح وخزنة الفرع وعهدة رصيدها غير صفر، ثم نجح إقفال عهدة صفرية أخرى وإعادة الطلب دون تكرار، ورُفض إقفالها مجددًا بمعرّف جديد. بقي نموذج العهدة ذات الجرد المفتوح، واختفى نموذج العهدة التي أُقفلت، ولم يظهر نموذج إقفال العهدة غير الصفرية.
- نجح HTTP ‏1/1 واختبار المحرك للإقفال والتصحيحات ‏2/2 وTypeScript و`git diff --check`. لا يثبت الاختبار تزامن PostgreSQL ولا التحصيل الحقيقي أثناء الإقفال؛ مخاطر إسناد التحصيل والفهرس البديل المذكورة أعلاه باقية، ولم تتغير ترقية قاعدة البيانات أو تُنفذ على إنتاج.

### تدقيق التحصيل الفعلي وإسناد التسوية — عيب قائم
- أُضيف `check:finance:collection-audit` بقاعدة PGlite اصطناعية وعميل Prisma WASM، ويستدعي `recordCommerceCollection` الفعلي ومحرك المالية في القاعدة نفسها؛ ليس اختبار HTTP أو تزامن PostgreSQL. نتيجة نجاح الاختبار تُثبت السلوك الخاطئ الحالي ولا تعني إصلاحه.
- لفاتورة أنشأها المدير، سجّل موظف الفرع تحصيلًا نقديًا 37، لكن ملخص عهدته أظهر مبيعات 0 ورصيدًا دفتريًا 0، ولم تُنشأ حركة مالية؛ قُبل إقفال عهدته رغم التحصيل. بعد الإقفال نجح تحصيل لاحق 13 من مسار البيع نفسه ولم ينشئ حركة، واختفى الحساب من ملخص الموظف. اختُبر replay للتحصيلين. السبب أن حساب الفترة يستخدم `commerce_sales.created_by_id` لا `commerce_collections.created_by_id`، وأن مسار التحصيل الفعلي لا يستدعي hook الحساب.
- الاتجاه المعاكس مثبت أيضًا: عندما أنشأ الموظف فاتورة وسجل المدير تحصيلها النقدي 19، نُسبت الـ19 إلى فترة الموظف رغم أن المدير هو الذي سجّل التحصيل. هوية مسجل التحصيل متاحة في `commerce_collections.created_by_id`، لكنها وحدها لا تثبت من أمسك النقد فعليًا أو الحساب المقصود، خصوصًا عند تحصيل الإدارة نيابةً عن آخرين. لذلك لم يُستبدل معيار الإسناد ولم تُضاف حركة تلقائية دون سياسة واضحة ومراجعة الحسابات التاريخية والتسوية؛ الجمع بين إضافة حركة وبين معادلة الفترة الحالية قد يحسب التحصيل مرتين. يلزم تصميم المصدر الحقيقي للنقد، والسياسة التاريخية والترحيل، وضمان التزامن واختبار المسارين الفعليين الأول واللاحق قبل النشر.
- نجح الاختبار 1/1 وTypeScript و`git diff --check`. لم تُستخدم بيانات إنتاج ولم تُجرَ هجرة أو نشر.

### قرار المستخدم وخطوة تصميم محاسبي للتحصيل
- اختار المستخدم إسناد التحصيل النقدي إلى مسجّل التحصيل. وإذا لم تكن له عهدة مفتوحة، يكون تحصيل المدير والمحاسب إلى خزنة فرع الفاتورة، بينما يُشترط للموظف فتح عهدة. صيغت قاعدة أولية في `prototypes/finance-collection-policy/destination.ts`: عند وجود عهدة مفتوحة للمسجّل في فرع الفاتورة تُختار، وإلا تُستخدم خزنة الفرع للإدارة ويُرفض الموظف، مع رفض الحساب الموقوف وتغيير كلمة المرور المطلوب والنطاق الخاطئ والحالات الملتبسة. نجح `check:finance:collection-policy` ‏3/3. الاختيار بين عهدة الإدارة المفتوحة والخزنة عندما توجد الاثنتان افتراض تصميمي أولي يمكن مراجعته؛ لا يصدر حركة ولا يغيّر التطبيق.
- توسع تدقيق `check:finance:collection-audit` ليستخدم أيضًا `createCatalogSale` الفعلي: بعد إقفال عهدة الموظف قُبل بيع كتالوج بدفعة أولى نقدية 7 دون حركة، ونجح replay دون تكرار. ما زال مسار البيع المخزني الأول غير مختبر بهذا السيناريو مباشرة.
- توضح `prototypes/finance-collection-policy/README.md` تصميمًا مقترحًا غير مفعّل لمصدر الحقيقة وسلامة المعاملة ومنع الاحتساب المزدوج والبيانات التاريخية والمتزامنة. **القرار لم يُطبّق بعد في التطبيق**؛ العيب ما زال قائمًا، ولم يُنفّذ SQL أو backfill. لا تكفي معرفة مسجّل التحصيل وحدها لتحديد موضع نقد تاريخي أو تصحيح تسويات مؤكدة. يلزم تصميم الانتقال والتسوية وإقفال العهدة واختبارات PostgreSQL الحقيقية قبل تفعيل السياسة.

### قيد مؤقت لصرف المصروف من نقد الموظف
- كشف اختبار المحرك أولًا أن إدارةً تستطيع تسجيل `HOLDER_CASH` بعد إقفال عهدة طالب المصروف، دون حركة أو ظهور العهدة في ملخص التسوية. اختار المستخدم أن يُنسب المصروف إلى **مسجّل الصرف**، ووافق صراحةً على قيد مؤقت لأن معادلة الفترة الحالية تنسبه إلى طالب المصروف ولا يجوز إعادة تفسير السجلات القديمة بصمت.
- في التطبيق الفعلي يرفض المحرك الآن صرف `HOLDER_CASH` بالنيابة عندما يختلف المسجّل عن طالب المصروف؛ ويشترط عهدة واحدة مفتوحة للمسجّل في فرع المصروف، مع منع الموظف من الصرف خارج فرعه الحالي. يقفل صف العهدة في المعاملة نفسها، ويزيد رقم مراجعتها عند حفظ الصرف حتى يصبح الجرد السابق قديمًا. يظل الصرف بلا حركة ويُدرج في معادلة الفترة الحالية؛ لا يُغيَّر التاريخ ولا يُسجل أي دفع عند الرفض. replay لطلب سبق حفظه لا يكرر الدفع. شرح النموذج هذا القيد. لا يغيّر القيد مسارات الخصم المباشر من حساب أو وسائل الدفع الأخرى.
- **أثر تشغيلي مقصود ومؤقت:** لا يمكن للإدارة تسجيل صرف `HOLDER_CASH` بالنيابة عن موظف آخر؛ يبقى المصروف معتمدًا عند الرفض. إجراء HTTP الحالي مخصص للمدير والمحاسب، ولذلك لن يتمكن الموظف من إتمام هذا النوع بنفسه من واجهة صرف الإدارة حاليًا. لا ينبغي التحايل بتغيير المصدر ما لم يطابق الدفع الفعلي؛ استكمال تسجيل الصرف لمصروف شخص آخر يحتاج الربط المحاسبي الجديد أو مراجعة منفصلة.
- نجح اختبار المحرك `check:finance:holder-cash-audit` ‏1/1 لرفض النيابة والفرع الخاطئ والعهدة المغلقة أو غير الموجودة، وقبول صرف مسجّل له عهدة، واحتسابه مرة في الفترة، وجعل الجرد السابق قديمًا، ومنع الإقفال مع مصروف غير مسوّى، وreplay دون تكرار. نجح HTTP المصروفات ‏1/1 للرفض والنجاح وبقاء المصروف معتمدًا عند الرفض، والتسوية ‏6/6، وapp-engine ‏3/3، والإقفال ‏2/2، والصلاحيات ‏36/36، وTypeScript و`git diff --check`.
- هذا إصلاح احترازي ضيق لا يطبق إسناد التحصيل الذي اختاره المستخدم، ولا يصحح المصروفات القديمة، ولا يحل غياب عهدة بديلة أو التزامن PostgreSQL أو `HOLDER_CASH` التاريخي وطلبات الصرف التي تنشأ قبل/بعد التحويل. HTTP اصطناعي بغير تفاعل متصفح، ولم يُستخدم SQL إنتاجي أو نشر.

### قيد مؤقت للتحصيل النقدي اللاحق
- وافق المستخدم على منع التحصيل النقدي اللاحق بالنيابة عن منشئ الفاتورة مؤقتًا، لأن `settlementPeriod` الحالي يستخدم منشئ الفاتورة وليس مسجّل التحصيل. أضيف حارس داخل معاملة `recordCommerceCollection` بعد التحقق من صلاحية الفاتورة والطلب السابق: يُرفض النقد إن اختلف المسجّل عن المنشئ، بما في ذلك الأدمن، ولا يُنشأ تحصيل. تحصيل البطاقة أو وسائل غير النقد يظل متاحًا وفق الصلاحيات السابقة. يظهر تنبيه في النموذج؛ لا يعتمد المنع على الواجهة.
- القيد يسري حتى عندما تكون `FINANCE_ENABLED` غير مفعّلة، لتجنب تكوين سجلات جديدة غير قابلة للإسناد قبل تفعيل المالية. أثره التشغيلي: لا يستطيع المحاسب أو المدير تحصيل فاتورة نقدًا أنشأها مستخدم آخر حتى اكتمال الربط الجديد؛ لا يُغيّر الدفعة الأولى وقت إنشاء فاتورة. إعادة طلب محفوظ قديم بنفس هوية المسجّل والحمولة تظل replay بلا إنشاء ثانٍ، بينما رفض تغيير الحمولة باقٍ.
- نجح اختبار خدمة التحصيل الفعلية الاصطناعي `check:finance:collection-audit` ‏1/1: رفض نقدي من مسجّل آخر دون إدراج، وسماح غير النقدي وتحصيل منشئ الفاتورة مع replay، وreplay لسجل اصطناعي سابق للقيد. كما وضع سجلين تاريخيين اصطناعيين لإثبات أن بيانات ما قبل القيد ما زالت منسوبة خطأً، واختبر استمرار قبول بيع أولي وتحصل لاحق لمنشئه بعد إقفال عهدته دون حركة. نجح HTTP ‏1/1 لرفض POST المحاسب والتنبيه والسماح ببطاقة وتحصيل المنشئ مع replay، وسياسات التجارة 16/16، واختبار قيد المصروف 1/1، والإقفال 2/2، وTypeScript و`git diff --check`.
- هذا **ليس تنفيذًا نهائيًا لسياسة المستخدم**: ما زال تسجيل تحصيل نقدي للفاتورة التي أنشأها صاحب عهدة مقفلة ممكنًا، والدفعة الأولى بلا ربط حساب، ولا يُنشئ التحصيل النقدي الحالي حركة الخزنة تلقائيًا. القيد لا يصحح التاريخ أو يمنع كل مخاطر الإقفال أو يثبت التزامن. يجب استكمال نموذج الإسناد والتسويات والانتقال ومراجعة قواعد البيانات واختبار PostgreSQL قبل النشر؛ لم تُنفذ ترقية إنتاجية.

### قيد مؤقت للعهدة المفتوحة عند التحصيل النقدي
- وافق المستخدم على اشتراط عهدة مفتوحة للمسجّل في فرع الفاتورة مؤقتًا عند تفعيل المالية، بما في ذلك المدير والمحاسب إلى حين اكتمال مسار الخزنة. أضيف الحارس داخل معاملات خدمات الدفعة الأولى في بيع الكتالوج والبيع المخزني، والتحصيل اللاحق، بعد صلاحية الدور والتحقق من replay. يقفل الخادم العهدة ويعيد فحص الإقفال، ويرفض إن لم توجد عهدة واحدة مفتوحة. عند الحفظ يزيد مراجعة الحساب لكي لا يُعتمد جرد سابق كما لو لم يحدث التحصيل؛ لا ينشئ حركة نقدية فورية، ويظل حساب التسوية الحالي يستخدم صافي الفترة. غير النقدي غير متأثر بهذا الشرط.
- يظل قيد «مسجّل التحصيل اللاحق هو منشئ الفاتورة» السابق مفروضًا حتى عند تعطيل المالية؛ شرط العهدة الجديد لا يعمل إلا عند `FINANCE_ENABLED=true`. القيد الجديد يوقف النقد للإدارة أيضًا عند غياب عهدة، **ولا ينفّذ بعد الاختيار النهائي للخزنة** الذي وافق عليه المستخدم. عند الرفض لا تُحفظ الفاتورة أو التحصيل، وreplay عملية محفوظة سابقًا لا يشترط إعادة فتح العهدة ولا يكررها. عُدلت تلميحات البيع والتحصيل لإظهار الشرط وعدم الادعاء بأن النقد يُسجّل تلقائيًا على الفرع؛ مؤشرات اليوم قد تشمل بيانات سابقة.
- نجح `check:finance:cash-custody-service` ‏1/1 على خدمات البيع المخزني والكتالوج والتحصيل اللاحق الفعلية بقاعدة اصطناعية: رفض الغياب والإقفال مع عدم إنشاء سجلات، وسماح العهدة المفتوحة، وreplay، وتحديث المراجعة ورفض الجرد القديم، وبقاء البطاقة ممكنة، واختبار تعطيل المالية. نجح أيضًا تدقيق التحصيل ‏1/1 وHTTP ‏1/1 للرفض بعد إقفال العهدة ونجاح البطاقة والتحصيل النقدي للمسجّل المخوّل؛ اختُبر الدفع الأول مباشرة بالخدمة لا HTTP. نجحت التسوية 6/6، والمصروف 1/1، والتجارة 16/16، وTypeScript و`git diff --check`. HTTP بـPGlite وNode fetch لا يثبت تفاعل المتصفح.
- هذه الجولة تحدّ من عيب التحصيل بعد الإقفال **عند تفعيل المالية** ولا تدّعي معالجة كل التزامن. يعتمد التجميع الحالي على طوابع زمن معاملات التحصيل والتسوية، ولم يُختبر سباق PostgreSQL الحقيقي بين إقفال/تسوية/جرد والتحصيل؛ قد يحتاج ذلك إلى ربط عناصر ثابت ومراجعة ترتيب الأقفال والحدود الزمنية. الدفعات السابقة، وفتح العهدة البديلة، واختيار الخزنة النهائي، وانتقال التاريخ غير معالجة؛ لم يُشغّل SQL إنتاجي أو نشر.

### قيد التحصيل أثناء التسوية أو الجرد المفتوح (مؤقت، بيانات اصطناعية)

بعد موافقة المستخدم، يُرفض التحصيل النقدي الجديد عند تفعيل المالية إذا كانت عهدة المسجّل في فرع الفاتورة تحمل طلب تسوية أو جردًا بحالة `OPEN`، سواء الدفعة الأولى في الكتالوج أو المخزون أو التحصيل اللاحق، بما يشمل الإدارة. لا يُمنع غير النقدي ولا إعادة الطلب المحفوظ سابقًا، وتبقى إجراءات الإلغاء أو البت وفق صلاحياتها. أُضيف تنبيه إلى النماذج. الحارس يقفل الحساب ويفحص الطلبات داخل معاملة التحصيل؛ إنشاء تسوية أو جرد مباشر أو موجه يرفع `revision`، ويسجل الجرد المراجعة الجديدة. يهدف تغيير صف الحساب إلى إجهاض snapshot أقدم في Serializable، مع إعادة المحاولة ضمن الحدود المطبقة؛ لا يثبت PGlite سلوك التزامن الحقيقي أو توافق رموز الأخطاء في PostgreSQL. يظل التحقق على PostgreSQL الحقيقي وتدقيق ترتيب الأقفال وإعادة المحاولة مطلوبين، خصوصًا أن تقديم الجرد الموجه/البت يقفل سجل الجرد ثم الحساب بينما الإنشاء يقفل الحساب أولًا. الاستعلام عن الطلبات المفتوحة في حارس التحصيل لا يقفل صفوفها. رفع المراجعة عند إنشاء تسوية يجعل جردًا سابقًا قديمًا حتى بلا حركة نقدية؛ هذا سلوك محافظ مقصود ومختبر.

نجح `check:finance:cash-custody-service` على بيانات اصطناعية لمسارات البيع الثلاثة مع تسوية وجرد مباشر وموجه، ورفض الحفظ وعدم تأثر غير النقدي وreplay واستئناف النقد بعد الإلغاء؛ واختبار `check:finance:access:http` أثبت رفض POST نقدي مع تسوية مفتوحة والبت فيها ثم النجاح وإعادة الطلب. نجح `check:finance:staff:http` و`check:finance:collection-audit` و`tsc --noEmit` و`git diff --check`. HTTP فشل مرة قرب نهاية الاختبار بسبب انقطاع خادم التطوير، ثم نجح كاملًا بحد ذاكرة Node قدره 2560 MB. لا يغطي هذا القيد مصروف `HOLDER_CASH` أو سائر الحركات، ولا يصلح ربط التحصيل بالحركات أو الأرصدة والبيانات التاريخية.

**عيب اكتُشف أثناء الاختبار ويتطلب معالجة منفصلة قبل النشر:** عند جرد عهدة لها مبيعات/مصروفات فترة غير مسوّاة، يحسب المحرك فرق الجرد من المتوقع في اليد، لكنه يحفظ الرصيد الدفتري في `observed_balance`، بينما قيد SQL يشترط `difference = counted_amount - observed_balance`؛ مثال اصطناعي رصيد دفتري صفر ومبيعات غير مسوّاة 22 ومعدود 22 يفشل إدخاله بـ`23514`. لا تُعد هذه الحالة مغطاة بنجاح اختبار الحارس؛ يلزم تصميم متوافق للمرجع والفرق والترحيل وبيانات الجرد القديمة، مع اختبارات مستقلة قبل تعديل SQL أو المحرك. لم تُطبّق ترقية إنتاجية أو تنشر تغييرات.

### إصلاح مرجع الجرد على العهدة

عولج تعارض الجرد المذكور أعلاه في المحرك، دون تعديل قيد SQL أو تنفيذ ترقية على أي بيانات: أصبح `observed_balance` في الجرد الجديد هو **المتوقَّع في اليد** (الرصيد الدفتري + تحصيلات الفترة النقدية − مصروفات نقد الموظف)، و`difference` هو المعدود ناقص هذا المرجع، متوافقًا مع قيد الجدول ومع التحقق عند التأكيد. للخزنة يظل المرجع رصيدها الدفتري. يسجل التدقيق المرجع والرصيد الدفتري كلًا على حدة. جرد صاحب العهدة الموجّه يستخدم المرجع نفسه، ويلتقط المراجعة وتاريخ القاهرة عند إقرار الموظف لا عند إنشاء الطلب، لأن مصروفًا أو حركةً أخرى قد تقع أثناء الانتظار؛ ويُرفض تأكيده قبل تسجيل الموظف، مع إظهار حالة الانتظار وإبقاء الإلغاء. لم تعد الجرود المباشرة تظهر للموظف كطلبات موجّهة. صار ترتيب أقفال تقديم الجرد الحساب ثم الجرد، مثل التأكيد.

في قاعدة اصطناعية أُثبت مثال رصيد 1000 ومبيعات 5000 ومصروف 800: جرد مطابق 5200 بلا حركة، وزيادة 100 تحرك 100 فقط، ثم جرد موجّه بعد مصروف إضافي ينتج عجز 20 ويحركه مرة واحدة، ثم تسوية الفترة تحرك 4180 دون خصم المصروف مرة ثانية. اختُبر replay، ورفض التأكيد المبكر، والتقاط المراجعة بعد حركة أثناء انتظار الموظف، والرفض المحافظ لمثال جرد قديم غير متوافق دون تعديل أو ترحيل. `settlement-engine` نجح 7/7 و`check:finance:app-engine` 3/3 و`check:finance:staff:http` 1/1 و`check:finance:holder-cash-audit` 1/1 و`check:finance:closure` 2/2 و`check:finance:cash-custody-service` 1/1 وtypecheck. اختبار HTTP أثبت أيضًا إخفاء التأكيد ورفض POST المبكر ثم إتاحته بعد إقرار الموظف؛ ليس اختبار تفاعل متصفح.

**حدود لازمة قبل النشر:** لم تُعد كتابة أي جرود أو حركات تاريخية. الجرود القديمة الموجّهة ربما خزّنت الرصيد الدفتري بدل المتوقع؛ يرفض التأكيد عندما يختلف المرجع الحالي، لكن تطابق الأرقام وحده ليس إثباتًا لصحة كل حالة تاريخية. يلزم جرد ومراجعة بشرية للطلبات القديمة المفتوحة والجرود المؤكدة وآثارها وخطة تصحيح معتمدة بدل backfill آلي. سياسة إسناد التحصيلات القديمة وتوقيت التسوية والمصروفات وعمليات قاعدة PostgreSQL المتزامنة لا تزال بحاجة لتدقيق مستقل؛ المثال الاصطناعي لا يثبت سلامة البيانات الفعلية أو التشغيل الإنتاجي.

### اختبار تزامن PostgreSQL اصطناعي وإصلاح إعادة المحاولة

أُنشئ اختبار `check:finance:postgres-concurrency` بخادم PostgreSQL 18.6 محلي مؤقت منعزل على Unix socket بلا TCP، وقاعدة وبيانات اصطناعية؛ لا يقرأ `DATABASE_URL`. يستخدم عميل Prisma WASM مع `@prisma/adapter-pg`، وحواجز بعد الحصول على قفل الحساب مع التحقق من انتظار الطرف الآخر فعليًا في `pg_stat_activity`. تعليمات التشغيل ومتطلباته في `prototypes/finance-postgres-tests/README.md`، وثنائيات PostgreSQL حُمّلت في `/tmp` ولم تُضف للمستودع.

كشف الاختبار أن تعارض الصف لدى حارس المالية يعود برمز PostgreSQL المحوّل `40001` من `financePort`، بينما كانت عمليات التجارة تعيد المحاولة فقط لـ`P2034`؛ فكانت تُجهض التحصيل بأمان لكن تعرض خطأ بدل إعادة المحاولة. أُضيفت إعادة محدودة للرمزين `40001` و`40P01` مع إبقاء `P2034` في البيع والتحصيل والكتالوج. يطبع محرك المالية الآن `P2034` إلى `40001` أيضًا لمعالجة التعارضات عند حدود معاملة Prisma خارج `financePort`، مع الحفاظ على حد المحاولات. اختُبر الأخير بحقن خطأ اصطناعي داخل المعاملة قبل commit، وليس خطأ commit حقيقيًا.

نجح الاختبار على PostgreSQL الفعلي: سباق التحصيل اللاحق وإنشاء التسوية بالترتيبين؛ الجرد المباشر والموجّه قبل التحصيل؛ التحصيل قبل جرد بمبلغ متوقع قديم؛ سباق الدفعتين الأوليين للكتالوج والمخزون أمام الجرد؛ والإقفال والتحصيل بالترتيبين. أثبت غياب الفاتورة/التحصيل المرفوض واحتساب التحصيل في التسوية المعاد طلبها ورفض إقفال العهدة غير المسوّاة. لم يختبر جميع التداخلات الممكنة. نجحت كذلك `check:finance:cash-custody-service` 1/1 و`check:commerce` 16/16 و`settlement-engine` 7/7 و`check:finance:holder-cash-audit` 1/1 وtypecheck و`git diff --check`.

**الحدود:** PostgreSQL وبياناته هنا للاختبار فقط؛ لم يُختبر محرك Prisma الأصلي في بيئة النشر ولا كل الإصدارات/مستويات العزل أو تزامن المصروفات والتأكيدات والتواريخ المتساوية والبيانات القديمة. لا يكتمل الربط المحاسبي النهائي بهذا الإصلاح، ولا تزال مراجعة التوقيت وإسناد التاريخ والموافقات والإطلاق مطلوبة. لم تُمس أي قاعدة فعلية أو تُجر أي عملية نشر.

### متابعة تزامن مصروف نقد الموظف وحدود الطابع الزمني

وُسع اختبار PostgreSQL الاصطناعي ليغطي اعتماد تسوية صفرية أثناء انتظار مصروف `HOLDER_CASH` على صف المصروف: أُجبرت بداية الصرف قبل الاعتماد وتأخره إلى ما بعد commit؛ اكتُشفت إعادة محاولة فعلية، ودخل المصروف الفترة التالية. وبالعكس، صُرف المصروف أولًا أثناء انتظار الاعتماد، فرفض المحرك التسوية القديمة. اختُبر أيضًا سباق الصرف وإقفال العهدة بالترتيبين: بعد الإقفال يُرفض الصرف بلا سجل دفع؛ وبعد الصرف يُرفض الإقفال مع مصروف غير مسوّى. هذه النتائج محددة بالترتيبات المختبرة، ولا تثبت كل السباقات.

**حدّ غير محلول مُثبت اصطناعيًا:** أُدرج تحصيل تجريبي بتاريخ `created_at` يساوي تمامًا `resolved_at` لتسوية مؤكدة. شرط الفترة الحالي `>` يستبعده؛ الحالة المصطنعة تثبت غموض حد الزمن، ولا تثبت ترتيب تحصيل حقيقي. لا يُغيّر الشرط إلى `>=` عشوائيًا لأن ذلك قد يعيد احتساب حدث داخل تسوية سابقة؛ يلزم ربط ثابت أو أدلة ترتيب وتسوية بيانات قديمة، وهو جزء من الربط المحاسبي النهائي. اختبار `check:finance:postgres-concurrency` نجح 1/1 بعد التوسيع، و`tsc --noEmit` و`git diff --check` نجحا. لم تُستخدم بيانات فعلية أو يُنشر شيء.

### تجربة تحديد الفترة بمعرّفات التحصيل والصرف

أُضيفت إلى نموذج التخصيص المعزول جداول اصطناعية لربط دفع `HOLDER_CASH` بعهدة مسجّله، وإيصال يثبت معرّفات تحصيلات ومصروفات الفترة وبصمة القيم المراجَعة. تعيد التجربة قراءة العناصر وقفلها وتتحقق من القائمة والبصمة والإجماليات قبل ربطها بالتسوية في معاملة واحدة؛ يسجل إيصال حتى للفترة الفارغة، وتبقى العناصر اللاحقة غير مسوّاة حتى لو ساوى وقتها وقت التسوية السابقة. يُرفض إلحاق عناصر بتسوية قديمة مؤكدة بلا إيصال. تبقى هذه التجربة منعزلة عن التطبيق ولا تسجّل حركة تسوية فعلية.

نجح `check:finance:period-prototype` 1/1 اصطناعيًا لتخصيص الصرف، التراجع الذرّي، تغيّر العناصر أو مبالغ متعاكسة مع بقاء الإجمالي، اختلاف الإجمالي، replay، الفترة الفارغة، الطابع الزمني المتساوي والطلب القديم؛ ونجح `check:finance:collection-prototype` 1/1. ووسع `check:finance:postgres-concurrency` على PostgreSQL اصطناعي لاختبار ترتيبين فقط بين تحصيل تجريبي وإثبات الفترة: في أحدهما يُلغى التحصيل الأقدم ويُعاد بعد الالتزام ويبقى معلقًا؛ وفي الآخر تفشل المراجعة القديمة بعد إعادة المحاولة ويبقى طلب التسوية مفتوحًا.

**غير مكتمل وغير صالح للنشر:** لا تسجّل التجربة حركات التسوية أو التحويل، ولا تتكامل مع الجرد والإقفال والرد والتصحيح وبيانات التاريخ أو صلاحيات التطبيق، ولا تطبق قيود عدم التغيير ضد SQL مباشر. ترتيب الأقفال التجريبي بين الحساب وصفوف المصدر مختلف ويحتاج تصميمًا موحدًا وتغطية deadlock وتزامن المصروفات؛ لا يستنتج نجاح اختبارين سلامة بقية التداخلات. يلزم كذلك تصميم مراجعة الأدلة القديمة ونقطة الانتقال والمطابقة والرجوع قبل أي ربط فعلي أو ترقية.

### متابعة إعادة التحويل وترتيب أقفال نموذج الفترة

أزيل فحص إقفال مبدئي من إجراء HTTP للتحويل لأنه كان يسبق فحص إعادة الطلب في المحرك: أدى ذلك إلى رفض إعادة إرسال تحويل محفوظ بعد إقفال أحد طرفيه. فحص الإقفال الخادمي داخل معاملة المحرك وبعد قفل الحسابات ما زال قائمًا للعمليات الجديدة. اختبار `check:finance:account-open:http` نجح 1/1: تحويل ذهاب وعودة ثم إقفال، وإعادة الطلبين دون تكرار الحركة، ورفض طلب جديد أو بيانات معدلة أو ممثل مختلف، ورفض replay عند سحب صلاحية التحويل. بقي رصيد الخزنة كما كان. اختبار HTTP ببيانات اصطناعية لا يثبت تفاعل المتصفح.

في نموذج الفترة التجريبي فقط، عُدّل تخصيص التحصيل والمصروف إلى قراءة بيانات المصدر أولًا بلا قفل، ثم قفل الحساب، ثم قفل المصدر وإعادة التحقق منه، بدل قفل المصدر قبل الحساب؛ هذا يزيل انقلاب ترتيب محدد مع التقاط الفترة التجريبي ولا يثبت ترتيب بقية النظام. وُسع اختبار PostgreSQL الاصطناعي ليشمل توقيتَي تخصيص دفع `HOLDER_CASH` تجريبي والتقاط الفترة، في معاملة اصطناعية واحدة للدفع والتخصيص؛ عند فوز الالتقاط تتراجع معاملة الصرف الأقدم وتُعاد، وعند فوز الصرف تُرفض المراجعة القديمة وتبقى الدفعات معلقة. ليس هذا تكاملًا مع إجراء الصرف الفعلي. ما زال توحيد أقفال الفاتورة والمصروف والخزنة والتسوية، واختبار الاختناقات والمصادر القابلة للتعديل وrollback وقطع الاتصال مطلوبًا قبل الاستخدام. نجحت اختبارات النموذجين 1/1 لكل منهما وPostgreSQL 1/1 والإقفال 2/2 وصلاحيات المالية 36/36 وtypecheck و`git diff --check`. لم تُنشر تغييرات ولم يُستخدم تاريخ فعلي.

### جرد حراس الصفحات ومفاتيح الاستدعاء

أُغلقت حالة الخطأ البرمجي في مستدعي الحارس: مفتاح كتابة غير معروف يُرفض الآن حتى للأدمن وعند تعذر قراءة المخزن، والمسار الذي لا يمكن ربطه بصفحة مسجلة يُحوَّل بدل المرور. هذا لا يغيّر سياسة تجاهل **القواعد القديمة المخزّنة** ذات المفاتيح غير المعروفة، ولا يغيّر fail-open للمفاتيح المعروفة عند تعذر المخزن. المسارات الديناميكية المعروفة تستمر في الرجوع إلى الصفحة الأم.

أُضيف `check:access:page-inventory` لفحص ملفات الصفحات كلها مقابل السجل والحارس، مع استثناء صريح للداشبورد الدائم والإدارة والإعداد والديناميكيات. هذا فحص مصدر لا يثبت ترتيب كل استعلام أو سلامة بيانات كل عنصر. وأُضيف `check:access:pages:http` بثلاث قواعد PGlite اصطناعية منفصلة: فُرض منع قالب المحاسب على 25 صفحة مسجلة (6 مبيعات و6 مخزون و13 مالية) وفُحص رفض طلبات GET المباشرة، وكذلك صفحتا تفاصيل الفاتورة والمصروف، وعدم ظهور علامتي بيانات اختبار في الاستجابة المرفوضة. لكل مجموعة فُحص منع مدير غير أدمن، واستثناء سماح لحساب المحاسب وتجاوز الأدمن لقالب المدير في صفحة واحدة. لا يختبر كل صفحات كل دور، ولا كل بيانات العناصر أو إجراءات POST، ولا تفاعل متصفح. `check:access:pages:http` نجح 3/3، و`check:access:page-inventory` 2/2، و`check:finance:access` 37/37، و`check:api:access` 3/3، وtypecheck و`git diff --check`. بقيت الحاجة لتغطية الإجراءات والعناصر والحالات غير المختبرة، وقيود النظام المالية وسياسة fail-open كما سبق.

### حراسة الإدارة أمام العهدة والتزامن (بيانات اصطناعية)

- عند تفعيل المالية، يُرفض نقل المستخدم أو إيقاف حسابه عند وجود عهدة مفتوحة، ويُرفض إيقاف الفرع عند وجود عهدة مفتوحة أو موظفين نشطين. إذا تعذّر استعلام العهد فلا تُعامل النتيجة كصفر: تُلغى المعاملة وتظهر رسالة تحقق. كان هذا السلوك السابق عند تعطيل المالية؛ تغيّر وفق القرار الموثق أدناه.
- تُنفَّذ تحديثات المستخدم، وإنشاؤه، وتفعيل الفرع أو إيقافه بمعاملات Serializable، مع قفل الفرع المختار قبل المستخدم، وإعادة محاولة تعارضات التسلسل/التشابك بحد أقصى. يُعاد فحص حالة الفرع والمستخدم داخل المعاملة، وتُلغى جلسات المستخدم الموقوف داخلها. فتح العهدة يقفل الفرع ثم صاحبها؛ لذلك لا يُعتمد على فحص سابق للمعاملة. هذا لا يغني عن مراجعة مسارات كتابة أخرى أو اختبار محرك Prisma الأصلي.
- حماية مؤقتة للطلبات القديمة: لا تُفتح عهدة بالموافقة على طلب إذا لم يعد مقدمه نشطًا وفي فرع الطلب، أو صار الفرع غير نشط. يبقى رفض الطلب متاحًا، وإعادة الطلب المعتمد لا تنشئ عهدة جديدة. هذه ليست تسوية نهائية لسياسة نقل الطلبات المعلقة أو معالجة التاريخ.
- أضاف اختبار PostgreSQL المؤقت حقن فشل استعلام العهدة للتحقق من عدم حفظ نقل المستخدم أو إيقاف الفرع؛ واختبر ترتيبَي فتح العهدة مقابل النقل، والموافقة على الطلب مقابل النقل/الإيقاف، وترتيبَي إنشاء مستخدم مقابل إيقاف الفرع. اختُبرت أيضًا الطلبات القديمة بعد النقل والإيقاف مع بقاء الرفض متاحًا. يستعمل الاختبار Prisma WASM وبيانات اصطناعية؛ لا يثبت جميع التداخلات، ولا يختبر هذه الإجراءات الإدارية عبر HTTP، ولا يراجع البيانات التاريخية.

### تثبيت مراجعة العهدة عند طلب التسوية
- كان فحص قِدم الجرد عند الاعتماد يعتمد على `created_at > created_at`؛ وهو لا يثبت ترتيب الالتزام، وقد يفوّت صرفًا ذا طابع مساوٍ. أُضيفت لقطة `account_revision` للطلب تُحفظ بعد زيادة مراجعة العهدة تحت قفلها، ويُرفض الاعتماد إذا تغيّرت المراجعة أو لم توجد لقطة موثوقة. فحص الطوابع السابق باقٍ كحماية إضافية، وليس بديلًا عن تخصيص العناصر.
- حتى اعتماد تسوية صفرية بلا حركة يزيد الآن مراجعة العهدة، بما يجعل معاملات الكتابة الأقدم التي تتعارض معها تعيد المحاولة تحت Serializable. الإلغاء والرفض وإعادة الطلب المعتمد تظل متاحة وفق صلاحياتها. التغيير محافظ: أي زيادة مراجعة للعهدة بعد الطلب قد تتطلب إلغاءه وإعادة الجرد حتى لو لم تتحرك أموال فعليًا.
- أُضيفت ترقية يدوية منفصلة `prisma/manual-settlement-revision-upgrade.sql` للأنظمة التي طبقت الترقية السابقة، كما أضيف العمود لملف التسوية الأصلي للتركيبات الجديدة. لا تُحدّث الترقية بيانات قديمة: الطلبات المفتوحة القديمة بقيمة NULL لا تُعتمد، ويجب مراجعتها وإلغاؤها وإعادة جردها؛ الطلب الجديد يُرفض برسالة جاهزية إذا لم يُثبَّت العمود. لم تُطبق الترقية على قاعدة فعلية، وتحتاج خطة نشر وإذنًا منفصلين.
- اختبار PGlite اصطناعي صنع مساواة بين وقت الدفع ووقت الطلب بعد صرف `HOLDER_CASH` فعلي، وأثبت أن فحص الوقت وحده لا يراه وأن لقطة المراجعة تمنع الاعتماد دون حركة؛ ثم ألغى الطلب وأعاد الجرد واعتمد الجديد واختبر replay. اختُبر عدم ملء القديم، وإعادة تنفيذ الترقية، ورفض الإنشاء دون العمود. PostgreSQL المؤقت اختبر ترتيبَي الصرف والاعتماد، وتحقق أن الاعتماد الصفري يزيد المراجعة وأن الصرف المنتظر يُعاد ولا يسقط من الفترة في السيناريو المختبر. نجحت التسوية والترقية 10/10، PostgreSQL ‏1/1، المحرك ‏3/3، الإقفال ‏2/2، حراسة التحصيل ‏1/1، صرف الموظف ‏1/1، staff HTTP ‏1/1، وTypeScript وdiff-check.
- **حدود:** لا تكشف المراجعة كتابةً خارج المسارات التي ترفعها، ولا تحل مساواة الطابع مع وقت اعتماد سابق داخل معادلة `settlementPeriod` أو تخصيص التحصيلات والمصروفات التاريخية. لا يزال ربط العناصر والقطع المحاسبي والتدقيق والمراجعة على محرك Prisma الأصلي ضرورية قبل النشر.

### تجربة خدمات فعلية مع مخصصات الفترة الاصطناعية
- أُضيف اختبار معزول `check:finance:runtime-prototype` يستخدم الخدمات الفعلية للتحصيل اللاحق والدفعة الأولى للكتالوج والمخزون وصرف `HOLDER_CASH`، مع مُعترِض للاختبار فقط يضيف تخصيص النموذج داخل معاملة الخدمة نفسها. لا تستورد خدمات التطبيق المُعترِض أو الجداول التجريبية. فشل اصطناعي بعد التخصيص أثبت التراجع عن التحصيل/الفاتورة وتغيير المخزون والتخصيص والمراجعة، وعن صرف المصروف وحالته. اختُبر النجاح وreplay دون تخصيص مكرر، وتعارض تعديل طلب، وتجاوز البطاقة للتخصيص النقدي.
- في PostgreSQL المؤقت اختُبر الصرف الفعلي مع مُعترِض التخصيص مقابل التقاط الفترة **الاصطناعي** بالترتيبين: عند تقدم الالتقاط أُعيد الصرف وبقي معلقًا للفترة التالية، وعند تقدم الصرف رُفضت المراجعة القديمة وبقي الصرفان معلقين. الالتقاط هنا يغير حالة اختبارية ولا ينفّذ اعتماد التسوية الحقيقي أو حركاته. نجح الاختبار 1/1 ونموذج الفترة 1/1 ونموذج التحصيل 1/1 واختبار الخدمات 1/1 وTypeScript وdiff-check.
- القيود المؤقتة في خدمات التحصيل ما زالت سارية؛ لم يُختبر مسار خزنة الإدارة النهائي عبر هذه الخدمات. يزيد الحارس الحالي والمخصص التجريبي مراجعة العهدة كلٌّ على حدة، وهو تفصيل يجب حسمه عند التصميم الفعلي. لم يُدمج النموذج في التسوية أو الجرد أو الإقفال أو التصحيح والردود، ولم يُختبر HTTP أو المتصفح أو محرك Prisma الأصلي للتكامل الجديد. الربط النهائي وترحيل التاريخ والسياسة النهائية ما زالت غير منجزة؛ لم تُنفذ ترقية أو نشر.

### ترتيب أقفال مخصص التحصيل الاصطناعي أمام التحويل
- كشف PostgreSQL الاصطناعي تعارضًا في النموذج التجريبي عند توصيله بالخدمة عبر مُعترِض الاختبار: كانت الخدمة تمسك عهدة المسجّل، ثم يحاول المخصص قفل كل حسابات الفرع المرشحة بما فيها الخزنة. عند حبس الخزنة اصطناعيًا انتهى التحصيل بـ`55P03`؛ ومع تحويل يمسك الخزنة ثم ينتظر العهدة قد ينقلب ترتيب الأقفال. لم يُثبت ذلك وحده حدوث deadlock في الإنتاج، إذ المخصص غير مفعّل أصلًا.
- عُدّل **النموذج فقط** لقراءة المرشحين ثم قفل الوجهة المختارة وإعادة التحقق منها قبل قفل المصدر وتخصيصه، بدل قفل الخزنة غير المختارة. نجح اختبار الخزنة المحبوسة، واختبار تحويل فعلي متوقف بعد قفل الخزنة مع تحصيل فعلي ممسك بالعهدة: اكتمل التحصيل ثم التحويل، ونجحت إعادة كل طلب بلا أثر مكرر. نجح PostgreSQL ‏1/1، وتجربة التحصيل والفترة والخدمات ‏1/1 لكل، وTypeScript.
- هذا يزيل انتظارًا وانقلابًا محددين فقط، وليس برهانًا على خلو النظام من deadlocks. قراءة المرشحين من لقطة المعاملة لا تحسم سياسة تزامن فتح عهدة جديدة مع اختيار خزنة بديلة؛ ما زالت أقفال الفاتورة والمستخدم والفرع والتسوية والبيانات القديمة واختبارات محرك Prisma الأصلي مطلوبة. لم يُربط النموذج بالتطبيق، ولم تُستخدم أو تُحدّث قاعدة فعلية أو يُنشر شيء.

### اختبار الاعتماد الفعلي مع تخصيص تجريبي وتحذير تساوي الإجماليات
- وُسّع مُعترِض الاختبار فقط ليُلحق معرفات التحصيلات والمصروفات وإيصال مراجعتها مباشرة بعد تحديث الاعتماد داخل معاملة `confirmSettlement` الفعلية. في PGlite اصطناعي اختُبرت حركتا التسوية والتسليم الفعليتان، وتغيّر قيم عناصر بإجمالي ثابت، والفشل بعد الإلحاق والتراجع عن الحالة والحركات والإيصال، وreplay، وبقاء التحصيل اللاحق معلقًا.
- في PostgreSQL المؤقت اختُبر الاعتماد الفعلي مع الحركات مقابل `payExpense` الفعلي بالترتيبين باستخدام المُعترِض فقط: عند تقدم الاعتماد أُلحقت العناصر المراجعة وبقي الصرف اللاحق للفترة التالية؛ وعند تقدم الصرف رُفض الاعتماد القديم وبقيت العناصر بلا إلحاق ولم تُنشأ حركاته. لم يتحول ذلك إلى ربط في التطبيق.
- أثبتت حالتان اصطناعيتان أن **تساوي الإجماليات لا يثبت تطابق العناصر**: تحصيل تاريخي بجهة تسجيل مختلفة، وصرفان على حد طابع زمني، أنتجا إجماليات متطابقة بمجموعتي معرفات مختلفتين بين المعادلة الحالية والتخصيص. أضيف للنموذج فحص محافظ لهويات التحصيلات والمصروفات وفق المعادلة الحالية، ويرفض الحالتين ويتراجع عن الاعتماد. تطابق المعرفات أيضًا لا يثبت صحة النقد الحقيقي أو التاريخ؛ المعادلة القديمة نفسها قد تكون خاطئة.
- نجحت تجربة الخدمات ‏1/1، وPostgreSQL ‏1/1، ونموذجا الفترة والتحصيل ‏1/1 لكل، والتسوية ‏9/9، وصلاحيات المالية ‏37/37، وTypeScript وdiff-check. المُعترِض يفترض استدعاءه بعد اعتماد جديد في المعاملة نفسها ولا يثبت ذلك ذاتيًا؛ لا يُستخدم لإلحاق سجلات مؤكدة قديمة. ترتيبات الأقفال والتاريخ والجرد والإقفال والردود والتصحيحات والخزنة والانتقال والنشر الفعلي لا تزال غير مكتملة. لم تُمس بيانات فعلية أو تُنفذ ترقية عليها.

### إعادة فتح العهدة — اختبار فهرس اصطناعي غير مفعّل
- بقي الفهرس الفعلي `finance_custody_per_holder` كما هو، ولا يسمح حاليًا بفتح عهدة ثانية لنفس الموظف والفرع بعد الإقفال. أُنشئ فهرس جزئي بديل **للاختبار الاصطناعي فقط** في `prototypes/finance-custody-reopen/index.test-only.sql` مع opt-in صريح؛ ليس ملف ترقية ولا يجوز تشغيله على بيانات فعلية.
- تبيّن أن مجرد تغيير الفهرس لا يكفي: حارسا التحصيل وصرف `HOLDER_CASH` كانا يعدّان العهد المغلقة ضمن المرشحين. عُدّلا لاختيار العهدة المفتوحة فقط تحت القفل ورفض الالتباس؛ احتُفظ برسالة العهدة المقفلة للصرف عندما لا توجد مفتوحة. عُدّل مخصص المصروف الاختباري كذلك. هذه التغييرات لا تفتح عهدة بديلة في التطبيق ما دام الفهرس الفعلي قائمًا.
- اختبار PGlite اصطناعي سوّى وأقفل العهدة الأولى ثم فتح بديلتها تحت الفهرس التجريبي، واختبر التحصيل والصرف للعهدة الجديدة وإعادة طلبات العهدة القديمة ورفض وجود عهدتين مفتوحتين في مخطط أُفسد عمدًا. واختبر PostgreSQL المؤقت تنافس طلبَي فتح، والفتح بينما الإقفال غير ملتزم، ومعاملة فتح بدأت قبل تحصيل وتسوية وإقفال العهدة القديمة؛ في التداخل المختبر فرض تعارض Serializable إعادة المحاولة ومنع دخول التحصيل القديم في الفترة الجديدة.
- نجحت تجربة إعادة الفتح وPostgreSQL والحراسة والصرف والخدمات ونموذج الفترة ‏1/1 لكل، والإقفال ‏2/2، والتسوية ‏9/9، وHTTP المصروفات ‏1/1 وTypeScript وdiff-check. لا تثبت هذه الحالات جميع التوقيتات أو صحة التاريخ؛ معادلة الفترة ما زالت تستخدم الطوابع الزمنية والإسناد القديم. لا تُستبدل قيود الإنتاج قبل تصميم التخصيص والانتقال والتاريخ والاختبار والموافقة.

### مقارنة عناصر فترة الانتقال — قراءة اصطناعية فقط
- أُضيف فحص معزول في `prototypes/finance-cutover-period-audit/` يقارن **معرفات** التحصيلات وصرف نقد الموظف بين معادلة الفترة الحالية والتخصيص التجريبي لعهدة محددة، ويعرض المشترك والموجود في أحد الجانبين فقط، والتساوي مع حد الفترة أو وقت الإقفال، والسجلات ذات الطابع بعد الإقفال، وبعض تناقضات التخصيصات المفتوحة مثل فرع أو مسجّل خاطئ أو مصدر غير نقدي. المجموعات قد تتداخل عمدًا.
- يشترط الاختبار opt-in ومعاملة قراءة فقط بلقطة متكررة؛ لا يحدّث أو يرحّل أي سجل. اختبر PGlite بيانات اصطناعية متساوية الإجماليات ومختلفة المعرفات، والحدود المتساوية، وحسابًا مقفلًا بأحداث لاحقة وطلبات مفتوحة، وتخصيصًا إلى فرع خاطئ أو لمصدر غير نقدي، وتخصيصًا سبق ربطه بتسوية، وسلامة البيانات قبل الفحص وبعده. اختبر PostgreSQL قراءة لقطة Serializable بعد التداخلات المختبرة في الخدمات الفعلية، دون تغيير مراجعة العهدة أو عدد الإيصالات. نجح الاختبار الجديد ‏1/1، وPostgreSQL ‏1/1، وتدقيق التحصيل القديم ‏1/1، ونموذج الفترة ‏1/1، وTypeScript وdiff-check.
- **ليس تدقيقًا إنتاجيًا أو شهادة جاهزية:** جداول التخصيص تجريبية وغير موجودة في التطبيق، وتطابق العناصر لا يثبت مكان النقد أو صحة التسويات التاريخية، والطابع الزمني لا يثبت ترتيب الالتزام. لا يشمل الفحص الردود والتصحيحات والأرصدة وتاريخ كل التسويات والأدلة الخارجية أو الخصوصية والأداء على قاعدة كبيرة. لا يُشغّل على بيانات فعلية ولا ينتج تعليمات ترحيل أو تسوية تلقائية؛ يلزم تصميم وموافقة منفصلان قبل أي وصول فعلي.

### حراسة أمر حالة المستخدم خارج الواجهة
- كان الأمر المحلي `npm run user:status` يحدّث حالة المستخدم مباشرة ويتجاوز حراسة العهدة الموجودة في واجهة الإدارة. أصبح يستخدم خدمة الإدارة نفسها، بقفل المستخدم ومعاملة Serializable وإعادة محاولة التعارض، مع إلغاء الجلسات داخل المعاملة عند الإيقاف أو التنشيط.
- لأن بيئة الأمر قد تفتقد `FINANCE_ENABLED` بينما قاعدة البيانات تحتوي المالية، يتحقق الأمر من مخطط المالية وجدول الحسابات عند الحاجة: يفحص العهد عند وجود الجدول، ويرفض إذا كان المخطط جزئيًا أو تعذّر الاستعلام، ويرفض غياب الجدول عندما يكون المفتاح مفعّلًا. عند غياب المخطط تمامًا والمفتاح غير مفعّل يمكنه العمل. تستخدم واجهة الإدارة الآن الحراسة المشتركة ذاتها؛ ولا تحمي الحراسة التعديل المباشر لمن يملك صلاحية قاعدة البيانات.
- نجح اختبار PGlite اصطناعي ‏1/1 لغياب المخطط والجدول الجزئي والعهدة المفتوحة وتعطّل الاستعلام وبقاء الحالة والجلسات عند الرفض وإلغاء الجلسات عند النجاح. اختبر PostgreSQL المؤقت ترتيبَي فتح العهدة مقابل أمر الحالة مع وجود الجدول وغياب المفتاح، مع التحقق من الجلسات والحالة؛ نجح ‏1/1. نجحت إدارة HTTP ‏1/1، واختبارات الإدارة ‏7/7، وTypeScript وdiff-check. اختبار HTTP لا يستدعي أمر سطر الأوامر نفسه، وPostgreSQL يستخدم Prisma WASM لا المحرك الأصلي. لم تُستخدم بيانات فعلية أو تُنفذ ترقية أو نشر.

## تعطل مخزن الصلاحيات — قرار منع الوصول المقيّد

اختار المستخدم المنع المؤقت لغير أدمن النظام عند فشل قراءة `access_control`. يبني الحارس مجموعة منع لكل الصفحات والعناصر المسجّلة عدا مسار الداشبورد الدائم، ويرفض الكتابة الخادمية للمفاتيح المعروفة؛ المفتاح غير المعروف يُرفض حتى للأدمن. الأدمن الفعلي يتجاوز المنع ويستطيع فتح الإدارة، لكن لا يمكن حفظ قواعد في جدول معطّل. تعرض الإدارة أن حالة القواعد غير معروفة بدل عرض قواعد فارغة على أنها سماح.

تعود الداشبورد لغير الأدمن بمحتوى آمن **قبل استعلامات بياناتها**، وتتوقف استعلامات الشارات المالية في التخطيط العام عند العطل؛ لا نعتمد على CSS لحماية البيانات. تسجيل الخروج وتغيير كلمة المرور يظلان متاحين، وواجهات البيانات المحروسة تستخدم الحارس نفسه. عند عودة القراءة تُطبّق القواعد المخزنة في الطلب التالي؛ انقطاع المخزن يعني توقف أعمال المستخدمين المتأثرين عمدًا.

`check:access:store-failure:http` يستخدم قاعدة PGlite وخادم Next اصطناعيين فقط: حذف جدول الاختبار لإحداث فشل قراءة فعلي، وفحص ثلاثة أدوار غير أدمن وصفحات مبيعات ومخزون ومالية وAPI وداشبورد بعلامة بيانات مرئية للأدمن؛ اختبر POST مباشرًا وحفظ الأدمن وتحقق من الصفوف بعد إيقاف الخادم. أعاد إنشاء الجدول **في القاعدة الاصطناعية فقط** وأثبت استعادة العرض ونفاذ قاعدة منع محفوظة. إعادة إنشاء جدول فارغ على قاعدة فعلية لا تستعيد قواعدها وقد تمنح وصولًا افتراضيًا؛ يجب استعادة القواعد الأصلية والتحقق من سلامتها، وليس الاكتفاء بإنشاء جدول فارغ. فحوص HTTP عينات وليست إثباتًا لكل إجراء أو بيانات أو متصفح، وPGlite ليس PostgreSQL إنتاجيًا.

قبل أي نشر، يلزم اختبار توفر الجدول وصلاحيات قراءته، وخطة تشغيلية للاستعادة من نسخة موثوقة والتحقق من القواعد وأدوار الأدمن، مع نافذة توقف محتملة وموافقة منفصلة. إسقاط الجدول مع الكود الحالي يؤدي للمنع وليس استعادة الخدمة؛ والرجوع إلى إصدار أقدم قد يعيد سلوك الفتح المؤقت ويحتاج تقييمًا أمنيًا. لم ينفذ أي SQL أو نشر على بيانات فعلية. الأقسام السابقة التي تذكر fail-open تصف الحالة التاريخية وقت اختبارها، لا السلوك الحالي.

## تجربة اصطناعية للفترة عند الجرد والإقفال

أُضيف اعتراض **اختباري فقط** للمعاملة الفعلية للجرد والإقفال يقارن معرّفات ومبالغ التحصيلات والمدفوعات المعلّقة في نموذج التخصيص بمعادلة الفترة الحالية. عند الاختلاف يرمي خطأ بعد الكتابة التجريبية داخل المعاملة، فتتراجع. في حالة اصطناعية طابع التحصيل فيها مساوٍ لافتتاح العهدة، استبعدت معادلة `>` التحصيل المخصّص؛ سجّل المحرك غير المعدّل مرجع جرد صفرًا رغم وجود تخصيص معلّق 10، وسمح بالإقفال مع بقاء التخصيص. لا يثبت هذا السيناريو حيازة نقد فعلية أو حالة تاريخ إنتاجية.

نجح `check:finance:count-close-period-prototype` ‏1/1: رفض الجرد وتأكيده وإقرار الموظف للجرد الموجّه والإقفال مع التراجع عن الآثار، ورفض حالة تساوي الإجماليات مع اختلاف معرّفات التحصيل، ثم فحص جرد فترة متطابقة غير فارغة وإعادة الطلب، وجردًا وإقفالًا فارغين وإعادة الطلب. لم يُسوِّ الجرد التخصيص المعلّق. نجحت أيضًا اختبارات runtime prototype وperiod prototype وclosure وTypeScript وdiff-check. المُعترِض محدّد بصيغ SQL ومعرّف حساب يمرره الاختبار، ولا يغطي المصدر والتصحيحات كلها أو التزامن في PostgreSQL؛ تساوي المعرفات لا يثبت صحة التاريخ. **لم يُصلَح المحرك الإنتاجي بهذه التجربة**، ولم تُطبّق ترقية أو يُشغّل تدقيق على بيانات فعلية.

مسودة بوابات الانتقال والتوقف والاستعادة، مع التمييز بين ما قبل الكتابة وبعدها، موثقة في `docs/finance-cutover-rollback-draft-ar.md`؛ ليست إذن تنفيذ ولا تعتبر النسخ وحده تراجعًا بعد معاملات جديدة.

### استكمال اصطناعي: صرف نقد الموظف مقابل الجرد

اختبر `check:finance:postgres-concurrency` على PostgreSQL مؤقت ترتيبَي إنشاء جرد مباشر مقابل صرف `HOLDER_CASH` فعلي، وترتيبَي إقرار الموظف لجرد موجّه مقابل الصرف، باستخدام مُعترِضي التخصيص والمقارنة الاختباريين داخل معاملات الخدمات. عندما سبق الجرد/الإقرار، سُمح بالصرف رغم بقاء الجرد مفتوحًا ثم رُفض تأكيد الجرد القديم بسبب تغيّر revision. عندما سبق الصرف، رُفض الجرد المباشر بتوقع قديم، أما إقرار الجرد الموجّه فالتقط المتوقع الجديد. اختُبر الجرد المطابق وإعادة الطلب وعدم إنشاء حركة فرق وعدم استهلاك التخصيص المعلّق. أعيد تنظيم تنظيف اتصال الاختبار لتحرير معاملة الإدارة قبل انتظار فصل Prisma عند الفشل.

كما أضاف اختبار PGlite حالة دفع مصطنعة بطابع مساوٍ لافتتاح العهدة؛ استبعدتها المعادلة القديمة، فقبل المحرك غير المعدّل جردًا وإقفالًا مع بقاء الدفع مخصصًا ومعلقًا في النموذج؛ رفض الاعتراض الاختباري الحالتين. نجحت اختبارات PostgreSQL ‏1/1 و`check:finance:count-close-period-prototype` ‏1/1 وTypeScript وdiff-check. فرض الطابع اصطناعي وليس إثباتًا لما حدث تاريخيًا؛ وPostgreSQL يستخدم Prisma WASM لا المحرك الأصلي. المقارنة والمعترضان ليسا ربطًا إنتاجيًا ولا يثبتان جميع التداخلات. عدم منع `HOLDER_CASH` أثناء الجرد سلوك قائم، لا تدعي هذه الاختبارات إيقافه؛ ولم تُستخدم بيانات فعلية أو يُنفذ نشر.

أُعيدت حالة تساوي وقت الافتتاح المصطنعة لكل من التحصيل والدفع على PostgreSQL المؤقت أيضًا: رفض مُعترِض الاختبار الجرد والإقفال وأثبت تراجع الإصدار والجرود والإيصالات والتدقيق والحركات، بينما أقفل المحرك غير المعدّل الحساب مع بقاء تخصيص اختباري معلّق. هذه إعادة إنتاج لحد مصنّع وليست حلًا إنتاجيًا أو استنتاجًا عن الماضي. نجح اختبار PostgreSQL بعد التوسيع ‏1/1 وTypeScript.

## جرد تجريبي لاتساق إيصالات التخصيص

أُضيف `prototypes/finance-cutover-period-audit/receipt-audit.test-only.ts` لتدقيق إيصالات **النموذج الاصطناعي** في لقطة ثابتة للقراءة فقط وبموافقة تشغيل اختبارية صريحة. يقارن معرفات التحصيلات والمدفوعات المرتبطة بالإيصال والتسوية، والبصمة والمبالغ الحالية، ويعرض اختلاف الحساب أو الفرع أو حالة التسوية وبعض تناقضات المصدر، وقوائم معرفات تالفة. يعرض التسوية المؤكدة بلا إيصال باعتبارها نقص دليل لا خطأ محسومًا، ويُظهر التخصيص المرتبط بلا إيصال حتى عند اختلاف حساب التسوية. حالات التقاطع تظهر من جهتي الحساب عند الإمكان.

نجح `check:finance:cutover-receipt-audit` ‏1/1 على PGlite اصطناعي: إيصال مطابق وفارغ، أدلة ناقصة، فرع وحساب ومصدر خاطئ، JSON تالف، إجماليات متساوية بمعرفات مختلفة، وتغير مبالغ متعاكس بإجمالي ومعرفات ثابتة؛ تحقق من رفض ظروف قراءة غير آمنة وعدم تعديل الصفوف. ونجح PostgreSQL المؤقت ‏1/1: تدقيق إيصال نتج عن اعتماد خدمة فعلي في القاعدة الاصطناعية، ثم كشف تغيير مبلغ فُرض اصطناعيًا وأُعيد بعد الاختبار. نجحت اختبارات period وruntime وTypeScript وdiff-check.

**حدود:** البصمة غير موقّعة ويمكن تغييرها مع المصدر، والتطابق لا يثبت حيازة أو تاريخًا أو صحة الحركات، والفحص ليس شاملًا لكل البيانات أو الأداء أو الصلاحيات ولا يحدد أهلية الترقية. لا يُستورد في التطبيق، ولا يُشغّل على بيانات فعلية ولا يُستخدم للتصحيح دون خطة وموافقة منفصلتين. PostgreSQL يستخدم Prisma WASM؛ لم تنفذ ترقية أو عملية نشر.


### فحص العهد مع تعطيل المالية

- وفق قرار المستخدم، تفحص معاملات نقل المستخدم أو إيقافه وإيقاف الفرع العهد المفتوحة إذا كان مخطط المالية موجودًا، حتى عند تعطيل `FINANCE_ENABLED`. يرفض التغيير عند عهدة مفتوحة أو مخطط جزئي أو تعذر التحقق؛ يُتجاوز الفحص فقط إذا كان المفتاح معطّلًا والمخطط غائبًا تمامًا. لا تشمل الحراسة التعديل المباشر للقاعدة.
- تعرض الإدارة تنبيهًا لحالة عدم اليقين، وتخفي ملخص الجاهزية المالية غير الموثوق وتضع «غير معروف» في التصدير عند فشل القراءة. لا تعرض رابط الحسابات عند تعطيل المالية.
- نجحت اختبارات `check:admin:status-custody` و`check:admin:finance-disabled:http` على بيانات اصطناعية، وكذلك سباقات مختارة في `check:finance:postgres-concurrency` على PostgreSQL مؤقت. اختبار HTTP يستخدم Node fetch وليس تفاعل متصفح؛ الاختبارات لا تثبت جميع السباقات أو سلامة بيانات إنتاجية.

### تداخل التحصيل وإعادة الطلب

- في PostgreSQL مؤقت اصطناعي، اختُبر تحصيل يسبق طلب جرد موجّه متزامنًا؛ التقط إقرار الحامل المبلغ بعد التحصيل. واختُبرت دعوتان متزامنتان للتحصيل نفسه: البيانات المطابقة تعيد النتيجة، والمبلغ المختلف يُرفض، مع تحصيل واحد وزيادة واحدة لمراجعة العهدة.
- كشف الاختبار تعارض SQLSTATE `40001` مغلفًا في خطأ Prisma `P2010` عند قفل الفاتورة. أصبحت إعادة المحاولة المحدودة في خدمات التجارة والكتالوج تتعرف على رموز التعارض الصريحة في metadata، مع اختبار استبعاد الأخطاء الأخرى. هذا لا يعالج جميع مسارات النظام ولا يثبت المحرك الأصلي لـPrisma؛ الاختبار يستخدم WASM وadapter على PostgreSQL مؤقت. نُقل تحديث مراجعة الفاتورة بعد التحقق من إعادة الطلب مع إبقاء القفل أولًا؛ تُزاد المراجعة عند عملية جديدة فقط. اختُبر replay للتحصيل والرد والمرتجع على PGlite، والطلبات المتزامنة للتحصيل وتجاوز المستحق على PostgreSQL مؤقت. لا يثبت ذلك جميع سباقات الرد والمرتجع على PostgreSQL.

- حُدّثت تجهيزات `check:commerce:integration` الاصطناعية لمخطط صلاحية الإلغاء وسقف الخصم والإقفال والجرد، حتى تعمل مع متطلبات الكود الحالية؛ نجحت 16 حالة فرعية. تطبيق SQL هذا في قاعدة اختبار مؤقتة فقط وليس ترقية فعلية.

### سباقات إضافية على الفاتورة

- على PostgreSQL مؤقت وبخدمات التطبيق الفعلية، أضيفت حالات مرتجعين وطلبي رد بالبطاقة بالمعرّف نفسه، ومرتجعين مختلفين للكمية الكاملة، وردّين يتجاوز مجموعهما المستحق. واختُبر التحصيل بالبطاقة مع المرتجع الكامل بكلا ترتيبَي القفل. تحققت الاختبارات من عدد السجلات ومراجعة الفاتورة ورسائل رفض الحالات المتنافسة.
- الفواتير الاصطناعية لبنود خدمة غير مخزنية؛ لا تغطي هذه التجربة سباقات السيريالات أو إعادة المخزون أو كل الأدوار، ولا تثبت الربط المحاسبي النهائي أو صحة التاريخ. تستخدم Prisma WASM وadapter، لا محرك Prisma الأصلي للإنتاج.

### الرد النقدي والجرد تحت التزامن

- على PostgreSQL مؤقت، تنافس ردّان نقديان لفاتورتين على عهدة واحدة: بعد خصم الأول رُفض الثاني عند احتمال رصيد سالب دون إقرار، ورُجعت الفاتورة والرد الفاشل. طلب الرد المكرر أنشأ حركة وحيدة مرتبطة به.
- اختُبر الرد النقدي مع الجرد المباشر في ترتيبَي القفل: الرد بعد فتح الجرد مسموح حاليًا لكنه يجعل اعتماد الجرد القديم مرفوضًا بتغير المراجعة؛ والرد أولًا يؤدي إلى رفض الجرد ذي الرصيد المتوقع القديم.
- الاختبارات اصطناعية ومحدودة وتستخدم Prisma WASM وadapter؛ لا تثبت جميع التداخلات أو التاريخ أو المحرك الإنتاجي. رصيد الرد المتوقع يحسبه الخادم داخل المعاملة؛ هذه الحالات لا تثبت أن المشغّل راجعه. الإقرار بالسالب يسمح بنتيجة سالبة؛ اختُبر سيناريو إقفال محدد أدناه.

### مرتجع السيريال وإعادة البيع

- أضيف اختبار PostgreSQL اصطناعي لبيع مخزني ثم مرتجعه مع فصل المخزون معطّلًا: أثناء تعليق المرتجع قبل إتمامه رُفض بيع السيريال نفسه ورُجعت الفاتورة وخصم المخزون، وبعد اكتمال المرتجع نجحت إعادة محاولة البيع بنفس المعرّف. تكرار مرتجع البيع الثاني متزامنًا أعاد نتيجة واحدة دون استعادة الرصيد أو رابط السيريال مرتين؛ تحقق الاختبار أيضًا من متوسط التكلفة ومراجعة الفاتورة.
- هذا ترتيب محدد على قاعدة مؤقتة عبر Prisma WASM، لا ضمان لجميع تداخلات المخزون والسيريالات أو الإلغاء أو وضع فصل المخزون، ولا يثبت صحة التاريخ الفعلي.

### الرد النقدي مع الإقفال وحد الجرد

- في تجربتَي PostgreSQL مع إقرار صريح بالرصد السالب، إقفال العهدة أولًا منع الرد ورجّع الفاتورة؛ والرد أولًا سجّل حركة واحدة ورصيدًا سالبًا ومنع الإقفال. الاختبار اصطناعي عبر Prisma WASM ولا يعمم على جميع التداخلات.
- **فجوة غير محلولة:** خدمة رد المبيعات الفعلية تستدعي خطاف الحركة دون مرجع آخر جرد أو إقرار بأن الدفع بعده. أظهرت تجربة اصطناعية بعد جرد مؤكد حركة رد بلا مرجع الجرد. لا يثبت غياب المرجع وقت الدفع الحقيقي أو أن التاريخ خاطئ، لكنه يمنع اعتبار ترتيب الرد والجرد متحققًا. يلزم تصميم المسار والإقرار ومراجعة التاريخ قبل الربط النهائي؛ لم تُنفّذ معالجة للبيانات.

### تجربة حراسة مرجع الرد النقدي

- تأكدت الفجوة على المسار الفعلي: النموذج والإجراء لا يرسلان مرجع الجرد، والخطاف يجعله اختياريًا. أُنشئ نموذج اختباري منفصل `prototypes/finance-refund-checkpoint/` يربط إقرارًا اصطناعيًا بالحساب والفرع والفاتورة والحركة ويستدعي حارس آخر جرد داخل معاملة خدمة الرد؛ ليس مربوطًا بالتطبيق.
- نجح `check:finance:refund-checkpoint-prototype` لحالات غياب الإقرار، وتقادم مرجع الافتتاح بعد اعتماد جرد، والرجوع الكامل عند الفشل، وتطابق حساب المراجعة، وحفظ المرجع، وreplay حتى بعد جرد تالٍ. ونجحت تجربتا PostgreSQL المختارتان لاعتماد الجرد والرد في ترتيبَي القفل؛ المعترض يسجل المرجع تجريبيًا ولا ينشئ حدث التدقيق الخاص بالخطاف، ويعتمد أشكال SQL محددة.
- لا يثبت إقرار المُشغّل توقيت الدفع الفعلي ولا يصحح التاريخ. يلزم قرار وتصميم مسار الرد السابق للجرد أو الملتبس، والتدقيق والمراجعة والصلاحيات والواجهة والتزامن والانتقال والتراجع قبل أي دمج إنتاجي. لم تُطبّق هجرة أو تُستخدم بيانات حقيقية.

### جرد أدلة الردود الاصطناعي

- أضيف نموذج قراءة فقط `prototypes/finance-refund-audit/` لتصنيف وجود حركة أو إقرار تاريخي للرد ومقارنة الفرع والحساب والمبلغ والجرد، ورصد المرجع غير المثبت والحدود الزمنية والمراجع اليتيمة أو غير الصالحة. يقارن الطوابع المسجّلة ولا يستنتج متى دُفع النقد فعليًا.
- نجح `check:finance:refund-audit` على PGlite في معاملة قراءة فقط، واختُبرت عينة رد من الخدمة الفعلية في لقطة PostgreSQL اصطناعية للقراءة فقط دون تغييرات. غياب الدليل ليس دليلًا على عدم الدفع أو عدم شمول الجرد، وتطابق السجلات أو خلو النتائج من الملاحظات ليس مصادقة على التاريخ أو إذنًا بالترقية. النموذج غير جاهز أو مصرح لتشغيله على بيانات حقيقية.

### قرار الرد السابق للجرد أو الملتبس

- اختار المستخدم إيقاف الرد السابق لآخر جرد أو غير مؤكد التوقيت للمراجعة اليدوية، دون تسجيل رد أو حركة في المسار العادي. أُضيف فحص للقرار في النموذج الاصطناعي واختُبرت الإجابات الصريحة والقيم المفقودة أو غير المعروفة والرجوع دون أثر. توجد الآن حراسة لهذا القرار في خدمة المبيعات عند تفعيل المالية؛ لا تزال المراجعة والاختبارات النهائية غير مكتملة.
- متطلبات الدمج والفجوات، ومنها بصمة الطلبات الجديدة وreplay القديم وأثر عدم كشف الأرصدة وتدقيق المرجع، في `docs/finance-refund-checkpoint-design-ar.md`. الإقرار ليس إثباتًا لتوقيت الدفع، ولا يجيز تصحيح التاريخ أو تشغيل هجرة.

- أُضيف نموذج مستقل لبصمة طلب الرد المراجع وإعادة الطلب القديم `prototypes/finance-refund-request-identity/`، مع اختبارات تغيير المستخدم والحساب والمبلغ والمرجع والإقرار والمدخلات التالفة. النموذج في الذاكرة ولم يُربط بالخدمة أو يُثبت إعادة الإرسال والتزامن على قاعدة حقيقية.

- جُرّبت بصمة الرد أيضًا بمعترضَين اصطناعيين حول خدمة الرد الحقيقية على PGlite، وفي تداخل مختار على PostgreSQL بنفس معرّف الطلب. لم تُدمج في التطبيق؛ معالجة تعارض التفرد خارج المعاملة، وتدقيق الخطاف، وإعادة المحاولة على محرك الإنتاج ما زالت متبقية.

- في الحالة الحالية اختُبر مسار الرد الفعلي على قاعدة PGlite اصطناعية بما يشمل مرجع الجرد، وسجل تدقيق الحركة، وبصمة الطلب، وإعادة الطلب القديم، وحقن P2002 دون الادعاء بأنه سباق فعلي. نجحت تداخلات محددة على PostgreSQL اصطناعي ومجموعة التجارة. نجحت مجموعة HTTP بعد تقسيمها إلى قسمين متتابعين لكل منهما قاعدة وخادم اصطناعيان مستقلان؛ شملت منع POST لتوقيت سابق أو مجهول أو مفقود، وحجب الرصيد، وإظهار تاريخ الافتتاح، والنجاح وإعادة الطلب. الاختبار لا يحاكي متصفحًا.

- نجح اختبار متصفح فعلي `check:finance:refund-browser` على Chromium وNext وPGlite اصطناعي: التحقق من حجب الرصيد وظهور تاريخ الافتتاح والجرد المؤكد ووقت اعتماده بتوقيت القاهرة، ومنع اختيارات التوقيت السابق أو المجهول، ومسح الإقرار عند تغيير الحساب، ثم المراجعة والتسجيل. يغطّي محاسبًا واحدًا وليس كل الأدوار والمتصفحات، ولا يثبت توقيت دفع مادي. تعليمات الإعداد المؤقت وحدوده في `prototypes/finance-browser-tests/README.md`.

- أُغلقت فجوة الرد النقدي عند تعطيل المالية: لا يقبل مسار الخدمة ردًا نقديًا جديدًا دون إمكانية مراجعة الحساب ونقطة الجرد، بما في ذلك POST مباشر؛ يظل غير النقدي متاحًا وفق الصلاحية. إعادة الطلب القديم المحفوظ بلا حساب، وإعادة طلب مراجع حُفظ قبل تعطيل المالية، تعيدان النتيجة بلا حركة جديدة. الأثر التشغيلي: يتوقف الرد النقدي الجديد عند تعطيل المالية حتى المراجعة. نجحت اختبارات الخدمة وHTTP وPostgreSQL الاصطناعي والمتصفح؛ حقن P2002 ليس برهانًا على تعارض commit فعلي.

### منع غموض حد الفترة مؤقتًا

- اختار المستخدم إيقاف العمليات للمراجعة عند تساوي طابع تحصيل نقدي أو صرف `HOLDER_CASH` مع افتتاح العهدة أو آخر تسوية مؤكدة. أضيف فحص في محرك المالية قبل إنشاء الجرد المباشر أو الموجّه، وتسجيل الموظف، وتأكيد الجرد، وطلب التسوية وتأكيدها، وإقفال العهدة. إعادة أمر محفوظ لا تكرر الكتابة، وإلغاء الطلبات المعلقة يظل متاحًا.
- الفحص محافظ على مستوى الفرع: أي تحصيل نقدي أو صرف من نقد الموظف في الفرع عند الطابع المحدد يوقف العهدة، حتى لو بدا أنه لموظف آخر، لأن التاريخ قد يتضمن تسجيلًا بالنيابة لا يمكن حسمه من الطابع. قد يوقف ذلك حالة سليمة مؤقتًا. لا يشمل كل غموض آخر ولا يثبت أن الحد التاريخي صحيح أو أن الفترة خالية من أحداث أقدم أو غير مسندة. لا تُنقل الأحداث بين الفترات ولا تُعدّل الطوابع.
- تعرض صفحات العهدة والتسوية والجرد تحذيرًا، وتحجب إنشاء الطلبات المتأثرة في الواجهة؛ الرفض الخادمي يبقى المرجع. المؤشرات تستخدم المعادلة القديمة ولا تُعد إثباتًا للقيم عند غموض الفترة؛ تحديث التنبيه ونطاق المؤشرات الرئيسية موضح أدناه. لا يوجد مسار معتمد بعد لحل الحالة التاريخية أو تجاوزها؛ يلزم مراجعة مستقلة وتصميم معالجة قبل استئناف العملية، لا تغيير الطابع عشوائيًا.
- نجحت اختبارات PGlite على التحصيل والصرف المتساويين، وحد افتتاح وآخر تسوية اصطناعية، ورفض التأكيد والتسجيل والإقفال والتسوية مع السماح بالإلغاء، والتراجع والـreplay. اختُبرت حالة فرع آخر لا يمنع وحالة نفس الفرع لمُنشئ مختلف تمنع. ونجحت مجموعة PostgreSQL الاصطناعي المحدودة وHTTP للعرض وPOST المباشر وTypeScript؛ PostgreSQL يستخدم Prisma WASM وليس محرك الإنتاج، ولم تُجرَ هجرة أو مراجعة بيانات فعلية.

### مؤشرات العهد بعد اكتشاف غموض الفترة

- أصلح حساب ملخص العهد للوحة المالية: كانت كل عهدة تجمع تحصيلات الفرع ومصروفات نقد الموظف كلها، ما يكرر الإجمالي عند وجود عدة عهد. أصبحت تستخدم نطاق حامل العهدة نفسه الذي تستخدمه معادلة التسوية الحالية (منشئ الفاتورة وطالب المصروف). وتستخدم لوحة الموظف الآن ملخص المحرك في لقطة القراءة نفسها بدل جمع الفرع كاملًا. هذا توحيد للمعادلة القديمة وليس إثباتًا أن المنشئ أو الطالب هو الحائز التاريخي للنقد.
- تحمل الملخصات مؤشر غموض الحد، وتعرض لوحة القيادة وصفحة المالية تنبيهًا بأن الأرقام غير مؤكدة ولا تُعتمد للتسليم عند وجود حالة في النطاق المعروض. تنبيه لوحة القيادة محجوب خادميًا عندما لا يُسمح بصفحة العهدة للموظف أو صفحة المالية للإدارة. الأرقام وبعض الرسوم تظل مرئية مع التحذير؛ لا يعني ذلك اعتمادها. ولم تُراجع جميع التقارير الأخرى أو جميع حالات الصلاحيات في هذا الاختبار.
- قورنت نتيجة تجميع لوحة المالية مع `settlementOverview` لعهد متعددة على PGlite، وفي حالتي حد اصطناعيتين على PostgreSQL؛ ونجح اختبار HTTP للتحذير وإخفائه عند منع صفحة عهدة الموظف. اختبار PostgreSQL يستخدم Prisma WASM، ولا تُستنتج منه صحة التاريخ أو مواضع النقد الفعلية.

- استكمال أمان عرض اللوحة: كان إخفاء تنبيه الحد عند حجب صفحة المالية يترك بعض التقديرات ظاهرة بلا تحفّظ. الآن تظهر لهؤلاء رسالة عامة ثابتة بأن مؤشرات العهد تقديرية ويجب مراجعة المسؤول قبل التسليم، سواء وُجد غموض أم لا؛ فلا تكشف الرسالة وحدها وجود حادثة حد. يبقى التنبيه المحدد للمصرح له. اختُبر HTTP للموظف مع غموض ودونه، وللمحاسب عند حجب المالية وتجاوز أدمن النظام. هذا لا يحجب كل الأرقام المالية في لوحة القيادة ولا يثبت انعدام قنوات الاستدلال الأخرى؛ يلزم جرد مستقل لصلاحيات المؤشرات قبل اعتبارها محمية.

### إظهار تقادم طلب التسوية

- اكتُشف أن تحذيرات الموظف والمحاسب ومؤشرات اللوحة كانت تعتمد على توقيت الحركة فقط، بينما محرك الاعتماد يرفض أيضًا عند اختلاف مراجعة الحساب أو غياب مراجعة طلب قديم. لذلك قد يبدو طلب غير قابل للاعتماد سليمًا، خصوصًا عند تساوي التوقيت.
- وُحّد استعلام مؤشر التقادم لهذه المواضع ليشمل اختلاف المراجعة أو غيابها إلى جانب فحوص الحركة السابقة، مع تعديل النص حتى لا يزعم أن السبب بالضرورة حركة جديدة. المؤشر للعرض فقط: المحرك تحت قفل الحساب هو المرجع، وقد توجد أسباب أخرى للرفض منها غموض بداية الفترة.
- في PGlite اصطناعي اختُبر طلب سليم، وتغير المراجعة بلا حدث ذي وقت لاحق ورفض المحرك، وطلب قديم بلا مراجعة. واختُبرت رسالتا الموظف والمحاسب عبر HTTP لطلب قديم. لا يُغيّر ذلك التاريخ ولا يضيف مراجعة للطلبات القديمة أو يجيز اعتمادها.

- استُكمل فحص تقادم التسوية على PostgreSQL مؤقت: طابقت مراجعة سليمة، وكشفت مراجعة متغيرة أو مفقودة داخل معاملة أُلغيت؛ نجحت مجموعة التزامن الاصطناعية. هذا لا يختبر محرك Prisma الأصلي للإنتاج.
- صفحة قرارات المحاسب تعرض الآن تحذير غموض بداية الفترة لكل طلب متأثر وتحجب نموذج اعتماده مع بقاء الرفض بسبب. فحص الصفحة لقطة عرض فقط؛ يظل رفض المحرك تحت القفل أساس الحماية من التغير بعد العرض. اختبر HTTP التحذير وحجب نموذج الاعتماد والإبقاء على الرفض؛ لا يحسم هذا الغموض أو يؤكد صحة أي مبلغ تاريخي.

### تصحيح عرض السيولة ومصروفات الشهر
- أزيل من لوحة المالية ولوحة القيادة مؤشر «صافي السيولة بعد المصروفات» الذي كان يطرح إجمالي المصروفات المسجّلة للشهر من أرصدة الخزائن والعهد المتوقعة. الإجمالي يضم حالات متعددة، وبعض المصروفات المدفوعة أثرت بالفعل في الأرصدة أو المتوقع؛ الطرح مرة أخرى لا يمثل صافي نقد موثوقًا.
- تُعرض مصروفات الشهر المسجّلة منفصلة عن إجمالي السيولة مع توضيح أنها بحالات مختلفة، وليست مبلغًا يُخصم مجددًا. إجمالي السيولة نفسه تقديري ويخضع لقيود إسناد العهد وغموض الفترات المذكورة أعلاه؛ لا يمثل تقريرًا محاسبيًا معتمدًا. اختُبر HTTP وجود التوضيح وغياب المؤشر المضلّل في اللوحتين، ولم تُجرَ أي حركة أو ترقية أو معالجة تاريخية.

### إيقاف مؤشر تدفق غير موثوق
- أوقف عرض «التحوّل النقدي الصافي» في لوحة القيادة بدل وصف الفرق بأنه نقد محتفظ به؛ كان يجمع التحصيل بتاريخ التسجيل ويقارن بمصروفات مختارة بتاريخ المصروف، وبنطاقين مختلفين للموظف، ويستخدم صفرًا عند غياب تدفق المدفوعات. التنبيه ثابت عند تفعيل المالية ولا يحدد وجود حالة خاصة. الحساب القديم ما زال داخليًا لكنه لا يُمرر للعرض؛ يلزم تصميمه واختباره قبل إعادته. سجلت شروط البديل في `docs/finance-dashboard-cash-flow-review-ar.md`.
- نجح اختبار HTTP الاصطناعي بعد رفع حد ذاكرة Node إلى 2560 MB، ويفحص عدم تسلسل نصوص المؤشر وظهور التنبيه. فشل تشغيل سابق عند إعادة تشغيل Next بسبب حد الذاكرة، وليس فشل تأكيد المؤشر. نجح typecheck وdiff-check. هذا ليس إثباتًا لصحة بقية التقارير أو التاريخ.

- أُضيف مفتاح `/dashboard#recorded-flow` القابل للإدارة لبطاقة الحركات المسجّلة، مع اشتراط صلاحيات مصادرها قبل استعلامها وإرسالها. تنطبق قاعدة السماح الافتراضية على المفتاح عند سلامة مخزن الصلاحيات. تفاصيل النطاق والاختبارات والتحفظات في `docs/finance-dashboard-cash-flow-review-ar.md` تحت «التنفيذ المحدود في التطبيق»؛ البطاقة ليست رصيدًا نقديًا أو ربطًا محاسبيًا نهائيًا.

### إصلاح اختبار إدارة العهد والمالية المعطّلة

قُسم اختبار HTTP إلى حالتين مستقلة القاعدة والخادم: عهدة مفتوحة ومخطط جزئي. لم يعد يعيد فتح دليل PGlite بعد إيقاف خادم Next، وهو ما أدى إلى تعطل الاختبار سابقًا. نجح ‏2/2؛ يتحقق من رفض النقل والإيقاف وإيقاف الفرع، وإبقاء تعديل الملف الآمن، وحالة المستخدم والفرع والجلسة من استجابة الإدارة، ومن منع المخطط الجزئي. نجح اختبار خدمة الإدارة ‏1/1 مع فحص قاعدة البيانات للمستودع والفرع والجلسات. لم يعد HTTP نفسه يفحص قاعدة الخادم مباشرة بعد إيقافه؛ اختبار الخدمة يكمل هذه التغطية ولا يثبت أن كل المسارات أو التداخلات قد اختُبرت.

### قائمة مراجعات المصروفات
- `/finance/expenses/reviews` يرث حراسة `/finance/expenses` ويضيف فحص `/finance/expenses#review` مع أقفال الكتابة، ولا يقرأ القائمة عند المنع. خدمة القراءة تعيد التحقق من دور المدير أو المحاسب. اختُبرت استثناءات الدور والحساب وقفل المالية وتجاوز الأدمن والموظف وترقيم النتائج اصطناعيًا؛ لا تمثل هذه اختبارات لكل سيناريوهات الصلاحيات أو آلية لإغلاق الحالات.

### توحيد مصطلحات المؤشر والفرق في شاشات المالية

- استُكمل تصحيح الرسائل بعد تغيير دليل المالية وصفحتي طلبات التسوية: توحّدت تسمية «مؤشر الفترة التقديري» في صفحات الموظف وقرارات المحاسب ونموذج الطلب، و«الفرق عن المؤشر» في جداول الطلبات والأرشيف وتصدير CSV والتقارير، بدل «الإجمالي المتوقع» و«العجز أو الزيادة» و«الانحراف». المقصود أن الرقم مؤشر محاسبة بالمعادلة القديمة، لا رصيد مؤكد ولا إسناد للنقد.
- وُضّح في شاشات الجرد أن التسجيل ملاحظة بلا أثر، وأن التأكيد المنفصل يسجّل تعديلًا دفتريًا بالفرق المُقرّ به إن كان غير صفر؛ سُمّي زر التأكيد «تأكيد الجرد — تعديل دفتري» بدل «تأكيد التسوية»، وصيغ «الفرق عن المرجع المسجّل» بدل «الفرق» لأن مرجع الخزنة رصيدها الدفتري ومرجع العهدة مؤشر الفترة.
- أُضيفت عبارات صريحة بأن الإقرار وسجل الحركة لا يثبتان انتقال النقد أو توقيته المادي في نماذج طلب التسوية والجرد الموجّه واعتماد التسوية والتحويل اليدوي ودليل المالية.
- هذا توضيح عرض فقط: لم تتغيّر الصلاحيات أو الحراسات أو المعادلات أو المبالغ أو مسارات replay، ولم تُنفّذ ترقية أو معالجة لبيانات فعلية. اختُبرت النصوص عبر HTTP على قاعدة PGlite اصطناعية مع Next، إلى جانب فحص TypeScript و`git diff --check`؛ اختبار HTTP يستدعي Node fetch لا متصفحًا، ولا يثبت سلامة كل التقارير أو التاريخ.

### تحقق replay من نتيجة قرارات الاعتماد والرفض وتأكيد الجرد

- كانت إعادة أمر محفوظ لـ`SETTLEMENT_CONFIRM` و`SETTLEMENT_REJECT` و`CASH_COUNT_CONFIRM` تعيد `result_id` بعد مطابقة بصمة الأمر فقط، دون التأكد من أنه يشير إلى الصف الذي اتُّخذ القرار بشأنه. أُضيف فحص مشترك في `command` يتطلب تطابق معرف النتيجة مع معرف الطلب/الجرد المُدخل ووجود صفه، قبل إرجاع نتيجة replay، في المسار العادي ومسار استعادة تعارض التفرد `23505`.
- الفحص قراءة عادية بلا قفل جديد ولا إعادة فحص الحالة أو الرصيد أو الفترة أو الخزنة أو الصلاحيات الإضافية؛ القرارات القديمة والمقفلة والمنقولة تبقى قابلة للإعادة بلا كتابة ثانية، والصلاحية الحالية يفحصها `command` كما كانت. لا يثبت الفحص صحة القرار أو وقوع حركة نقدية، ولا يعالج ذرية قواعد الصلاحيات أو الربط المحاسبي والتاريخ.
- على قاعدة PGlite اصطناعية اختُبر تعمّد تغيير `result_id` للأوامر الثلاثة: رُفض replay دون تغيير عدد الطلبات أو التدقيق أو الحركات أو الحالات أو النسخ، ثم عادت الإعادة بعد استعادة المعرف؛ وشمل ذلك حقن `23505` للوصول إلى مسار الاستعادة. نجحت `check:settlement:engine` ‏20/20 و`check:finance:engine` ‏34/34 و`check:finance:app-engine` ‏3/3 و`check:finance:closure` ‏2/2 و`check:finance:count-close-period-prototype` ‏1/1 و`check:finance:period-notice:http` ‏1/1، مع TypeScript و`git diff --check`. هذه اختبارات بيانات مصطنعة ولا تُعمّم على كل التداخلات أو محرك الإنتاج.

### جرد تغطية فحص نتيجة replay

### تجربة توجيه التحصيل بعد حاجز الفرع

- أُضيف نموذج مخبري غير مربوط بالتطبيق `prototypes/finance-collection-policy/routed-collection.test-only.ts`: بعد حاجز الفرع المشترك تُقرأ الحسابات وتُختار الوجهة، لا قبلها؛ وreplay يقرأ الوجهة المحفوظة ولا يعيد التوجيه أو يلمس الحاجز. إقرار استلام الخزنة يجب أن يكون صريحًا من المُشغّل ولا يُصنَع من الوجهة، ويُزال عند اختيار العهدة.
- على PostgreSQL مؤقت معزول اختُبر الترتيبان: بدء الافتتاح ثم التحصيل، وبدء التحصيل ثم الافتتاح. في الترتيب الأول أعادت المعاملة المتأخرة المحاولة بلقطة جديدة فاختارت العهدة المفتوحة بلا حركة خزنة؛ وفي الثاني بقيت وجهة الخزنة المحفوظة رغم اكتمال العهدة لاحقًا. تحقق الاختبار من retry بتعارض تسلسلي/طريق مسدود، وتحصيل واحد وتخصيص واحد، وعدد الحركات، وثبات مراجعة الحاجز عند replay، ورفض replay خزنة بلا إقرار وقبول replay عهدة مع إقرار زائد. التفاصيل والحدود في `docs/finance-routed-collection-experiment-ar.md`.
- التحقق: TypeScript و`git diff --check` ناجحان، `check:finance:routed-collection-postgres` ‏1/1 ثلاث مرات، `check:finance:postgres-concurrency` ‏1/1، `check:finance:collection-policy` ‏3/3، `check:finance:collection-prototype` ‏1/1. هذه قاعدة اصطناعية عبر Prisma WASM وليست محرك الإنتاج.
- النموذج يشاركه كتّاب محددون فقط، ويقرأ replay قبل الصلاحية، ويعيد اختيار الحساب داخل أمر التخصيص؛ لا يثبت كل الأقفال أو المسارات أو التاريخ أو نقل النقد، ولا يُسند بيانات تاريخية ولا يُصحّح مجاميع، ولم يُدمج في التطبيق أو تُطبّق هجرة. حراسة التحصيل للعهدة وبديل الخزنة وإسناد الفترة وعضوية التسوية والانتقال ما زالت غير محسومة.
