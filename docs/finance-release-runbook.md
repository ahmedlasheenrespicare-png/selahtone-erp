# خطة تشغيل ترقية المالية (قاعدة البيانات أولًا)

هذا المستند هو **خطة التنفيذ** لا قرار تنفيذ. لا يُشغَّل أي شيء على قاعدة الإنتاج إلا
بموافقتك المنفصلة في خطوته، وبعد أن تكون قد قرأت الملف ونفّذت ما قبله.

الملفات المعنية، كلها للقراءة والتشغيل اليدوي في **Neon SQL Editor**:

| الملف | ما يفعله | متى |
|---|---|---|
| `prisma/manual-finance-release-preflight.sql` | فحص قراءة فقط قبل الترقية: أعداد وبصمات القديم، وأسماء محجوزة | قبل أي تغيير |
| `prisma/manual-finance-release-upgrade.sql` | ينشئ مخطط `finance` + سجل `finance_release.migrations` | بعد نسخة + موافقة منفصلة |
| `prisma/manual-finance-release-postflight.sql` | فحص قراءة فقط بعد الترقية ويقارن بالبصمات السابقة | فورًا بعد الترقية |
| `prisma/manual-finance-release-rollback.sql` | يحذف المخططين إن لم تُدخل أي بيانات مالية | حالة إيقاف فقط |

كل ملف يبدأ بمعاملة وينتهي بـ`COMMIT` (أو `ROLLBACK` في الفحوص)، ويُشغَّل **كاملًا
دفعة واحدة** بعد التأكد من اختيار الفرع `production` وقاعدة البيانات `neondb`.

---

## ١. قبل الترقية — النسخة وتجربة الاستعادة

النسخة شرط، لا خطوة اختيارية. ما نعرفه عن النسخ الحالي:

- سير العمل `nightly-backup.yml` ينفّذ `pg_dump` بصيغة نصية، ثم يضغطها ويشفّرها عبر
  `scripts/backup-to-r2.sh` إلى ملف باسم `selahtone-<stamp>.sql.gz.enc`.
- السير workflow يحمل خطوة استعادة **نائبة (placeholder)** تطبع تعليمات فقط؛ أي أن
  الاستعادة لم تُختبر عمليًا حتى اليوم.
- **لا توجد مرفقات في النظام (قرار نهائي 2026-10-30)**، فلا تخزين كائنات ولا ملفات ضمن نطاق النسخة؛ `pg_dump` يكفي لبيانات القاعدة.

الخطوة:

```bash
# ١) نسخة يدوية قبل الترقية (مباشرة، غير مشفّرة، تبقى على جهازك)
pg_dump "$DATABASE_URL" --no-owner --no-privileges -f "selahtone-prefinance-$(date +%F).sql"

# ٢) تجربة استعادة على قاعدة مؤقتة — هذا هو الاختبار الحقيقي
bash scripts/restore-drill.sh --file "selahtone-prefinance-$(date +%F).sql" \
     --target "postgres://user:pass@localhost:5432/selahtone_drill"
```

`scripts/restore-drill.sh` يتعامل كذلك مع الأثر المشفّر الليلي
(`*.sql.gz.enc` بكلمة `BACKUP_PASSPHRASE`) ونسخ `pg_dump -Fc`:

```bash
BACKUP_PASSPHRASE=... bash scripts/restore-drill.sh --file selahtone-20261030-010000.sql.gz.enc          # فحص بلا سيرفر
BACKUP_PASSPHRASE=... bash scripts/restore-drill.sh --file selahtone-20261030-010000.sql.gz.enc --target "postgres://…/drill"
```

- الأوامر الجاهزة للنسخ والفحص خطوة بخطوة (مع ما ترسله لي بعد كل خطوة) في
  `docs/finance-release-commands.md`.
- الوضع الأول يفك التشفير والضغط ويتحقق أن الملف مقروء ويحصي `CREATE TABLE` (بلا قاعدة بيانات).
- الوضع الثاني يستعيد فعليًا في قاعدة **مؤقتة تسميها أنت**، ثم يطبع أعداد الفروع
  والمستخدمين والبنود وحالة مخطط `finance`. يرفض العمل إن كان الهدف نطاق Neon أو
  قاعدة باسم الإنتاج، إلا بتأكيد صريح `--allow-neon-target`.

**نقطة توقف:** إن لم تكتمل النسخة أو لم تُقنعك تجربة الاستعادة، لا ننتقل للخطوة ٢.

## ٢. شبكة الأمان: فرع تجريبي (بدون طرفية)

إن لم تتوفر طرفية أو Docker على جهازك، فالبديل المتاح من المتصفح وحده:

1. لوحة Neon ← **Branches** ← **New branch** من الفرع **production** باسم
   `pre-finance-20261030`، بالبيانات «حتى الآن»، **مع** إنشاء compute endpoint.
2. الفرع نسخة copy-on-write معزولة: ما نجربه عليه لا يمسّ الإنتاج.
3. نُجري **بروفة كاملة** للترقية عليه (الكتلة أ٣ في `docs/finance-release-commands.md`)
   قبل أي تنفيذ على الإنتاج.

حدود هذا البديل بصراحة: الفرع يحميك من أخطاء الترقية، **لكنه ليس نسخة خارج Neon**
ولا يحميك من فقدان المشروع أو الحساب، ونافذة استرجاع الإنتاج على خطة Free ست ساعات
فقط. النسخة بـ`pg_dump` تبقى مطلوبة لاحقًا، ويمكن تنفيذها بالتوازي (المسار ب).

## ٣. فحص ما قبل الترقية

1. Neon SQL Editor ← الفرع `production` ← القاعدة `neondb`.
2. الصق `prisma/manual-finance-release-preflight.sql` كاملًا وشغّله.
3. انسخ عمود `finance_release_preflight` واحتفظ به.

**نقطة توقف:** أي من هذه يوقف العمل:

- عدد البنود ≠ 7، أو البصمة تختلف عن آخر فحص معروف.
- وجود جدول في `public` بأحد الأسماء المحجوزة للمالية (`accounts`، `payments`، …).
- اختلاف قاعدة البيانات أو الفرع عن المتوقع.

## ٤. المراجعة قبل الموافقة

الأسئلة المفتوحة التي يجب حسمها قبل تشغيل ملف الترقية:

1. **الهوية والصلاحيات:** دور SQL Editor لا يثبت هوية دور التطبيق ولا صلاحياته. هل
   تريد أن نكتفي بصلاحيات المالك الحالية، أم تطلب مراجعة `GRANT`/RLS قبل الفتح؟
2. **الملكية:** الترقية تُنفَّذ بدورك في SQL Editor، فتكون الجداول مملوكة له. التطبيق
   يستخدم `DATABASE_URL` الخاص به؛ إن لم يكن هو المالك نفسه فنحتاج قرار صلاحيات صريحًا.
3. **المرفقات:** ملغاة نهائيًا بقرارك؛ لا جداول ولا تخزين ولا واجهة رفع في أي مرحلة.
4. **القيود المؤجلة:** غير مضمنة، والسبب مانع تقني معروف: `PrismaPg 6.19.3` يترك
   الاتصال محجوزًا عند رفض قيد مؤجل في `COMMIT`. لا نُفعّلها قبل حلّه واختباره.
5. **البيانات القديمة:** لا تُنقل ولا تُحذف. المصروفات والقيود الحالية تبقى كما هي؛
   إن ظهرت صفوف قبل التنفيذ فالفحص يكتشفها والترقية لا يمسّها (مُختبر).

**الموافقة:** أطلب منك صراحة «نفّذ الترقية» قبل الخطوة ٤. لا أستبدلها بأي افتراض.

## ٥. التنفيذ

1. تأكد من عدم وجود كتابات جارية (نافذة هدوء قصيرة يكفيها دقائق).
2. شغّل `prisma/manual-finance-release-upgrade.sql` كاملًا دفعة واحدة.
3. النتيجة المتوقعة: نجاح بلا أخطاء، وظهور سطر واحد في `finance_release.migrations`.
4. عند أي خطأ: نفّذ `ROLLBACK;` إن بقيت المعاملة مفتوحة، ثم سجّل نص الخطأ كاملًا قبل
   أي محاولة أخرى. إعادة تشغيل الملف نفسه آمنة (بلا أثر مزدوج).

## ٦. فحص ما بعد الترقية

شغّل `prisma/manual-finance-release-postflight.sql` وقارن `finance_release_postflight`
بنتيجة الخطوة ٢:

- **يجب أن تتطابق** بصمات وأعداد القديم (`expense_categories` = 7 الآن، والبنود كما هي).
- المتوقع بعد الترقية: 16 جدولًا في `finance`، وكل أعداد الصفوف صفر، وسجل واحد
  باسم `finance_release_upgrade`.
- أي اختلاف في البصمات أو الأعداد القديمة = إيقاف فوري ومراجعة، لا إكمال يدوي.

## ٧. إيقاف أو رجوع

- **رجوع نظيف قبل أي استخدام:** شغّل `prisma/manual-finance-release-rollback.sql`.
  يفحص أولًا أن كل جداول `finance` فارغة؛ فإن وُجد صف واحد يرفض ولا يحذف شيئًا.
- **بعد إدخال بيانات:** لا يوجد رجوع آلي. الخيار الوحيد الموثوق هو استعادة النسخة،
  وهذا يعيد كل شيء للوراء لا المالية وحدها — لذلك لا نفتح المالية للمستخدمين قبل
  اكتمال الخطوة ٥.

## ٨. ما بعد القاعدة: فتح الواجهة

مفتاح `FINANCE_ENABLED` غير مضبوط في الإنتاج، وبدونه تُحوَّل `/finance` إلى لوحة
القيادة ولا يُنفَّذ أي استعلام مالي. ترتيب الفتح المقترح (يحتاج موافقة منفصلة لكل
خطوة، وهو موضوع مرحلة قادمة لا هذه المرحلة):

1. ترقية القاعدة + فحص ما بعدها (هذا المستند).
2. واجهات الخزنة والعُهد والمصروفات للمدير والمحاسب.
3. صلاحيات الموظف وحجبه على مستوى الخادم.
4. (ملغى) المرفقات وتخزينها.

## سجل البروفة

نتائج البروفة الفعلية على الفرع التجريبي (`2026-10-30`) موثّقة بالأرقام في
`docs/finance-release-log.md`: تطابق الفرع مع الإنتاج، تنفيذ الترقية، وفحص ما بعدها،
وما لم يُثبت بعد.

## ما جُهّز واختُبر فعليًا

| الفحص | الأمر | النتيجة |
|---|---|---|
| مرشح المراجعة | `npm run check:finance:release-candidate` | 9/9 (PGlite وPostgreSQL 18.4) |
| ملفي الترقية والرجوع | `npm run check:finance:release-scripts` | 10/10 (PGlite وPostgreSQL 18.4) |
| النواة على المخطط المراجَع | `npm run check:finance:app-engine` | 1/1 |
| حارس التحويل | `npm run check:finance:cutover` | 25/25 |

الترقية نفسها **لم تُنفَّذ على أي قاعدة أعمال بعد**؛ كل ما سبق على قواعد يمكن التخلص منها.

مسار PostgreSQL اختياري ويحتاج تمرير `FINANCE_TEST_PG_BIN` لمجلد `bin` محلي و`LD_LIBRARY_PATH`
لمجلد `lib`؛ بدونه تُشغَّل اختبارات PGlite فقط ويُتخطى مسار PostgreSQL.
