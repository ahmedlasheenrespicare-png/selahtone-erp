# المالية داخل التطبيق — مرحلة منقولة ومعطّلة افتراضيًا

هذا المجلد هو نقل نواة المالية من معمل `prototypes/finance-engine` إلى التطبيق الحقيقي، **مرحليًا وبمفتاح تعطيل**. لا يظهر أي شيء للمستخدمين ولا يُقرأ مخطط `finance` إلا إذا كان المتغير `FINANCE_ENABLED=true`، وهو **غير مضبوط في الإنتاج**.

## ما نُقل حتى الآن

- `engine.ts`: النواة بعد تحويلها من `finance_lab` إلى المخطط المراجَع `finance`، مع استخدام الجداول الحقيقية `public.users` و`public.branches` و`public.expense_categories` (مع تحويل الأنواع `role_code::text` و`status::text`). مُنفذ البنود `tx.categoryPort` صار **إلزاميًا** للإنشاء والتعديل بدل الكتابة المباشرة.
- `types.ts` و`validation.ts` و`policy.ts` و`attachment-validation.ts` و`categories.ts`: منقولة كما هي مع توافق المسارات.
- `db.ts`: معاملة `SERIALIZABLE` واحدة من عميل Prisma الحقيقي، وتحويل أخطاء السائق، وإعادة التحقق من الجلسة مقابل صف المستخدم داخل المعاملة (`assertFinanceActor`)، ومفتاح `FINANCE_ENABLED`.
- `src/app/(app)/finance/page.tsx`: صفحة أولى تعرض الحسابات المسموحة فقط. **عند تعطيل المالية تُحوّل إلى `/dashboard` ولا تُنفَّذ أي استعلام مالي.**
- عنصر قائمة جديد يظهر فقط عند تشغيل المالية.

## ما لم يُنقل بعد

واجهة المصروفات الكاملة واعتمادها وصرفها، واجهات الجرد والتاريخي وحالات الاشتباه، المرفقات، وربط البيع والتحصيل والرد بالحركات النقدية، وتقارير الموظف. كل بند يُنقل على مرحلة مع اختباره.

## شرط التشغيل (لم يتحقق بعد)

1. ترقية SQL مراجَعة تُنفَّذ على قاعدة الإنتاج، وفحص ما قبلها وما بعدها متطابقان.
2. تصميم المرفقات وتخزينها، والصلاحيات وRLS وهوية دور التطبيق.
3. نسخة حديثة واختبار استعادة.
4. موافقة تشغيل الترقية، ثم موافقة نشر منفصلة، ثم ضبط `FINANCE_ENABLED` ومراقبة ما بعد التشغيل.

## الاختبارات

```bash
npm run check:finance:app-engine   # النواة المنقولة على المخطط المراجَع بجداول حقيقية وهمية
npm run check:finance:release-candidate
```

الأول يثبت أن النواة المنقولة تعمل على المخطط المراجَع مع `public.users` و`public.branches` و`public.expense_categories`، وأن العمليات المالية لا تلمس الصفوف القديمة ولا تُنشئ مخطط المعمل. لا يثبت صلاحيات الإنتاج أو أن الترقية نُفذت.
