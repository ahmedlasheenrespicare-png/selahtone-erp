# Cash collection destination — design only, not wired to the ERP

For an Arabic, non-production summary of current evidence, the previously selected policy, and remaining integration work, see `docs/finance-attribution-and-period-plan-ar.md`.

> Update: the application now has a **narrow temporary equality guard** for branch cash collections and holder-cash payments exactly at an opening/last-confirmed-settlement boundary. The older unguarded-engine observations below describe experiments before that change. The allocation, exact-ID membership guard, historical reconciliation and final accounting remain test-only/unimplemented. See `docs/access-control-roadmap.md` for scope and false-positive tradeoffs.

User decision: cash is attributed to the person recording the collection. If that person has an open custody in the invoice branch, select their custody. If a manager/accountant has no such custody, select the invoice branch vault; if a staff member has none, reject cash collection. The branch still comes from the server-validated sale. The pure resolver in `destination.ts` demonstrates this selection and rejects inactive/password-reset users, wrong-branch staff, missing destinations and ambiguity. It is not an authorization or locking boundary and is not imported by the application.

## Required design before wiring

1. Apply the same policy to initial catalog sales, initial inventory sales, and later invoice collections. Use the actor and branch read inside the existing serializable transaction. For retry, resolve an existing request before destination lookup and verify the stored payload and actor; never create a second accounting effect.
2. Persist an immutable relationship between the collection and its selected account and accounting treatment, with a unique constraint on collection and referential integrity. Do not infer historical destinations from today's staff branch, current custody, or invoice creator. A transaction must lock the selected account, check it is still open, insert the collection and association, and perform its accounting effect atomically; closing an account must share the lock and check pending assigned items. Decide lock ordering across invoice, actor, branch, and account and test races on real PostgreSQL.
3. The current settlement formula is `book balance + period collections - holder-cash expenses`. For custody, the draft option is to record an association **without** immediately crediting a movement and include assigned, not-yet-settled collections in that custody period. For vault, draft option is an immediate collection movement and exclude that collection from custody period sums. This is a proposal, not implemented or reconciled. Any alternative must ensure each amount is counted exactly once, including after a cash count, settlement, refund and replay.
4. Define cutover for existing collections and pending/confirmed settlements and counts before changing the formula. Existing rows have a recorder but do not prove where cash was physically held. No backfill should silently assign old collections or rewrite confirmed histories. Define reviewed opening checkpoints, legacy unresolved items, continuity of totals, non-cash methods, misrecording/reversal, reporting, and rollback.
5. Check `HOLDER_CASH` payments too: the current period identifies them by expense requester, who may differ from the person whose cash was spent. Correcting collection destination alone does not fix that separate ambiguity. Review historical annotations and transfers before allowing replacement custodies or asserting closure safety.
6. Test direct service and HTTP for all three real write paths, missing/closed accounts, scope, role, duplicate and changed request, rollback after any failure, normal and negative/correction/refund paths, pending counts and settlements, attribution after reassignment, timestamp boundaries, old data and mixed accounting versions. Run actual concurrent PostgreSQL races (collection versus close, count, settlement and duplicate request) and browser tests. PGlite and pure tests do not establish isolation correctness.

Do not enable a migration, production feature, or automatic backfill from this prototype. The audited current application still has the defects reproduced by `check:finance:collection-audit`.

## Disposable transactional experiment

`allocations.test-only.sql` and `allocate.test-only.ts` are a narrow proof of concept and are **not imported by application services**. The SQL requires a separate explicit disposable-database opt-in. The experiment validates the collection's stored method and recorder, reads candidate accounts, locks and revalidates the selected destination, and inserts one unique collection assignment in the same transaction. For custody it records a pending item and bumps account revision; for vault it calls the existing movement hook and stores the movement link. The item-based sample sum uses unsettled collection IDs, avoiding a timestamp-only boundary. `check:finance:collection-prototype` tests replay, rollback, scope, closed/missing destination and distinct custody/vault effects.

This is not a complete ledger: the current application settlement, count, closure and sales paths do not read or write this table. A narrow candidate hook can attach a reviewed set of pending IDs to a synthetic confirmed settlement inside the same test transaction, but it does not run the real settlement calculation or movements; it does not enforce that an existing confirmed settlement is new in the current transaction. There is no complete stale checking, historical cutover, correction/reversal, or real concurrency verification. In fact, the test deliberately demonstrates that the current closure code does not consult the candidate table: a synthetic direct close leaves a pending allocation. Do not use the experiment as an adapter, migration, or production feature.

## Legacy data inventory experiment

`legacy-audit.test-only.ts` is a read-only aggregate query tested exclusively on synthetic PGlite data via `check:finance:collection-legacy-audit`. It reports per-branch cash totals; recorder/invoice-creator differences; absence, presence, overlap and basic inconsistencies of matching movement/historical evidence; orphan evidence; holder-cash requester/recorder differences; and open/confirmed settlements and open counts. It does not infer actual custody, determine which collections were settled, identify safe balances or produce backfill SQL. In particular, **absence of a movement or historical annotation does not imply that cash is unrecorded or unsettled**: it may already be included in an opening, count, settlement or another process. A matched movement is also evidence, not proof of complete reconciliation.

This query is not a production audit tool, is not exposed as an endpoint or CLI, and has not been reviewed for production volume, access controls, completeness, performance, or live concurrency. It requires an explicitly supplied transaction and a trusted branch ID; it must not be used on real data without separate authorization and a reviewed operational plan.

## Synthetic period membership experiment

`period.test-only.ts` extends the disposable schema with a holder-cash payment assignment and a receipt for a reviewed set of collection and payment IDs. `reviewTestPeriod` fingerprints IDs and exact stored amounts. `captureTestPeriod` rechecks both complete pending sets, their fingerprint and the reviewed settlement totals, then marks the items and writes a receipt in one caller-owned transaction. An empty receipt is explicit, so replay cannot silently consume later items. A synthetic later item remains pending even if its timestamp equals the preceding settlement timestamp. The candidate refuses attaching items to a previously confirmed settlement without a receipt, and applies the temporary same-recorder restriction to holder-cash payments.

**This is still a laboratory model, not a settlement implementation.** The status transition is synthetic and posts no adjustment or handover movements. It is not wired to account balances, cash-count checkpoints, real sales/expense writes, closure, corrections, refunds, authorization policy, or legacy cutover. The test-only tables and records do not themselves enforce immutability against arbitrary SQL; a fingerprint detects a change against an actual reviewed snapshot, it does not reconstruct lost evidence. The sample allocators read source metadata without a row lock, lock the chosen account, then lock and revalidate the source. The capture also locks the account before assigned source rows. This narrows one inversion in the laboratory only: the complete system also locks invoices, expenses, settlements, vaults and users, so system-wide ordering and deadlock handling remain required. `check:finance:period-prototype` checks an abort of payment plus allocation, mismatched/changed sets and offsetting amount changes, rollback, replay, empty periods, and legacy refusal on PGlite. The isolated PostgreSQL test adds two collection-versus-capture and two synthetic holder-payment-versus-capture orderings, using a payment and assignment in the same synthetic transaction; it does not establish correctness for real application integration, other concurrent writers, production Prisma, or the full application.

## Selected-account lock experiment

The real collection service's temporary guard holds the collector's custody before the test-only allocator runs. The previous allocator then attempted to lock *all* candidate accounts, including a vault, which inverts a vault-first transfer's account ordering. A PostgreSQL test demonstrated the unnecessary wait: with only the vault held, custody collection timed out (`55P03`). The prototype now reads candidates and locks/revalidates only the chosen account. The same test passes while the vault is held, and an actual transfer paused after locking the vault can coexist with the real collection holding the custody; both finish and replay without duplication in this specific interleaving.

This change affects the **prototype only**. Candidate reads use the transaction snapshot and the chosen row is revalidated under lock; they do not by themselves establish a complete rule for concurrent creation of a custody while a vault fallback is selected. Account opening, branch/user changes, multiple vault/custody candidates, invoice and settlement locks, aborts, isolation levels, and deployed Prisma still require a comprehensive integration design and testing. Do not use this as proof of global deadlock freedom or switch on the final policy.

## Real confirmation plus test-only attachment

The synthetic runtime harness now also intercepts the real `confirmSettlement` transaction immediately after its confirmation update and attaches the reviewed experimental collection/payment IDs and receipt in that **same** transaction. PGlite tests exercise actual adjustment and handover movements, changed source amounts with unchanged total, injected failure after attachment, rollback, replay, and a later pending collection. The PostgreSQL suite exercises real confirmation with real movements versus real holder-cash payment in two selected commit orders; attachment still uses test-only tables and hooks, not application code.

A deliberately constructed legacy crossover showed that equal totals can hide *different IDs* between the engine's old attribution formula and the candidate allocations; another synthetic case demonstrates the same for holder payments at an equal timestamp boundary. Therefore the test-only attachment now conservatively compares both exact ID sets against the current formula and rejects a mismatch. This is a diagnostic bridge, **not proof of correct historical attribution or physical custody**: matching wrong legacy assumptions can still yield the same IDs. The helper assumes it is invoked immediately after a new real confirmation in the same transaction; it does not itself establish that provenance and must never be used to attach items to old confirmed settlements. Its query locks and snapshot boundaries also have not been reviewed as a production lock protocol. The application remains unchanged and cutover, count, closure, refunds, corrections, vault fallback, and historical review remain unimplemented.

## Count and closure period mismatch experiment

`count-close-guard.test-only.ts` and `testCountClosePeriodGuard` are a **test-only interceptor**, not a production guard. After a tentative real count or closure write, inside that same transaction and under the engine's account lock, the experiment compares pending collection/payment IDs and amounts with the current timestamp formula. A mismatch throws and rolls back the tentative command. The closure check also rejects pending experimental assignments. It is keyed to particular SQL strings and a caller-supplied account (checked against the written row in the tested paths), and is deliberately unsuitable for production; the application does not call it.

`check:finance:count-close-period-prototype` constructs a synthetic collection whose timestamp equals the account opening boundary. The real, unmodified engine accepts a count using zero as observed cash even though the experimental assignment has ten pending, and would close the zero-book-balance account leaving that assignment pending. The interceptor rejects the count, its confirmation, a directed employee submission, and closure, with rollback assertions on movements, records, request receipts, audit and revision. It also rejects equal totals with different collection IDs, and accepts/replays a matching count with a nonempty pending period and an empty count/closure; a count does not consume or settle the assignments. This is a deliberately constructed ambiguity, not proof of a historical or actual cash holding.

The sample compares IDs and current amounts only; it does not prove source/recorder validity, historical settlement, snapshot provenance, immutability, or complete allocation. It has no integration with other count/correction paths, no reviewed lock protocol, and no PostgreSQL concurrency test. The historical unguarded engine exhibited the boundary defect; the current application has a conservative equality guard, not complete ID allocation. No migration, backfill, production feature, or real-data audit is implied by the experiment.

A separate synthetic payment-side boundary fixture now confirms the same risk for `HOLDER_CASH`: when a test payment's `recorded_at` is artificially made equal to account opening, the legacy count and closure omit it while the experimental assignment remains pending. The interceptor rejects the mismatched count and closure. This test deliberately changes test timestamps and does not establish how an actual historical event should be attributed. Successful command replay still returns its stored receipt after later changes; it does not execute the test interceptor or create another write.

On temporary PostgreSQL, selected interleavings exercise a real direct count and directed holder submission versus a real holder-cash payment with test-only allocation and comparison. The earlier engine allowed payment after an open/submitted count and invalidated confirmation by revision. The application now blocks new holder-cash payments with an open or confirmed count; revised tests exercise that conservative behavior and payment-first stale direct counts. Counts leave the experimental payment pending. These are selected scenarios only, not a production integration or global concurrency proof.
