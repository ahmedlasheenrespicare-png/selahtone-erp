# Global open-custody uniqueness — synthetic experiment only

**Do not run the SQL against existing or real databases. It is not a migration or a production-ready audit.** The explicit session setting is a test tripwire, not authorization or a security boundary.

`index.test-only.sql` refuses a synthetic schema with a missing holder or more than one open custody for a holder, then builds a unique partial index on `holder_id` for open custodies. It keeps the existing permanent `(branch_id, holder_id)` index; it does not enable reopening an old custody in the same branch. It neither edits nor resolves conflicting rows. Do not copy the disposable test's direct updates/deletes into a remediation workflow.

The PGlite test exercises opt-in, duplicate refusal, preservation of rows, a cross-branch duplicate after index creation, and existing-index preservation. The isolated PostgreSQL test first reproduces a defect in the current application guard: an uncoordinated external insert commits after the duplicate check and before closure, and closure still succeeds. In a separate clean state it then builds the test index and races two direct inserts in different branches: one waits and receives the unique-index error. This validates only those synthetic interleavings, not every workflow, privilege setup, deployment driver, error translation, rollback, historical attribution, or future index alteration.

An actual change would require a separately reviewed policy and audit, conflict-resolution procedure that preserves all financial evidence, proof of constraint/schema health (including non-null holders), writer/privilege controls, rollout and rollback plans, performance and index-build locking tests, and explicit approval. A regular index build takes a table lock and may block writes; `CREATE INDEX CONCURRENTLY` has different transaction, failure and recovery semantics; only the narrow failed-build interleaving below has been evaluated, not a deployment procedure. Neither index nor audit proves physical cash, completes historical period attribution, or makes the application production-ready.

Run locally only on disposable data:

- `npm run check:finance:custody-uniqueness-prototype`
- `SYNTHETIC_POSTGRES_BIN=... npm run check:finance:postgres-concurrency` (creates an isolated local PostgreSQL cluster and a separate test database; never reads `DATABASE_URL`).

`audit.test-only.ts` is a separate **global** read-only synthetic anomaly inventory, not a production audit endpoint or authorization boundary. It pages open custody accounts by ID and flags another open custody for the same holder (across all branches), missing holder/branch/user, inactive holder, holder/branch mismatch, and existence of open count or settlement on that account. An account can have several flags and each duplicate account appears separately. It returns IDs and branch references, not balances, amounts, movements, names or inferred physical cash; it cannot identify the correct account, calculate exposure, or prove complete historical settlement. Closed accounts, orphan movements and non-open requests are outside its scope.

The caller must provide a single consistent read-only transaction for all pages, and missing tables fail rather than becoming empty results. The 18-digit cursor bound excludes some valid PostgreSQL bigint IDs. The global scan is intentionally unscoped and can reveal relationships across branches; session opt-in is not access control. It has not been reviewed or benchmarked for real data, large tables, adverse schemas, cross-branch confidentiality or authorization. It must not be exposed in the application or run on existing databases. Use `npm run check:finance:custody-uniqueness-audit` for the permissive PGlite fixture; the separate disposable PostgreSQL test checks two-page read-only behavior on the synthetic candidate schema.

Additional synthetic checks: when an uncommitted external writer inserts two conflicting custodies before the actual script starts, the preflight cannot see them, the ordinary index build waits, and after the writer commits the build fails with `23505`; rolling back leaves both synthetic rows unchanged and no new index. This covers one PostgreSQL interleaving, not build performance, cancellation, `CONCURRENTLY`, or operational recovery. A permissive-schema test also shows that the preflight rejects an existing null holder but a later null holder is **not** prevented by this unique index alone. The candidate schema has a holder/kind check, but an actual deployment must independently verify and enforce that constraint for future writes; the test-only preflight is not an enduring constraint.

A further disposable PostgreSQL experiment started a concurrent unique-index build while an external writer held two conflicting inserts. After the writer committed, the build failed and left an index with `indisvalid=false` and `indisready=false`; `IF NOT EXISTS` accepted its name without fixing it. This is one failure phase; other failures may leave different readiness or enforcement behavior. The test deletes its own throwaway data and drops its own throwaway index only; it is not a recovery instruction.

`index-observation.test-only.ts` pages raw PostgreSQL catalog observations for indexes on the synthetic `finance.accounts` table, including uniqueness, validity, readiness, liveness, definition and predicate. It requires an opt-in but that is not authorization. It does not certify definitions, check all constraints, validate semantics or recommend dropping anything. Definitions and total index counts are not bounded in size; catalog visibility, large schemas and privilege boundaries have not been evaluated. It requires a consistent read-only snapshot across pages and must not be exposed or used on real data. PGlite checks a misleading index name; the disposable PostgreSQL test checks the failed concurrent build. Run the PGlite check with `npm run check:finance:custody-index-observation`.

`constraint-observation.test-only.ts` separately pages raw table constraint and column metadata in a disposable database: definitions, `convalidated`, deferral, the optional catalog `conenforced` field, column types and `attnotnull`. It does not interpret check semantics, prove constraints apply to every workflow, check domain constraints/triggers/privileges, or make a safety decision. `enforced=null` may mean that catalog field is unavailable; never treat it as enforced. Catalog definitions and total output size are not bounded; all pages require one consistent caller-owned read-only snapshot. The opt-in is not access control and this code must not be used on real databases. `npm run check:finance:custody-constraint-observation` runs the PGlite fixture; the isolated PostgreSQL 18 test uses a separate deliberately permissive database.

That synthetic fixture creates a `NOT VALID` check with a pre-existing invalid row: validation fails, a new row whose expression is false is rejected, but a null `kind` gives SQL `UNKNOWN` and passes the check. The observer reports an unvalidated check and nullable column, not a repair. Candidate schema has additional constraints; this experiment does not assert any actual deployment has the defect or that observing flags proves a clean migration.
