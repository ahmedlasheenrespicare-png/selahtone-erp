# تجربة معزولة لنافذة التحويل — ليست ترقية إنتاج

**لا تشغّل `schema.test-only.sql` أو `tests/fixtures/finance-cutover.sql` على Neon أو قاعدة أعمال.** النموذج مستقل عن الموقع وعن نواة `finance_lab`، وأسماء الأدوار والجداول والحسابات فيه وهمية. ليس تصميمًا نهائيًا أو حدًا أمنيًا للإنتاج، ولم يُعدّل قاعدة المستخدم أو الموقع. المالية لم تُنشر؛ تشغيل أي ترقية أو نشر يتطلب مراجعة وموافقتين منفصلتين.

## ما الذي تختبره التجربة؟

- حارس تجريبي على 26 جدولًا **في الـfixture فقط**، بينها جداول التجارة والجرد والمالية الوهمية. يأخذ قفلًا مشتركًا يبقى حتى نهاية المعاملة. الانتقال يأخذ قفلًا حصريًا وينتظر الكتابات الجارية؛ المعاملة التي تعمل على لقطة قديمة قد تُرفض وتحتاج مراجعة وإعادة محاولة آمنة.
- تبدأ الحالة `LEGACY`، ثم `FROZEN` لإيقاف الكتابات المحروسة، ثم `NEW`. يمكن التراجع من التجميد إلى القديم **قبل** تفعيل الجديد فقط. بعد تفعيل الجديد يمكن التجميد والاستئناف، لكن لا يسمح النموذج بالعودة إلى `LEGACY`. يُسجّل سبب الانتقال ودور قاعدة البيانات وإصدار متوقع ومعرّف طلب؛ الإعادة لا تكرر الانتقال وتعرض حالته الحالية. ليس هذا خطة استعادة بيانات أو خطة تشغيل نهائية.
- لكل معاملة جديدة تصريح خاص برقم المعاملة واتصال قاعدة البيانات، يُزال عند الإنهاء أو التراجع. لا يكفي `application_name` أو إعداد جلسة مخصص لتقليده. يمنع ذلك الكود القديم الذي لم يستدعِ التصريح حتى لو استعمل دور الاتصال الجديد بالخطأ. لكنه ليس إثبات هوية المستخدم ولا دليلًا على تسجيل حركة نقدية؛ أي شخص يملك بيانات الدور الجديد وصلاحية الاستدعاء يستطيع استدعاءه عمدًا.
- للتحصيل أو الرد النقدي في `NEW` يتحقق المحفّز المؤجل قبل نجاح المعاملة، في هذا النموذج فقط، من وجود **حركة واحدة صحيحة أو سجل تاريخي واحد صحيح، وليس كليهما**، مع تطابق المبلغ وفرع الفاتورة والحساب والجرد المرتبط والاتجاه. عملية البطاقة أو التحويل أو المحفظة لا تقبل حركة أو سجلًا نقديًا. تتراجع المعاملة كلها عند الفشل. القيود الفريدة والأقفال تمنع تسجيل الحركة والسجل التاريخي للحدث نفسه بالتزامن، حتى مع مستوى العزل الافتراضي؛ قد يرفض PostgreSQL إحدى المعاملات بتعارض تسلسلي أو تعارض أقفال.
- يتطلب فتح الحساب الوهمي جرد افتتاح مطابقًا في المعاملة نفسها. يسجل الجرد اللاحق مبلغًا وتاريخًا ومؤكدًا من سجل المستخدمين الوهمي، ويجب ألا يسبق الجرد السابق. الحركة العادية تشير لأحدث جرد مسجل للحساب مع إقرار أنها بعده؛ السجل التاريخي يشير إلى جرد احتسبه، ولليوم نفسه يتطلب إقرار أنه قبله. يتداخل قفل الحساب مع إنشاء جرد لاحق حتى لا تُعتمد حركة بمرجع أقدم. الأحداث النقدية والحسابات وبيانات الجرد المؤكدة لا تُعدّل أو تُحذف في `NEW`، وفرع الفاتورة لا يتغير؛ التصحيح الفعلي يلزمه تصميم سجلات مستقلة.
- فحص كون المُدخل مديرًا أو محاسبًا ونشطًا ومنتهيًا من تغيير كلمة المرور يعتمد على **معرّف مُقدَّم وسجل وهمي**، لا على جلسة دخول موثقة. التسجيل التاريخي لا ينشئ حركة نقد ثانية. الإقرارات والتواريخ والأرقام لا تثبت وقوع القبض أو الرد أو الجرد في الواقع، ولا تكتشف تسجيل الواقعة نفسها بطلب آخر ومعرّف حدث مختلف.

## تشغيل الاختبار بأمان

```bash
npm run check:finance:cutover
```

الأمر دون `FINANCE_TEST_PG_BIN` يشغّل اختبار رفض التثبيت دون السماح الصريح فقط، **ويتخطى اختبار PostgreSQL الرئيسي**. لتشغيل الاختبار الرئيسي، استخدم مستخدم نظام غير root ومجلدًا مطلقًا يحوي برنامجي `initdb` و`postgres` المحليين، وأضف مسار المكتبات المحلية إن احتاجه توزيع PostgreSQL، مثلًا:

```bash
FINANCE_TEST_PG_BIN=/absolute/local/postgresql/bin \
LD_LIBRARY_PATH=/absolute/local/postgresql/lib \
npm run check:finance:cutover
```

ينشئ الاختبار عنقود PostgreSQL جديدًا ومؤقتًا وUnix socket خاصًا بلا مستمع TCP، وينشئ أدوارًا وبيانات مختلقة ثم يوقفه ويحذفه. لا يقرأ `DATABASE_URL` الحقيقي، ولا يستخدم `seed` أو `db:push`. اختبارات PostgreSQL تحاكي أيضًا دوال البيع والتحصيل والرد المنشورة من كود المستودع على بيانات وهمية، بما في ذلك منع الكود القديم والتراجع عند فشل الحركة، ومعاملات متزامنة عند `SERIALIZABLE` و`READ COMMITTED` وإيقاف مستخدم أثناء المراجعة. في تشغيل محلي على PostgreSQL 18 وNode 20 و22 اجتازت المجموعة **25 اختبارًا من 25 دون تخطٍ**. تشمل اختبارًا يثبت وجود المشكلة التالية؛ نجاح هذا الاختبار **ليس** إصلاحًا لها.

## تجربة ثانية: ربط الحارس بنواة `finance_lab` الفعلية

`lab-bridge.test-only.sql` جسر اختباري يربط حارس التحويل بنواة المالية **كما هي في المعمل**، لا بنسخة مبسطة:

- يُثبّت داخل معاملة واحدة على قاعدة PostgreSQL المؤقتة، بعد تثبيت `finance_lab` وحارس التحويل، ويرفض التثبيت دون تفعيل الخيارات الثلاثة معًا (`finance_cutover_test_only` و`finance_cutover_lab_test_only` و`finance_lab_test_only`). يضيف حارس كتابة على 18 جدولًا من جداول النواة.
- يستبدل مُحفّزات التجربة الاصطناعية بمُحفّزات تتحقق من **الحركات والسجلات التاريخية الفعلية** في `finance_lab.movements` و`finance_lab.historical_commerce`: وجود دليل واحد فقط للحدث النقدي، وتطابق المبلغ والفرع والفاتورة والحساب والجرد، وأن الحركة العادية تشير إلى آخر جرد مؤكد (أو إلى الافتتاح)، وأن السجل التاريخي محفوف بالإقرارات الأربعة المحفوظة وتاريخه لا يتجاوز الجرد المختار. غير النقدي لا يقبل حركة أو سجلًا.
- يتحقق من صلاحية المُدخل بمقارنة سجلي المستخدمين الوهميين (`public.users` و`finance_lab.users`) معًا، ومن أن فتح الحساب وتأكيد الجرد والتسجيل التاريخي للإدارة فقط، وتحصيل الموظف لعهدة نفسه أو خزنة فرعه فقط. هذا تحقق من **معرّف مُقدَّم** لا من جلسة موثقة.
- يضيف قيدًا على دفع المصروف: النقدي بعد الجرد يلزم حركة واحدة مطابقة وترتيبًا صريحًا عند تداخل الجرد، والنقدي التاريخي المشمول بالافتتاح لا ينشئ حركة، وغير النقدي بلا حساب أو جرد. يُحفظ في الجدول إقرار الدفع الفعلي (`actually_paid`) وإقرار شمول الافتتاح بدل بقائه في سجل التدقيق فقط.
- يجعل الحسابات وبيانات الجرد المؤكدة والحركات والسجلات التاريخية والمدفوعات والمصروفات المدفوعة غير قابلة للتعديل أو الحذف في حالة `NEW`، مع بقاء حجز الرصيد وتأكيد الجرد في خطوتين.

التشغيل (يُنشئ عنقود PostgreSQL مؤقتًا ويحذفه؛ لا يقرأ `DATABASE_URL` ولا يستخدم `seed` أو `db:push`):

```bash
FINANCE_TEST_PG_BIN=/absolute/local/postgresql/bin \
LD_LIBRARY_PATH=/absolute/local/postgresql/lib \
npm run check:finance:cutover-core
```

دون `FINANCE_TEST_PG_BIN` يعمل اختبار رفض التثبيت فقط و**يتخطى** اختبار PostgreSQL. يجتاز حاليًا **11 اختبارًا من 11** على PostgreSQL 18 مع Node 20 و22، ويشمل: تجميدًا يمنع مسارات التجارة والمالية الحقيقية، وعشر حالات فشل `COMMIT` متتالية، وإنهاء اتصال أثناء `COMMIT` المؤجل، وفتح الحسابات، وبيعًا وتحصيلًا وردًا نقديًا، وتاريخيًا ليوم الجرد، ومصروفًا نقديًا وتاريخيًا وغير نقدي، وتسليمًا وجردًا من خطوتين، وإعادة الطلب نفسه بعد ضياع الاستجابة، ومنع تعديل الأدلة، ومنع العودة للقديم. هذا تقدم في المعمل وليس دليل جاهزية؛ النواة نفسها ما زالت تجريبية وغير منشورة، وبعض الجداول مثل تصحيح المصروف والافتتاح وحالات الاشتباه ليست محكومة بهذا الجسر بعد.

## تجربة ثالثة: مجمّع اتصال مملوك لكل عملية

`owned-prisma.test-only.ts` نموذج اختباري يعالج مشكلة الاتصال المحجوز:

- كل عملية تفتح **مجمّعًا مستقلًا باتصال واحد** وعميل Prisma خاصًا بها، ثم تُدمّر أي اتصال بقي محجوزًا بعد انتهاء المعاملة، وتتأكد من وصول عدد اتصالات المجمّع إلى صفر. لأن المجمّع مملوك لهذه العملية وحدها، لا يمكن أن يحرر اتصال طلب آخر أو أن يُعيد اتصالًا مكسورًا إلى مجمّع مشترك.
- يميّز بين خطأ داخل المعاملة (النتيجة معروفة: لم يُحفظ شيء) وخطأ بعد اكتمال نداء الاختبار (`FixtureCommitOutcomeUnknown`): الحالة الثانية نتيجة **مجهولة**، ولا يجوز إعادة المحاولة بمعرّف طلب جديد قبل التحقق؛ ويُعاد رمي أخطاء التنظيف مجمّعة مع الخطأ الأصلي بدل إخفائها.
- يقبل فقط مقبس Unix داخل مجلد مؤقت match باسم `selahtone-cutover-*`، ويفحص أن دور الاتصال هو دور التجربة وأن قاعدة البيانات لا تستمع على TCP. هذا تحقق إضافي في الاختبار وليس حدًا أمنيًا للإنتاج.
- **ليس** مدير اتصالات إنتاجيًا: يفتح مجمّعًا وعميلًا لكل عملية، ويستخدم `pool.end()` دون ضغط أو إعادة استخدام أو قيود على عدد العمليات المتزامنة، ولا يحل مشكلة النتيجة المجهولة بل يصنّفها فقط، ولا يختبر انقطاع الشبكة أثناء `COMMIT` نفسه أو Pooler أو إعادة المحاولة على مستوى التطبيق.

## نتيجة مهمة مفتوحة: اتصال PrismaPg بعد فشل COMMIT

في عميل الاختبار المؤقت `PrismaPg 6.19.3` مع `pg`، أدى رفض قيد مؤجل عند `COMMIT` إلى التراجع عن البيانات كما يجب، لكن اتصالًا بقي محجوزًا من مجمّع الاختبار بدل عودته إليه. يتعمد اختبار معزول إعادة إنتاج ذلك ويتحرر اتصال الاختبار يدويًا بعد القياس؛ تكراره في نظام فعلي قد يستنزف الاتصالات. استخدام `SET CONSTRAINTS ALL IMMEDIATE` داخل مُغلّف الاختبار يحول بعض أخطاء التحقق المتوقعة إلى أخطاء داخل المعاملة، لكنه **ليس حلًا عامًا** لفشل `COMMIT` أو التعارض التسلسلي أو انقطاع الاتصال، ولا يُنقل كما هو إلى الإنتاج.

التطبيق المنشور يستخدم `PrismaClient` المعتاد، وليس هذا المُكيّف التجريبي؛ **لم نختبر سلوك محركه أو مجمّع Netlify/Neon عند فشل COMMIT** ولا نزعم وجود المشكلة فيه أو عدمها. قبل اعتماد أي تصميم يستخدم قيودًا مؤجلة يلزم اختيار آلية الاتصال الحقيقية، ومعالجة تحرير الاتصالات والتحقق منه باختبار ضغط وفشل COMMIT والتزامن والانقطاع وإعادة المحاولة ذات المعرّف نفسه، دون افتراض نتيجة معاملة مجهولة. المسألة مانع جاهزية، وليست موافقة على تغيير الحزمة أو نشرها.

أثبت اختبار الجسر (`check:finance:cutover-core`) أن نمط **المجمّع المملوك** يستعيد الاتصال في كل مرة: عشر حالات فشل `COMMIT` متتالية أنتجت `checkedOutAfterTransaction=1` و`destroyed=1` وانتهى المجمّع بعدد اتصالات صفر، دون تغيير أي بيانات، وكذلك عند إنهاء الاتصال أثناء `COMMIT` المؤجل. هذا يثبت إدارة الأعراض داخل التجربة ولا يثبت عدم وجود الخلل في مُكيّف Prisma أو أن النمط صالح للإنتاج بمفرده؛ ولا يزيل حاجة اختبار المحرك الحقيقي، ولا يحل نتيجة `COMMIT` المجهولة (يُصنّفها فقط)، ولا يختبر ضغطًا أو انقطاعًا شبكيًا أو Pooler.

## الحدود والخطوات المطلوبة قبل الإنتاج

- جداول وأقفال التجربة تختلف عن جداول المالية في المعمل؛ لم تُوصل بالمنفذ أو واجهات المالية أو محرك الرصيد أو سير المصروفات والتحويل والجرد الحقيقي، ولم تنفّذ محاسبة الأرصدة أو تصحيحها أو تسوية فروقها. وجود حركة في الـfixture لا يعني أن النواة الحقيقية أنشأتها أو أن الرصيد الفعلي صحيح. لم يُختبر هنا منع اختيار الموظف عهدة غيره أو المصروفات، أو كل مسارات الفروع الموقوفة.
- التثبيت التجريبي لا يحصر جميع جداول الإنتاج أو مسارات الكتابة أو الملكية وRLS والمحَفّزات والأدوار الفعلية. يجب تحديد هوية اتصال التطبيق وصلاحياته واتصال مدير الترقية، ومنع امتلاك التطبيق للجداول أو تعطيل المحفزات، ومراجعة تأثير الـpooler على هوية الاتصال والانتقالات. التثبيت والأقفال والاعتماديات وأداء الجدول الخاص للأحداث وحجمه قد تحتاج تصميمًا واختبار حمل وتنظيفًا آمنًا.
- يجب ربط عمليات المالية والتجارة الحقيقية في **معاملة واحدة**، واختبار فشل كل خطوة وحجز الأرصدة والصلاحيات والفروع، والتكرار بعد نتيجة مجهولة وعمليات لا يمر فيها الطلب عبر المسار المتوقع. يستلزم الأمر مخططًا فعليًا وفحوصًا قبلية وبعدية محدثة وخطة صيانة ورجوع ومراجعة المرفقات والنسخ، ثم مراجعة SQL وموافقة تشغيل مستقلة وموافقة نشر مستقلة.
- مدير قاعدة البيانات أو مالك الجداول أو حامل صلاحيات التطبيق قد يزور بيانات أو إقرارًا أو يغيّر الحماية؛ النموذج لا يحل هذه المخاطر. لا يثبت الفحص السابق أن بيانات الإنتاج لم تتغير. نسخة المستخدم الجديدة واختبار الاستعادة مؤجلان باختياره؛ لا تُحذف النسخة القديمة أو Snapshot ولا يُجرى اختبار الاستعادة دون إذن جديد.
