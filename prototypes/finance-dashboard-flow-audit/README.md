# Synthetic expense period inventory — test only

`expenses.test-only.ts` compares three independent sets of synthetic expense IDs for an explicitly selected branch and optional requester: expense date, attested payment date, and database recording timestamp (converted to Cairo). It flags missing/invalid selected fields and unequal effective versus recorded payment amounts; it never selects a preferred date, computes a balance, classifies physical payment, or accesses a database. Only rows marked paid enter the two payment sets; expense-date set includes every status.

The timestamp is database evidence, not the time money physically changed hands. The payment date is an attestation, not independent proof. Date-set equality, equal amounts, or no findings do not prove timing, provenance, actual payment, correction accounting, allocation, completeness or cutover readiness. Missing/invalid dates are omitted from the relevant sets and reported for paid records; callers must not treat those sets as complete. This small synthetic comparator does not validate authorization, real schemas, cancelled sales, collections, refunds, multiple payments, historical inclusion, opening balances, query snapshots, access control or performance. It is not a reporting API and must not be run on real data without a separately reviewed design and authorization.

Run `npm run check:finance:dashboard-flow-audit`. Tests cover cross-month expense/payment/recording, Cairo date rollover, differing actor/branch scopes, pending and missing evidence, invalid dates, amount mismatch and non-mutation. No SQL, migration or backfill is involved.

`recorded-flow.test-only.ts` is a separate in-memory sketch for the user's choice of registration-time reporting. It groups supplied synthetic collection, refund and payment events by explicit method and actor/branch scope, using recording dates in Cairo and integer cents; it does not net or call the result cash on hand. It refuses partial totals when scoped input contains invalid evidence. This is not a database adapter: the caller could supply incomplete or duplicated real-world events with different IDs, and no selection of actor semantics, cancelled invoices, corrections, historical payments, accounting movement associations, or cross-source authorization is approved by the sketch. Deduplication and grouping are not proof of physical cash. The disabled UI remains disabled.

`sources.test-only.ts` is an opt-in, read-only **synthetic** source inventory using the candidate column shapes. It selects each recorded collection/refund/payment for a specified Cairo month and branch (optionally exact recorder), includes events linked to currently cancelled invoices and marks them, and flags historical payments and whether a correction currently exists. Flags describe state at the read snapshot, not state at event time. It preserves the originally recorded payment amount, does not fabricate cancellation reversals or apply later corrections, and does not decide how a UI should treat flagged items. `CURRENT_TIMESTAMP` can represent transaction start, not commit order or physical event time.

The new database test uses a deliberately minimal PGlite schema, an explicit test-only session setting and a caller-owned read-only transaction. It checks branch/recorder scoping, both month boundaries, payment/collection/refund, cancellation and correction flags, refusal without opt-in, and read-only enforcement. This is not a test against the full production schema or actual services. The session setting is a guard against accidental use, not an authorization boundary. The prototype cannot establish completeness or defend against missing source rows, corrupt joins, multiple real-world recordings, phantom events, privacy, output scale or runtime permissions; no database access is authorized for real data.

`check:finance:dashboard-flow-services` also creates a fresh disposable preview schema, applies candidate SQL only there, and runs actual catalog-sale, later collection, cancellation, card refund, expense approval and holder-cash payment services. It checks the test-only reader returns their recorded IDs, recorder, methods, amounts and cancelled-sale flags once despite replay, and that the reader leaves counts and audits unchanged. It uses PGlite and Prisma WASM, not native Prisma or production. This is one chosen sequence, not a complete audit of corrections, historical flows, authorization, failures, clock changes or concurrency.
