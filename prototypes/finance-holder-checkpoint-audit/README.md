# Synthetic holder-cash checkpoint inventory — not for production

`audit.test-only.ts` inventories **candidate evidence**, not settled/unsettled status or an accounting allocation. For one supplied branch and a page of `HOLDER_CASH` payment IDs, it enumerates every custody with the expense requester's ID in that branch (including closed and multiple possible custodies), and its opening, confirmed settlements and confirmed counts. A missing candidate remains visible. It exposes the expense requester and payment recorder independently. It compares the payment's claimed calendar date with each reference date, and its database registration timestamp with the reference's registration/confirmation timestamp, including exact ties. Settlement day is Cairo local; a count's date is `counted_on` and its timestamp is confirmation time, not a proven physical count time.

This is intentionally broad. Current or historical account membership, an earlier or matching date, a matching recorder, a timestamp tie, or lack of evidence **does not prove** who paid, when money changed hands, whether the opening/count/settlement contained the payment, or which period owns it. No result assigns an account, proposes a backfill, changes a status, fixes an amount, or declares a payment safe. Canceled/open references are not enumerated; unrelated sources and checkpoints, direct writes, evidence outside these tables, corrections, physical documents, prior operational settlements and legacy inconsistencies require separate review. Missing or malformed records may be omitted by joins, and output does not prove inventory completeness. Multiple custodies may be candidates even where their lifetimes do not overlap the event: this is deliberate and must not be treated as proof either way.

The page limit is applied to payments before expanding candidate accounts and references. The number of evidence rows for a single payment is unbounded; this is not a performance-safe production scanner. The helper requires a caller-supplied transaction and a session test-only opt-in. **The opt-in is not an authorization boundary**; the helper does not enforce read-only, access control, database identity, retention or production-safe load. Tests use disposable databases and explicit read-only transactions. Do not invoke this on real or copied production data without separate authorization and reviewed operational/security plans.

Run `npm run check:finance:holder-checkpoint-audit-prototype` for isolated fixture behavior and `npm run check:finance:holder-cash-opening-audit` for a PGlite integration with actual synthetic service records. The PostgreSQL concurrency test also checks one synthetic payment and settlement through Prisma WASM. Neither proves native Prisma production operation or all concurrent behaviors.

## Synthetic review and correction evidence

`corrections.test-only.ts` is a **separate** payment-paged inventory: one PAYMENT row and separate REVIEW, CORRECTION and MOVEMENT evidence rows per matching payment, with no multiplication against candidate custody checkpoints. It returns selected fields rather than full snapshots. Reviews are matched by expense, while corrections are included if **any** of their payment, expense or review-expense links matches. Their actual IDs are exposed so contradictory links can be investigated; the same correction can consequently appear for more than one payment. Attached correction movements are listed separately, with their stored kind, direction, amount, branch and timestamp. Each review records whether its snapshot has a `source` key as well as its value, distinguishing a missing legacy key from an explicit null. No ordering of records establishes physical timing or an accounting period.

A review's proposal is **not** a confirmed amount. A correction's before/after amounts, nullable book difference and linked movements are stored evidence, not a calculated settlement effect; a missing movement or a null book difference does not prove that a difference was included or excluded in a count, opening or settlement. These rows are not joined to a checkpoint and do not resolve attribution. Orphan reviews/corrections with no matching selected `HOLDER_CASH` payment, malformed or missing source, external records, and evidence outside these tables are not inventoried. Matching a contradictory link can expose IDs and fields from another expense or branch, so even the supplied branch is **not** a confidentiality boundary. This helper is strictly synthetic and is not authorized for production or copied data.

As with checkpoint rows, pagination bounds payment IDs, not evidence rows (including the extra lookahead payment). A single payment may expand without bound. Use one caller-owned, read-only consistent snapshot when comparing with the separate checkpoint inventory; separate calls without one can see different database states. The session flag is not an access control or read-only enforcement. Run `npm run check:finance:holder-correction-evidence-prototype` for synthetic ambiguous-link fixtures and `npm run check:finance:holder-correction-guard` for PGlite integration with real service-created reviews. The temporary PostgreSQL/Prisma WASM test checks a service-created review, not native Prisma or production readiness.

## Expenses without a matching holder-cash payment

`unmatched-reviews.test-only.ts` complements (does not replace) the payment-paged scanner. It pages expense IDs in a supplied branch which have a review or a correction connected by its expense, payment-expense or review-expense link, **and no payment currently marked `HOLDER_CASH` for that expense**. It emits an EXPENSE marker and separate PAYMENT, REVIEW, CORRECTION and linked MOVEMENT rows, including payment method/source, snapshot-source presence, actual link IDs and nullable references. More than one link may match without multiplying a row; a contradictory correction can nevertheless appear under multiple expenses. This includes legitimate card, transfer, wallet and account-cash cases: **the inventory is not an error classification**, and a missing payment, missing source, snapshot claim or mismatch is not proof of a holder payment. Do not infer cash or settlement effects.

The expenses must exist and have a branch; records that cannot be associated with any existing scoped expense through these links remain outside the inventory. If an expense has both holder-cash and other payments, this scanner excludes it and the payment-based scanner does not list the other payment; neither scanner proves data completeness. The branch filter is not a privacy boundary: inconsistent cross-expense links can expose identifiers or evidence associated with another branch. A page limit applies to expenses, not evidence rows, and lookahead evidence is also unbounded. The query has not been performance-reviewed. The opt-in is not authorization; the caller must provide a read-only consistent snapshot when comparing both scanners. Only disposable synthetic data is allowed. Run `npm run check:finance:unmatched-review-evidence-prototype`; PGlite and temporary PostgreSQL via Prisma WASM integration are covered by the holder correction guard and concurrency tests.

## Mixed payment sources on the same expense

`auditSyntheticMixedPaymentReviews` uses the same expense-paged evidence query for an existing branch expense with both a currently recorded `HOLDER_CASH` payment and a payment whose source differs or is null, provided a review or linked correction exists. It includes all payments and the same separate review, correction and movement evidence, so the earlier scanners' gap for the non-holder payments of a mixed expense can be inspected. Null is included as unknown, not classified as another actual source. The lax synthetic fixture intentionally allows records that normal schema constraints or service paths may forbid; this does not claim mixed payments occur in actual data.

The same opt-in, branch-confidentiality, malformed/orphan, unbounded expansion, consistency and performance limitations above apply. It does not inventory mixed expenses without a review or linked correction, prove actual payments or allocation, or establish that all legacy evidence is covered. Use only disposable synthetic data, never production or copies without separate authorization. The PGlite fixture tests pagination, unknown source, branch and opt-in and verifies caller-enforced read-only behavior; mixed mode has not been independently checked against native Prisma or real datasets.

## Globally unscoped reviews and corrections

`auditSyntheticUnscopedEvidence` provides **two independently paged global inventories**, with separate cursors for review IDs and correction IDs. Reviews qualify when their directly linked expense is missing or has a null branch. Corrections qualify only when none of the expenses linked directly, via the payment, or via the review both exists and has a non-null branch. A correction is not excluded merely because its associated movement has a branch. Each qualifying correction expands to its movements, exposing their recorded branches without attributing the correction. A review may be unscoped while a related correction is scoped via a different link; the inventories can overlap and do not classify errors or establish actual payment, source, allocation, or who owned a branch.

The query tests presence of a non-null branch ID, not whether that branch exists, is active, or is correct. It does not inventory standalone unlinked payments or movements, correction movements whose correction is missing, other unlinked evidence, inaccessible tables, or arbitrary inconsistencies on otherwise scoped records. Scoped contradictory links need the separate branch inventories, and no combined output proves completeness. This query is global and can reveal sensitive data and movement branches; there is **no authorization or confidentiality boundary**. Pagination limits parent IDs only, not movement rows, including the lookahead correction; performance has not been evaluated. The test-only flag is not a permission or read-only enforcement: caller must use a single consistent read-only transaction when comparing pages/scanners. Use strictly with disposable synthetic databases, never real data or copies without separate authorization and security review. Fixture tables deliberately permit broken foreign keys and null branches that normal constraints might prevent, so results do not imply such records exist. Run `npm run check:finance:unscoped-evidence-prototype`; tested on PGlite only, not native Prisma or real data.
