# Synthetic cutover-period comparison — not a production audit

This experiment compares, for one custody and one repeatable snapshot, the IDs the **current** timestamp/creator-based period formula selects with pending IDs in the **experimental** allocation tables. It returns matched, old-formula-only and candidate-only items separately for cash collections and holder-cash payments. It also flags exact cutoff/closure timestamp ties, events timestamped after closure, and selected inconsistencies in pending test allocations (wrong branch, recorder/requester, assignment author, noncash/source, or treatment). Categories overlap intentionally; an item on a boundary may also be candidate-only.

The function requires a test-only session opt-in plus a read-only REPEATABLE READ or SERIALIZABLE transaction. It has no application endpoint, performs no writes, and is tested only against disposable synthetic PGlite and PostgreSQL databases. The experimental allocation tables are **not** production tables; this is neither a production readiness gate nor a migration/backfill tool. No production data may be inspected with it without separate authorization, access controls, security/performance review and an approved plan.

Important limitations:

- Matching sets and amounts **do not prove** that the current formula is correct, who physically held cash, or that an earlier settlement/count included an event. A discrepancy is a review lead, not a correction instruction.
- Timestamps represent transaction time, not necessarily physical or commit ordering; exact-boundary and post-closure flags do not classify an event as settled or unsettled. This diagnostic intentionally mirrors the existing unbounded old formula for a closed account, so later events may appear there.
- It does not audit whole confirmed-history membership, allocation immutability, refunds, corrections, account balances, opening amounts, orphan source rows, expenses from other sources, or evidence outside these tables. A filtered list is not an exhaustive safety certificate.
- It returns item IDs and amounts and has not been assessed for production privacy, volume, indexes, locking or execution time. Do not copy its SQL into a live workflow or use its output for automatic reconciliation.

Run `npm run check:finance:cutover-period-audit` for the PGlite scenarios. The disposable PostgreSQL concurrency suite additionally runs the diagnostic in a read-only serializable snapshot after selected real-service payment and settlement interleavings. The latter uses Prisma WASM and is not proof for deployed Prisma or all races.

## Synthetic receipt consistency inventory

`receipt-audit.test-only.ts` separately inventories **test-only** settlement receipts for one custody, plus settlements referenced by that custody's test allocations or by receipts naming it. It flags a receipt on an unconfirmed settlement, a receipt/settlement account mismatch, incompatible settlement branch/account, malformed or duplicate IDs, differences between receipt IDs and attached IDs, selected invalid source/assignment relationships, differing receipt/settlement/attached totals, and a fingerprint mismatch against the **current** source values. Confirmed settlements with no receipt are listed as missing evidence, not declared wrong; linked allocations without a receipt are listed even when the settlement belongs to a different account. For a corrupted foreign allocation, both relevant account views can surface the related settlement.

`check:finance:cutover-receipt-audit` uses synthetic PGlite fixtures to cover a matching receipt, explicit empty receipt, missing evidence, wrong account/branch/source, malformed ID lists, equal totals with different IDs, and offsetting amount changes with unchanged IDs and totals. It checks opt-in, snapshot isolation, and unchanged rows. The disposable PostgreSQL suite additionally checks a real-service synthetic confirmation with a test-only receipt, then deliberately changes and restores a source amount and checks detection in a read-only serializable transaction.

This is **not** a historical proof, production audit, migration, completeness certificate, or correction algorithm. The hash is not authenticated: if both a source and the stored receipt/hash change, this diagnostic can be fooled. Matching IDs, amounts, source relationships and hash do not prove physical custody, authorization, event ordering, legitimate settlement or movement correctness. It does not audit other history or unattached pending data; the separate period comparison examines some pending records. It uses multiple queries and returns identifiers and amounts without production-scale, privacy, access-control or performance review. Do not run it on actual data or treat its output as cutover approval without a separate approved plan.

The synthetic PGlite receipt test also demonstrates a limitation: after offsetting changes to two source amounts, rewriting the unauthenticated stored hash to match produces no issue in that particular consistency check. The diagnostic remains read-only and the fixture is restored afterward. This is an intentionally coordinated test mutation, not evidence of real tampering, and reinforces that a matching hash is not independent audit evidence.

The synthetic receipt audit was also tested against a recorder-only change: the ID/amount hash remained unchanged, but the separate source-consistency check emitted `invalid_collection_allocation`. The audit did not modify the fixture; restoring the recorder removed the constructed change. This detects current inconsistency only, not original identity or a change later reverted.

A disposable PostgreSQL mixed collection/payment receipt additionally demonstrates a post-confirmation recorder change: confirmation replay still returns the saved result without revalidating source history, while this read-only inventory reports `invalid_payment_allocation` and the ID/amount fingerprint remains unchanged. Restoring the synthetic fixture clears the current inconsistency. Neither replay nor a clean inventory proves historical identity, and this test is not authorization to inspect or alter actual records.

The context also flags when the selected confirmed-settlement timestamp is earlier than the custody opening timestamp or later than its closure timestamp. These are timestamp comparisons only, not proof of commit or physical ordering. Synthetic tests show that a collection or payment can be in both `matched` and `afterClosure`: matching formula and candidate IDs therefore cannot certify membership or justify a backfill. This remains an isolated diagnostic, not an application guard.
