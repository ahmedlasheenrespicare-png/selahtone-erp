# Synthetic refund request identity experiment

A pure, test-only proposal for distinguishing legacy refund request hashes from a versioned hash containing the account review's checkpoint and explicit after-checkpoint assertion. It preserves the exact legacy input/hash shape; replay of legacy rows requires the original unreviewed payload and original actor. A reviewed payload is never silently treated as a legacy replay, and a new hash differs if the actor, account, amount, checkpoint or assertion changes. A malformed, missing or noncanonical review is not eligible for a new reviewed request. The caller must separately require a valid review **after** checking for an exact legacy replay, before any new write.

`npm run check:finance:refund-request-identity` tests hashing and input selection in memory only. The experiment is not imported by the application, does not lock or read rows, create audit events, check account ownership or current checkpoint, enforce permissions, perform a transaction, or test actual database replay/concurrency. It does not establish when a refund was physically paid. Further design must cover clients, old retries that unexpectedly include new fields, lost responses and commit races, and deployment sequencing. A mismatch rejects rather than guessing whether a new reviewed payload is a replay of an old request. No production or real-data use is authorized.

A separate test-only Prisma interceptor now composes with the checkpoint interceptor and exercises the real commerce service against disposable PGlite. It stores a versioned hash, rejects changed review/amount and mismatched reviewed snapshot, replays an exact new request once, and replays an exact legacy row without retroactive attribution. On disposable PostgreSQL (Prisma WASM adapter), one selected overlapping same-request scenario waited on the sale lock and returned the existing result with one refund and movement.

These interceptors rewrite arguments and replay results to accommodate the unmodified service. In particular, a mismatching saved hash must not be passed back unchanged when it happens to equal the service's old hash: the experiment explicitly forces a mismatch instead. The catch path outside the transaction for a unique-constraint error is not adapted or proven; this is not a production implementation, comprehensive race coverage, or a test of a native Prisma engine.
