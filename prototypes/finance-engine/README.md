# مختبر نواة المصروفات والعهد — بيانات وهمية فقط

هذه نواة **تجريبية غير جاهزة للاستخدام الفعلي**؛ مربوطة بصفحات **نسخة تجريبية مؤقتة فقط**، وليست مرتبطة بالمبيعات المنشورة أو بـPrisma الإنتاج أو بمخزن مرفقات إنتاجي. راجع `prototypes/finance-app/README.md`. لا تُشغّل ملف SQL على Neon أو على قاعدة تحتوي بيانات عمل. لا يُعدّ التطوير المعزول موافقة على ترقية قاعدة قائمة أو النشر.

- `schema.test-only.sql` ينشئ مخططًا منفصلًا `finance_lab` وجداول وهمية للفروع والمستخدمين. يرفض البدء دون تفعيل جلسة اختبار صريح. هو أداة مختبر وليس ترحيل إنتاج، ولا يضمن حاجز التفعيل وحده سلامة تشغيله على قاعدة حقيقية.
- `engine.ts` و`policy.ts` و`validation.ts` تجرّب صلاحيات المدير والمحاسب والموظف، والبنود والمصروف والاعتماد والدفع والتسليم، والمبالغ الصحيحة وحماية التكرار والتزامن. عند تسوية فواتير فرع موقوف لا يقبل خطاف التحصيل النقدي إلا المدير أو المحاسب؛ فتح حساب أو تسليم أو جرد جديد مقيد بفرع نشط في المختبر. يتحقق جسر التطبيق من تطابق حالة الفرع في النسختين الوهميتين. يتطلب منفذ SQL معاملة `SERIALIZABLE` حقيقية تُلغي كل جزء عند الفشل. معرّف المستخدم وسيط خادمي موثوق وليس مصادقة؛ يُستمد في التطبيق التجريبي من جلسة متحقَّق منها.
- المصروف المدفوع: طلب المراجعة وحده لا يغير المال. بعد تحقق المدير أو المحاسب يمكن تأكيد مبلغ مصحح بسبب، ويُحفظ الأصل والدفع والتصحيحات السابقة، وسبب المراجعة والمؤكد وحساب النقد والرصيد قبل/بعد. الفرق النقدي **تعديل دفتري لما دُفع أصلًا وليس ردًا أو حركة نقد فعلية**. لا يحرك الدفع غير النقدي أو التاريخي المشمول بجرد البداية النقد. الإغلاق بلا تصحيح ممكن بسبب ويُسجل دون تغيير الرصيد. لا يجوز أن تتجاوز الضريبة المدخلة المبلغ المصحح، ولا يحول المختبر المبلغ إلى صفر أو يلغي الدفع تلقائيًا.
- جرد النقد يُسجَّل بنتيجة فعلية والرصيد الحالي، ثم يراجَع ويُؤكّد في خطوة منفصلة؛ يحق للمُدخل نفسه التأكيد. يُحفظ قبل/بعد والسبب والهويتان. يبقى الرصيد دون تغيير حتى التأكيد، ويُسجَّل التطابق دون حركة؛ يُرفض الجرد القديم إذا حدثت حركة ولو عاد الرصيد كما كان، ويُلغى بسبب ويُعاد. لا تسمح واجهة الجرد إلا بفرع نشط في المختبر.
- عند احتمال أن يكون جرد مؤكد لاحق قد عالج فرق مصروف، يُحجب التصحيح أو الدفع النقدي المدخل متأخرًا للمراجعة بدل حسمه مرتين. في يوم جرد مؤكد يمكن تسجيل الدفع الفعلي بعده فقط بإقرار صريح يحدد آخر جرد روجع؛ الجرد اللاحق للدفع أو ترتيب اليوم المجهول يمنع التصحيح الدفتري الآلي. لا يستطيع النظام التحقق من الواقع المادي أو إثبات عدم وجود تسوية خارجية؛ يعتمد على مراجعة البشر وإقراراتهم. الحالات الملتبسة ومسارات الحركات القديمة بحاجة لتصميم منفصل قبل الإنتاج.
- تصحيح الافتتاح في فرع نشط يحفظ الأصل والتصحيحات والفرق والرصيد قبل/بعد. دون جرد لاحق يُرحّل فرق دفتري واحد بعد إقرار عدم التسوية؛ مع وجود جرد مؤكد لا يمكن ترحيل فرق آخر، ويمكن فقط توثيق أن آخر جرد عالج الفرق بعد إقرار صريح، وإلا لا تُحفظ العملية. يمكن حفظ حالة اشتباه افتتاح منفصلة دون تصحيح، ولا يثبت الإقرار حقيقة المعالجة أو أي تسوية خارج النظام.
- التحصيل والرد النقديان السابقان للجرد يُختبران عبر سجل منفصل يُكتب مع الفاتورة ذريًا دون حركة نقدية ثانية، بعد إقرار الإدارة بالتاريخ والترتيب والحساب وعدم تكرار العملية. العملية العادية تُلزم إقرار وقوعها بعد آخر جرد وتُراجع هوية الجرد تحت قفل الحساب؛ يحفظ خطاف المختبر هذا المرجع. لا تثبت الإقرارات الواقع، ولا يمكن كشف كل تكرار أُدخل بطلب مختلف. خطافات النواة القديمة وحدها يمكن استدعاؤها دون مرجع جرد، ويجب ألا تُستخدم كربط إنتاجي.
- `attachment-validation.ts` يفحص الاسم والامتداد والنوع والترويسة وحجم البايتات، بحد **5,000,000 بايت**. تنفذ النواة حفظ ملف وهمي واحد فقط لكل مصروف في جدول المختبر، ضمن معاملة واحدة مع حصة إجمالية (20 ملفًا أو 20,000,000 بايت) ومعرّف الطلب وسجل التدقيق. يُعاد التحقق من البصمة عند التنزيل وتفحص الصلاحيات في القراءة والكتابة. هذا التخزين **مؤقت فقط**؛ فحص الترويسة لا يضمن سلامة المحتوى ولا يفحص البرمجيات الخبيثة، ولا يمثل تصميم تخزين أو نسخ مناسبًا للإنتاج. لا ترفع بيانات حقيقية أو تفتح ملفًا مجهول المصدر.
- الخطافان `postCashCollectionInTransaction` و`postCashRefundInTransaction` أدوات اختبار فقط؛ لا يفحصان وسيلة الدفع أو صحة الفاتورة أو كون الرد دُفع. يلزم أن يتحقق المستدعي من **نقدية العملية الفعلية** وصلاحيتها وأن يحفظ التحصيل/الرد والخطاف في **المعاملة نفسها**. لا تُستدعى لبطاقة أو تحويل أو محفظة، ولا للمرتجع وحده.

- لحالات الافتتاح والتحصيل/الرد التاريخي يمكن حفظ بلاغات وملاحظات للمراجعة بلا حركة أو تعديل الفاتورة. ربط الحالة بتصحيح الافتتاح أو التسجيل التاريخي وتأكيدها ذري، ويمكن إغلاقها بسبب بلا تغيير. يحفظ السجل السبب والفاعل والوقت والبيانات المحتملة، ويقتصر على الإدارة؛ تعدد الحالات للتاريخي مسموح، وحالة افتتاح واحدة مفتوحة لكل حساب. يحتفظ التأكيد بلقطة الحالات وإصداراتها ويرفضها إن تغيرت أو أضيفت ملاحظة بعد المراجعة؛ الحد التجريبي 200 حالة مفتوحة من النوع نفسه على الفاتورة الواحدة. ربط الفاتورة بفرعها يفرضه الجسر. المعرف يمنع إعادة الطلب نفسه وليس تكرار الواقعة بطلب جديد، ولا يثبت الإقرار صحتها؛ ولا يمنع إدخالها خطأ كعملية عادية. السجل مؤقت في تطبيق المعمل ولا يغطي كل الحالات.

## الاختبارات

بعد تثبيت الاعتمادات وتوليد Prisma Client للاختبارات حيث يلزم:

```bash
npm run check:finance:engine
npm run check:finance:commerce-prototype
npm run check:finance:native
```

الأول يستخدم PGlite داخل الذاكرة، ويفحص الصلاحيات وتصحيح المدفوع والجرد وخطوتيه وترتيب اليوم والتاريخي والسالب والتراجع عند فشل الكتابة وإغلاق المراجعة بلا تغيير وحالات الاشتباه وربطها وحجبها عن الموظف ومراجعة الملاحظات المتغيرة. الثاني يشغّل وظائف البيع الحالية على مخطط وهمي ويستخدم معترضًا خاصًا بالاختبار لربط التحصيل والرد بنواة المختبر داخل معاملة واحدة. هو تجربة تقنية وليس ربطًا للموقع، وقد كشف أن بصمات طلبات البيع والتحصيل والرد الحالية لا تتضمن الحساب النقدي المختار؛ يجب حل ذلك قبل أي ربط فعلي.

الاختبار الثالث اختياري: يُتخطّى عند عدم ضبط `FINANCE_TEST_PG_BIN`. لتشغيله، عيّن هذا المتغير إلى المجلد المطلق الذي يحتوي `initdb` و`postgres` المحليين. ينشئ الاختبار عنقود PostgreSQL **جديدًا مؤقتًا** بمستخدم نظام غير root، ولا يستمع على TCP، ويستخدم Unix socket داخل مجلده الخاص، ثم يوقفه ويحذف مجلده؛ لا يقرأ `DATABASE_URL` أو يتصل بقاعدة موجودة. قد تحتاج بيئة الثنائيات إلى مكتباتها المحلية. يُجبر الاختبار المعاملات على التداخل ويختبر الطلب المكرر والتنافس على رصيد ومصروف واحد وعلى حفظ مرفق واحد وآخر مساحة في حصة المختبر. يختبر أيضًا تزامن الجرد مع حركة أو تصحيح أو دفع متأخر، وتكرار التأكيد، وتنافس إغلاق المراجعة وتصحيحها. النجاح لا يثبت جاهزية الإنتاج أو سلامة الترحيل.

## عوائق ما قبل أي تطبيق فعلي

يلزم مراجعة المعالجة المحاسبية المختبرية قبل أي استخدام فعلي، وتصميم حالات الجرد المتداخلة التي تُحجب للمراجعة والتصحيح العام للدفعات والحركات دون افتراض رد نقدي؛ ومراجعة تصحيح الافتتاح المحدود ونقطة بدء الحسابات والتحصيلات والردود التاريخية المختبرية محاسبيًا؛ ومعالجة بيانات الجداول الحالية؛ وتصميم تخزين مرفقات آمن وصلاحياته ونسخه؛ ودمج الحساب المختار في طلبات البيع والتحصيل والرد ومنع تكرارها، مع تطبيق قرار قصر تسوية الفرع الموقوف على المدير والمحاسب في الربط الفعلي بعد مراجعته وموافقة مستقلة؛ ما طُبّق حتى الآن داخل المختبر فقط. راجع `docs/finance-planning.md`. لا يوجد اقتراح جاهز لترحيل الإنتاج بعد.

> تنبيه: تجربة المرفقات داخل هذا المختبر **ملغاة نهائيًا** بقرار 2026-10-30، ولا يجوز نقلها إلى التطبيق أو إلى أي ترقية قاعدة.
