# تجربة معزولة لربط البنود القديمة — ليست ترحيل إنتاج

هذا نموذج جزئي لمراجعة طريقة الاحتفاظ بجدول بنود المصروفات الحالي؛ لا يتصل بالموقع ولا بقاعدة Neon، ولا يجهّز كل المالية للنشر. `category-schema.test-only.sql` و`categories.ts` وتهيئة المخطط في الاختبار **لبيانات وهمية فقط**، ويجب ألا تُشغّل على قاعدة أعمال حتى لو أمكن تفعيل حارس الاختبار. لا تقرأ الاختبارات `DATABASE_URL` ولا تستخدم `seed` أو `db:push`.

## الاتجاه المقترح في التجربة

- تستخدم البنود الموجودة في `public.expense_categories` نفسها، لا نسخة ثانية. يظل `id` عددًا صحيحًا و`code` فريدًا بطول 30 حرفًا كحد أقصى؛ لا يضيف تثبيت المخطط التجريبي صفوفًا للبنود ولا يغيّر أعمدتها أو أسماءها أو أكوادها أو حالتها. تحافظ التجربة على علاقة `public.expenses` القديمة بهذا الجدول، ولا تنسخ المصروفات أو القيود القديمة إلى جداول جديدة. لوحة التطبيق الحالية تعد صفوف جدول البنود القديم نفسه.
- توجد في مخطط الاختبار بيانات إضافية اختيارية للإصدار والمُدخل. لا توجد صفوف مبدئية للبنود القديمة: عند غيابها يظهر إصدار افتراضي، ولا يُختلق اسم منشئ أو وقت إنشاء مجهول. عند تعديل بند قديم عبر التجربة يُحفظ التغيير وسببه وهويته في سجل تدقيق، وتُنشأ بيانات الإصدار دون اختلاق منشئ سابق. البند الجديد يحصل على رمز داخلي متوافق، ويُحفظ المُدخل. تعارض الرمز لا يغير بيانات قديمة.
- يستدعي منفذ البنود نفس المعاملة `SERIALIZABLE` التي تستعملها نواة المختبر، ويحفظ المصروف الجديد اسم البند وقت إدخاله حتى لو تغير الاسم لاحقًا. لا يشمل ذلك تلقائيًا تاريخ أسماء مصروفات الجدول القديم؛ لذلك يجب إعادة فحص أي مصروفات قديمة قد تظهر قبل الترقية ومراجعة أثرها. يمكن تعديل أو تعطيل البند للإدارة فقط، بينما تبقى معرفات البنود وروابطها. يُرفض تعديل مبني على نسخة عرض قديمة حتى لو غُيّر اسم البند مباشرة خارج واجهة التجربة دون زيادة الإصدار.
- يحتفظ الاختبار بالأسماء القديمة المتكررة إن وُجدت بدل إسقاط الترحيل أو حذفها، ويمنع إضافة اسم مكرر أو تغيير الاسم إلى اسم مستخدم داخل المسارات المختبرة. يمكن إيقاف بند قديم مع بقاء اسمه المكرر. هذا الفحص يعتمد على `SERIALIZABLE` لجميع الكتّاب المشاركين؛ الكتابة المباشرة أو مسار قديم لا يستخدمه قد يتجاوز منع التكرار والتدقيق، ويلزم حصر هذه المسارات وتأمينها قبل الإنتاج.
- في الاختبار فقط يُحوَّل مخطط المختبر مؤقتًا ليشير مباشرة إلى `public.users` و`public.branches` الوهميين بدل إنشاء نسختين، مع حذف تخزين مرفقات المختبر من النموذج. تعديل نص SQL هنا آلية **اختبار فقط** وليس محولًا للإنتاج أو ملف ترقية نهائيًا. ربط جلسة المصادقة، دور قاعدة التطبيق، جداول البيع، المرفقات، واجهات التطبيق وخطة التحويل لم تُنفّذ بهذه التجربة.

## الاختبارات وحدودها

```bash
npm run check:finance:categories-candidate
```

تُستخدم بيانات مختلقة في PGlite؛ يوجد اختبار اختياري على PostgreSQL محلي بعد ضبط `FINANCE_TEST_PG_BIN` إلى المسار المطلق لمجلد `initdb` و`postgres` المحليين، مع مكتباتهما عند الحاجة. يبدأ الاختبار عنقودًا جديدًا مؤقتًا على Unix socket خاص دون TCP ويوقفه ويحذف مجلده؛ لا يتصل بأي قاعدة موجودة. يجب تشغيله كمستخدم غير root.

يشمل الفحص نموذج سبعة بنود، ومصروفًا وقيدًا قديمين وهميين رغم أن الفحص الفعلي أظهر صفرًا وقت تشغيله، للتحقق من عدم حذف البيانات عند التهيئة. يشمل أيضًا الحارس والرجوع عند فشل التهيئة داخل معاملة، وعدم وجود نسخ مستخدمين وفروع، والحجب، والنسخة التاريخية للبند، وإيقافه، وسجل السبب، ورصيد حساب وهمي وصرفًا منه، وإعادة الطلب، وتعارض الرمز واسم البند، والفشل المتأخر. يختبر PostgreSQL المحلي تداخل الطلبات والتعديلات، وإيقاف مستخدم أو فرع بالتزامن. هذه النتائج لا تثبت صحة صلاحيات أو مخطط أو بيانات الإنتاج ولا تحمي من تغيير خارج المسارات التجريبية.

تحتاج الترقية النهائية إلى تصميم متكامل وفحوص شروط مسبقة ونسخة وخطة رجوع ونافذة تحويل، والتحقق الآمن من هوية قاعدة التطبيق ودوره وصلاحياته والفهارس والتسلسل والقيود والمحَفّزات، ومراجعة البيانات التي قد تكون تغيرت منذ الفحص. تدقيق ومعرّفات النموذج المستقلين ليسا تصميم التدقيق والطلبات النهائي. لا توجد موافقة على تشغيل SQL للإنتاج أو نشر الموقع.
