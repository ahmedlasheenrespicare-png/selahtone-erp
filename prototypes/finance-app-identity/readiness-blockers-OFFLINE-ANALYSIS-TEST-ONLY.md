# تحليل أوفلاين لموانع الجاهزية — TEST ONLY / غير قابل للتنفيذ

**تاريخ:** 2026-11-05 · **النطاق:** `OFFLINE_ANALYSIS_ONLY` بعد تكليف منفصل صريح ورد كاملًا حرفيًا:
«تكليف منفصل صريح بتحليل أوفلاين للموانع» (تنسيق Markdown مقبول).

**الحدود الملزمة:** `NO_SRC_NO_RENDER_YAML_NO_PRODUCTION_SQL_NO_DEPLOY_NO_SYNC_NO_TRUE`.
لا SQL تنفيذي في هذا الملف، ولا أسرار، ولا قيمة `DATABASE_URL`، ولا صفوف بيانات، ولا إجراء مالي، ولا `COMMIT`، ولا اختبار رد نقدي، ولا commit/push.

**ما لا يفعله هذا التحليل:** لا يفتح أي بوابة، ولا يحل أي مانع، ولا يُثبت أي نتيجة، ولا يُغيّر `render.yaml` أو `src`، ولا يُجيز نشرًا أو إعادة تفعيل. الحكم يبقى `NOT_READY` بوابة `SEPARATE_REENABLE_DECISION` = `CLOSED_NOT_READY`، و`reenable_gate=CLOSED`، و`C1/C2=FAIL`، و`IDENTITY_GAP_CONFIRMED`.

**الترتيب الثابت:** فحص قراءة-only ⇒ تقييم أوفلاين ⇒ نص مُراجَع ⇒ موافقة SQL صريحة منفصلة ⇒ خطة رجوع ⇒ موافقة نشر منفصلة ⇒ ضبط قيمة المتغير فقط ⇒ `C4` ⇒ `C5` ⇒ فحص بعد التشغيل ⇒ **قرار منفصل صريح** بـ`FINANCE_ENABLED`. لا موافقة شاملة.

## المانع ١ — إثبات هوية التطبيق المنشور

- **الدليل الحالي:** `C5` المحلي أكّد `current_user = session_user = selahtone_app` من اتصال مجمّع على جهاز المشغّل، بلا صفات امتياز، و18 جدولًا بالصلاحيات المتوقعة. لكنه `ROLE_IDENTITY_ONLY_NOT_A_PROOF_OF_THE_DEPLOYED_APP`.
- **الفجوة:** المالية معطّلة فلم يحدث طلب DB حي من العملية الشغّالة؛ والسجل لا يطبع قيم المتغيرات؛ وضبط `DATABASE_URL` مؤكَّد بتقرير مشغّل لا بسجل (`OPERATOR_REPORT_NOT_LOG_PROVENANCE`).
- **التصميم الأوفلاين المقترح:** فحص قراءة-only لاحق يُنفَّذ من اتصال العملية الشغّالة نفسها، نصه مُثبَّت بصمة، داخل معاملة قراءة-only تُرجَّع، ويُخرج هوية الجلسة وصفات الدور فقط.
- **معيار القبول:** هوية `selahtone_app` من اتصال أنشأته إعدادات الخدمة المنشورة، وتأكيد `ROLLBACK`، وخلو المخرج من أي سرّ.
- **يلزم لاحقًا:** نص مُراجَع ⇒ موافقة حرفية منفصلة قبل التنفيذ ⇒ خطة رجوع.

## المانع ٢ — تنفيذ RLS والمحفّزات بالدور

- **الدليل الحالي:** RLS معطّلة في `finance` و`public`، صفر سياسات، صفر محفّزات إنتاجية؛ والمحفّزات الـ19 مخبرية في `finance_lab`/`finance_cutover_test`.
- **الفجوة:** `C4` سجّل **حالة الكائنات** لا **التنفيذ**؛ لا توجد سياسات production مُراجَعة، ولا اختبار سماح/منع بدور التطبيق.
- **التصميم:** مصفوفة سياسات لكل جدول + سيناريوهات سماح/منع على PostgreSQL مؤقت، مع فصل صريح بين «وجود المحفّز» و«تنفيذه».
- **معيار القبول:** منع افتراضي موثّق، ومسار كتابة مسموح مُختبَر، ورفض أي تجاوز، بلا إجراء مالي حقيقي.
- **يلزم لاحقًا:** نص مُراجَع وموافقة منفصلة؛ لا يُفعّل RLS في الإنتاج من هذه الجلسة.

## المانع ٣ — ذرية `access_control`

- **الدليل:** `check:finance:atomic-contract-gap` (4/4) يوثّق الفجوة مخبريًا؛ محضر العمل ذو الأولوية الثانية مفتوح.
- **الفجوة:** الذرية مثبتة في بُعد الصفوف لا عبر حدود الوصول وربط النتيجة بالطلب.
- **التصميم:** عقد ذري على PG مؤقت: حد معاملة واحد + حقن فشل عند الالتزام + فحص صفر كتابات جزئية.
- **معيار القبول:** صفر كتابات جزئية، وارتباط كل نتيجة بطلبها، واختبارات معملية خضراء فقط.

## المانع ٤ — دورة حياة `PrismaPg 6.19.3` عند فشل `COMMIT`

- **الدليل:** في اختبار معزول، فشل قيد مؤجل عند `COMMIT` أبطل البيانات وترك اتصالًا محجوزًا من المجمّع.
- **الفجوة:** لا سياسة تحرير/إعادة محاولة؛ خطر فقد صامت أو كتابة مزدوجة أو استنزاف المجمّع.
- **التصميم:** إعادة إنتاج على PG18 مؤقت + سياسة تحرير الاتصال + منع إعادة الكتابة العمياء.
- **معيار القبول:** لا اتصال محجوز بعد الفشل، ولا فقد صامت، ولا كتابة مزدوجة.

## المانع ٥ — نسخة مرشحة + رجوع مُجرَّب

- **الدليل:** مسودة مرشح للمراجعة فقط، و`runbook` و`restore-drill.sh`، وآخر نسخة يدوية قديمة غير مُختبَرة.
- **الفجوة:** لا نسخة مُوسومة مُختبَرة ولا بروفة رجوع على الإصدار الحالي.
- **التصميم:** بصمات قبل/بعد، ونسخة موسومة، وبروفة رجوع كاملة على قاعدة اختبار معزولة.
- **معيار القبول:** تطابق البصمات ونجاح الرجوع، بلمس قاعدة الاختبار فقط.

## المانع ٦ — توقيت الحركة النقدية والمراجعة البشرية

- **الدليل:** لا إثبات؛ واختبار الرد النقدي ممنوع قبل الجاهزية.
- **الفجوة:** لا دليل على تسجيل الحركة عند قرار المراجعة، ولا على خلوّ الحركات اليتيمة.
- **التصميم:** تحليل وصفي لمسار الطلب⇒القرار⇒الحركة على بيانات اصطناعية مخبرية.
- **معيار القبول:** ارتباط كل حركة بقرار بشري موثّق وصفر حركات يتيمة، بلا بيانات فعلية ولا رد نقدي حقيقي.

## المانع ٧ — نافذة التحويل

- **الدليل:** نموذج معزول في `prototypes/finance-cutover` يوضّح الحاجة.
- **الفجوة:** النشر ذو المرحلتين (قاعدة ثم موقع) بلا نافذة تمنع البيع/التحصيل/الرد/الصرف/التحويل، وبلا منع للطلبات المباشرة.
- **التصميم:** معيار النافذة + حارس رفض + اختبار تجاوز مخبري + خطة إنهاء.
- **معيار القبول:** رفض كل كتابة محظورة داخل النافذة حتى عبر الطلب المباشر.

## المانع ٨ — بيانات السجل الناقصة

- **الدليل:** سجلان بلا سنة ولا طوابع ولا قيم env؛ أحداث `false`/`true`/الاستعادة بلا مَن/متى/قرار.
- **الفجوة:** لا ربط زمني بين التغييرات وقراراتها، والسجل لا يُثبت ضبط `DATABASE_URL`.
- **المطلوب (وصفي فقط):** السنة والطوابع، ومَن/متى/قرار ضبط `false` الأصلي، ومتى/قرار إعادة `true`، ومتى/قرار الاستعادة — بلا `DATABASE_URL` ولا كلمة مرور ولا صفوف بيانات.

## المانع ٩ — تعارض `render.yaml`

- **الدليل:** `render.yaml:31 = "true"` بلا `sync:false` بينما القيمة الحية `false`.
- **الفجوة:** أي `Sync`/Blueprint قد يُعيد التفعيل صامتًا قبل استيفاء الشروط.
- **التصميم:** تحليل خياري للتسوية (منع `Sync` أو تعديل Blueprint) **دون لمس الملف في هذه الجلسة**.
- **معيار القبول:** قرار منفصل صريح يزيل التعارض ويمنع إعادة التفعيل الصامتة، مع تحقق بعده.
