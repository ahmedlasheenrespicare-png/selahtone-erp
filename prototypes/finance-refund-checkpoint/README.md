# Refund checkpoint experiment — test only

The actual commerce refund service currently creates a cash movement without supplying `checkpointRef` or `afterCheckpoint` to the finance hook. A synthetic PostgreSQL diagnostic in `check:finance:postgres-concurrency` confirms this after a confirmed count. Absence of a reference does **not** prove when money physically changed hands or that any existing history is wrong.

`adapter.test-only.ts` is a disposable transaction interceptor, not application code. After the real refund row is tentatively created, it invokes the existing latest-checkpoint guard with an explicitly supplied synthetic review. It checks that actor, invoice, branch, account and the subsequently inserted refund movement match that review, then marks the movement's checkpoint in the same transaction. It deliberately recognizes exact Prisma delegate and SQL shapes; it does not write the production hook's checkpoint audit event and is not safe or complete enough to deploy. It does not enforce browser input, session identity, user permission, source provenance, or noncash behavior. The guard itself verifies the branch, account and current confirmed checkpoint under the account lock. An operator's statement is not independent evidence of physical payment time.

`npm run check:finance:refund-checkpoint-prototype` uses PGlite and synthetic data to exercise omitted confirmation, stale opening reference after a count, rollback of tentative refund and invoice revision, valid confirmed-count and opening metadata, wrong reviewed account, and replay including after a subsequent count. The PostgreSQL disposable suite tests two selected lock orders between real count confirmation and refund with the interceptor: count-first rejects the stale review, while refund-first invalidates the earlier count by revision. It uses Prisma WASM with an adapter, not the native production engine.

Before any production design: decide and review operator workflow and policy for events before a checkpoint (including ambiguous or historical cases), define what happens when balance visibility is restricted, preserve existing authorization and replay semantics, specify audit and correction paths, integrate transactionally without SQL interception, cover all write routes and cross-service lock ordering, and test browser, native Prisma/PostgreSQL, historical reconciliation and deployment/rollback. No automatic backfill, data change, production integration or upgrade is authorized by this experiment.

## Chosen policy, synthetic exercise

The user chose to **stop for manual review** when the cash refund occurred before the last count or its timing is unknown. The experiment rejects those two explicit answers and malformed/missing values before a new synthetic refund or movement is saved; an explicit after-checkpoint assertion must still pass the locked latest-checkpoint check. This does not implement an approval or historical-correction workflow, or prove an assertion true.

The interceptor requires an explicit timing value for new events but is intentionally **not production ready**: the intercepted review is not bound to the service request hash, and replay may return the earlier result without rechecking it. A production design must preserve legacy replay without claiming old refunds had a checkpoint, bind new review data to new requests, require a reviewed snapshot and explicit assertion server-side, and decide safe retry behavior after rejected/uncertain attempts. An operator could misstate timing; extra independent evidence and controls remain necessary. The live sales action still does not enforce this policy.
