# Synthetic refund evidence inventory — test only

`audit.test-only.ts` accepts a caller-owned transaction and synthetic branch ID. It inventories refund rows against canonical `refund:<id>` movement references and historical refund annotations, and lists unmatched/noncanonical references separately without casting arbitrary strings to integers. It compares current amounts, branch/account metadata, checkpoint ownership and confirmed status; flags recorded timestamp boundaries and selected ordering inconsistencies; and flags cash/noncash evidence overlap. It never writes, creates backfill, assigns a destination, infers physical payment time, or resolves a case.

The result is **evidence and uncertainty**, not a verdict. `NO_EVIDENCE` does not mean the money was not paid or omitted from an opening/count; `CHECKPOINT_UNATTESTED` does not prove a payment occurred before or after any count. Matching references, current amounts, timestamps or an attestation cannot establish provenance, authenticity, historic amounts or correctness; even an empty findings list is not clearance for migration. Recorded timestamps are database records, not proof of real-world event time. Different event IDs may refer to the same real-world payment; this query cannot detect that.

`check:finance:refund-audit` uses a disposable PGlite fixture and a read-only transaction for no evidence, ordinary/mismatched/overlapping evidence, wrong branch/account/amount and count status, equal boundaries, malformed and oversized references, and orphan annotations. The disposable PostgreSQL suite also reads a synthetic real-service refund in a read-only serializable snapshot and checks that its missing checkpoint is flagged with no table/revision changes. PostgreSQL tests use Prisma WASM and adapter, not the native engine.

Not an endpoint, CLI, production report or cutover authorization. Requires the reviewed candidate tables and closure/count schemas; expects foreign keys and canonical relationships, is not designed for corrupted schemas, exhaustive event provenance, all cross-branch evidence discovery, scale, pagination, access control, transaction lifetime, live concurrency or production performance. Historical investigation requires a separate reviewed plan, authorization, independent evidence and a consistent snapshot. Do not run on actual data without explicit separate approval.
