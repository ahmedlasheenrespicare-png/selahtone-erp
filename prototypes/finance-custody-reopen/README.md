# Custody reopening: synthetic index experiment only

The current application schema has a permanent unique `(branch_id, holder_id)` index for custodies. As a result a closed custody cannot be replaced for that holder and branch. `index.test-only.sql` replaces it with a partial unique index only in an explicitly opted-in disposable test database; it is **not a migration** and must never be run on real data.

`check:finance:custody-reopen-prototype` exercises the actual interim collection and holder-payment services on PGlite after the synthetic index change: duplicate open is rejected, prior cash is settled and the account closed, a new custody is opened, old requests replay against their original records, later cash and holder payment select the new open account, and a deliberately corrupted test schema with two open custodies fails closed. Test-only allocation also selects the replacement. The real application guards now filter to open accounts, but the real permanent index remains unchanged, so this does **not** enable reopening in the application.

The separate disposable PostgreSQL test checks competing replacement openings, opening while a close is committing, and one interleaving where the opening transaction began before old cash was settled and the old custody closed: in that run a serialization retry gave the replacement a later opening timestamp and avoided double counting. These tests do not prove safety of all transaction timing, historical cutovers, old unsettled items, same-timestamp boundaries, reversals, counts, actor/branch changes, deployment engines or long-running transactions. The existing period still relies on timestamps and the old attribution formula; the partial index alone is not a safe fix. A separately reviewed design and migration, historical audit, and authorization are required before any real index change.

`close-identity.test-only.ts` is a separate pure experiment for future custody-closure review: its legacy digest matches the current normalized `CLOSE_ACCOUNT` payload, while a new digest binds a snapshot of account ID, branch, kind, holder and closed state. Old replay cannot be upgraded by adding a snapshot, and a reviewed request cannot replay by dropping or changing it. This is not a closure command, an authorization check or proof of review; callers would still need current authorization and a locked comparison within the transaction, and legacy forms and retry behavior require design. It is not integrated or exercised against the real closure service. Run `npm run check:finance:close-identity-prototype` for the pure synthetic unit test.

`reviewed-close.test-only.ts` is a disposable SQL-intercepting adapter around the real closure service, not a production API. A synthetic PGlite test demonstrates locked account-identity comparison, rollback after a holder mismatch, current authorization, legacy-only replay without manufacturing review, and reviewed-request replay after closure. It temporarily translates a matching request hash in the returned test row so the unmodified engine can recognize replay; only the reviewed hash is persisted for a new test write. Returning fields to their old values defeats this fingerprint. This initial PGlite experiment did not cover PostgreSQL races; two selected orders were subsequently tested as described below. It does not cover all authorization paths, UI or migration; run `npm run check:finance:reviewed-close-prototype`.

Two PostgreSQL test orders now pair the reviewed-close adapter with intentionally uncoordinated direct holder reassignment. Reassignment-first triggers the real close retry and then rejects the stale snapshot with no closure, command or closure audit; closure-first commits the reviewed closure, after which the direct writer can still change the holder and the original request replays. The latter explicitly shows that replay does not protect later account identity. The test-only SQL adapter is not application integration or evidence of an actual reassignment.

`close-evidence-audit.test-only.ts` reads synthetic account/request/close-audit candidates and compares reconstructed fingerprints against current identity. A unique candidate is not a proven association: audit rows have no request FK. In PGlite, changed current holder or audit reason yields unresolved, duplicate close audits yield ambiguity, and change-then-restore or rewriting both identity and the unkeyed digest can produce a match. The comparator makes no writes and is not a production audit, access check, physical proof or historical reconstruction.

Disposable PostgreSQL now also tests concurrent duplicate reviewed-close requests: identical deliveries serialize and replay, while a different snapshot under the same request ID conflicts. Each selected scenario retains one close command and one audit, with no cash movement. A real-service legacy close also replays through the lab adapter without a snapshot, rejects retroactive snapshot addition, and still requires current authorization. This remains SQL-intercepting test code, not a production endpoint or proof of human review.

The identity-only reviewed-close snapshot does **not** include account revision. A disposable PGlite test records equal opposing transfers through the real service, returns the custody book balance to zero and advances revision, then shows that the unchanged identity fingerprint is accepted by the lab adapter (subject to the real engine's ordinary checks). The events remain separate records and do not establish physical transfers. This motivates—but does not implement or approve—a revision-aware review and still cannot protect against writers that do not bump revision.

A separate laboratory v2 close snapshot now binds account revision and an explicit request version without upgrading legacy or v1 replay. In PGlite, two real-service offsetting transfers bump revision and make an old v2 snapshot fail; a newly reviewed snapshot succeeds and replays. A deliberate SQL writer then inserts offsetting movements without bumping revision, and another old v2 review still succeeds: this is a concrete limitation, not proof of such a writer in real data. At that stage the synthetic evidence comparator was v1-only; a limited v2 comparison was added later as described below. At that stage no v2 PostgreSQL race had been exercised; two selected orders were subsequently added below. No production integration or UI is claimed.

A disposable PostgreSQL test pairs v2 reviewed closure with the real transfer service. Transfer-first bumps account revision and the retried closure rejects the stale fingerprint; closure-first causes the transfer to reject the closed custody without a movement. Saved commands replay in the exercised paths. This covers only two synthetic orders and does not establish physical transfer or production integration.

The read-only synthetic evidence comparator can now recognize a v2 candidate using the **current** account identity and revision, assuming it was open before closure. A later revision makes the comparison unresolved without changing replay, and a privileged writer can rewrite the account and unkeyed request digest to manufacture a match. Audit events are not request-linked; neither a unique candidate nor a match authenticates the past.

A PGlite counterexample hides the original close audit event and substitutes a single older synthetic event with the same account, actor and reason: the v2 comparator still reports a match, despite there being no request link. The fixture restores the original afterwards. The test runs in a serializable transaction; at that stage the comparator used multiple queries, subsequently replaced as described below. This scenario has not been tested on PostgreSQL or real data.

Additional PGlite cases make the v2 evidence unresolved as `ambiguous_sources` for a second candidate request or missing audit, and `state_inconsistent` for a different audit actor. The original request still replays in each case: replay is not an audit verification. The synthetic fixtures are restored afterwards; these cases have not been exercised on PostgreSQL.

On disposable PostgreSQL, the v2 comparator was also exercised after the close-first transfer race: a current candidate matched, a second close audit made the sources ambiguous, and a later synthetic revision increment made the result unresolved; replay persisted in both cases. This tests selected sequential reads in serializable transactions, not comparator concurrency, event/request linkage, or historical authenticity. The substituted older event, different actor and duplicate-request cases above remain PGlite-only.

A disposable PostgreSQL interleaving now demonstrates the isolation caveat: a READ COMMITTED reader paused after the account query can combine the old revision with a newly rewritten request hash and report a candidate match even though neither committed state matches. The same interleaving under SERIALIZABLE READ ONLY stayed unresolved on its stable snapshot. The writer atomically changes synthetic revision and unkeyed hash, and the fixture is restored. This is not evidence of such a real writer; stable isolation still cannot authenticate history or link an audit to a request. That three-query variant is retained only as an explicitly unsafe test comparator.

The current test-only comparator now reads bounded candidate sets in a single SQL statement. In the same PostgreSQL interleaving it stayed unresolved at READ COMMITTED, since the statement sees one snapshot; the old multi-statement variant remains solely for the counterexample. PGlite, PostgreSQL and typecheck passed. A statement snapshot does not prevent later changes, authenticate a hash, authorize access or link an audit to a request; this remains non-production.

A further PGlite case uses the real directed-count request and cancellation services: a v2 snapshot taken while the count is open is rejected by the ordinary pending-count guard, but after cancellation the account revision is unchanged and the same snapshot closes successfully. Both commands replay. This does not make cancellation incorrect; it demonstrates that the account revision is not a complete version of count-request state even for cooperating service writes. Defining a review scope requires separate design, preserving cancellation and replay; this case has not been run on PostgreSQL or the UI.

`pending-snapshot.test-only.ts` is a separate pure experiment combining a v2 account fingerprint with canonical, distinct sets of currently open count and settlement IDs. PGlite shows its value changes after the real count cancellation even when the account revision does not. It is not consumed by the close adapter and does not read or lock rows, authorize, preserve replay, capture request attributes or terminal history, or authenticate the digest. If its inputs return to the same values it cannot detect the intervening change. Any integrated design needs its own review scope and coordination, while preserving cancellation and replay; no production change is proposed by this test.

A PGlite counterexample now submits an artificial counted amount through the real directed-count service. The count's actor and amount change while its OPEN ID and account revision remain unchanged, so the pending-ID fingerprint stays identical; the real close guard still rejects an open count. Submission replays and cancellation remains allowed. The recorded amount and acknowledgement do not prove physical cash, and the experiment does not choose a production review scope. This case has not been tested on PostgreSQL or the UI.

On disposable PostgreSQL, a reviewed v2 close was paused after locking the account while the real count cancellation completed without changing account revision. The close rejected the open count visible in its transaction snapshot and saved no close request; a fresh call with the same input and fingerprint succeeded after cancellation, and close and cancellation replayed. This is one selected ordering through the test-only close adapter, not a production integration, evidence of human review, or a reason to block cancellation.

The experiment now also includes an optional single-statement test reader of the account and current open IDs, returning null for a missing account. PGlite verified unchanged output after count submission and changed output after cancellation; PostgreSQL verified before/after cancellation in the selected close interleaving. Its one-statement snapshot is not a lock or an atomic close check; it has no authorization, pagination, history, or request contents, and is not used by the close adapter. Earlier descriptions of the pure helper not reading SQL remain true of that helper itself.

An additional PGlite test creates and cancels a real synthetic settlement: its open ID enters and leaves the reader's fingerprint while cancellation leaves the account revision unchanged. A directed count on a different account in the same branch does not enter that fingerprint; settlement creation and cancellation replay and no movement is recorded. This tests ID scoping, not access authorization, physical cash, history or integration with close. This case has not been run on PostgreSQL or the UI.

An isolated PostgreSQL counterexample shows that a partial unique index and SERIALIZABLE alone do not guarantee chronological opening and closing timestamps: a transaction can establish a snapshot before closure, insert after closure commits, and commit with its earlier transaction-start `CURRENT_TIMESTAMP`. This simplified schedule does not reproduce all finance-engine reads or establish the cause of the intermittent reopen assertion. The experimental index and test are not a migration or authorization to reopen custody.

The full disposable PostgreSQL engine experiment has now reproduced the unsafe timestamp ordering: the replacement opening committed on its first attempt with `opened_at` earlier than the previous account's `closed_at` (about 119 ms in that run), using the test-only replacement index. The assertion remains in place and the suite failed. The current application index is unchanged and prevents this reopening; do not deploy the experimental index or infer a production-ready remedy.

`open-boundary-guard.test-only.ts` explores a fail-closed predecessor-row lock and strict transaction-start-versus-closure timestamp check around the engine's replacement insert. In one disposable SERIALIZABLE stale-snapshot order, locking forces a retry; in a deliberately READ COMMITTED example with an older transaction clock and a newer statement snapshot, the guard rejects until the caller starts a fresh transaction. Both tested requests replay. This is not an approved reopening design: transaction timestamps do not prove commit or physical order, and this SQL interceptor does not coordinate all writers, validate history or identities, or make the partial index deployable. The unguarded engine assertion remains unchanged; later successful runs do not invalidate the reproduced failure.

A further disposable counterexample demonstrates why that guard is not a solution. A long-running close writes its transaction-start timestamp, an opening transaction starts later under READ COMMITTED, and a deliberately uncoordinated SQL writer inserts a collection before the close commits. The guard then accepts because the opening timestamp is later than `closed_at`, yet the old creator/time formula attributes the synthetic collection to the new account. This does not establish actual double counting, real physical ordering, or behavior of coordinated production writers; it exposes the lack of a reliable cutover boundary. The application index remains unchanged.
