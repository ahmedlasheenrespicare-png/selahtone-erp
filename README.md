# صلة تون — نظام الإيرادات والمصروفات

تطبيق **Next.js 15** لشركة صلة تون للسمعيات، يعمل مع Netlify وNeon وCloudflare R2.

## ما يعمل الآن

| الصفحة | ماذا تفعل |
|---|---|
| `/login` | تسجيل الدخول وجلسة JWT **موقّعة** داخل كوكي HttpOnly؛ تُراجع حالة الجلسة والحساب من قاعدة البيانات |
| `/change-password` | تغيير كلمة المرور، وإجبار الحسابات الجديدة أو المُعاد تعيينها على تغيير الكلمة المؤقتة |
| `/dashboard` | لوحة القيادة والفروع والمستودعات وقيمة المخزون |
| `/inventory` | الأصناف ومعدلات الضريبة وأرصدة المستودعات حسب الصلاحية |
| `/inventory/new` | إنشاء صنف مشترك ومراجعته قبل الحفظ، للمدير والمحاسب |
| `/inventory/opening` | تسجيل رصيد افتتاحي لمستودع واحد مع السيريالات المطلوبة |
| `/inventory/serials` | سجل السيريالات، مقيّد بفرع موظف الكاونتر |
| `/setup` | فحوصات حية للإعداد ومحرك الضريبة |
| `/api/health` | فحص صحة للمراقبة |

## تحديث تثبيت موجود — مهم قبل النشر

تتطلب ميزات المصادقة وإدخال المخزون إضافات لمخطط قاعدة البيانات. **لا تنشر إصدارًا يعتمد على جداول لم تُضف إلى قاعدة التطبيق بعد.** حالة كل تثبيت تختلف؛ لا تُعِد تنفيذ تحديث سبق تطبيقه.

- خذ نسخة احتياطية قابلة للاستعادة، واختبر استعادتها والترحيل على قاعدة منفصلة مطابقة قبل أي تغيير في قاعدة قائمة. حدّد نافذة صيانة، وتحقق من أن اتصالات التطبيق والترحيل تشير للقاعدة المقصودة دون مشاركة بيانات الاتصال.
- ابدأ بفحص `prisma/manual-inventory-preflight.sql` للقراءة فقط، ثم قارن النتائج بالمخطط وتحقق من الأرصدة أو السيريالات الموجودة مسبقًا. افحص `prisma/manual-inventory-permissions.sql` للحساب الذي سيُنشئ الجداول وحساب التطبيق. لا تثبت هذه الفحوص وحدها هوية قاعدة التطبيق أو اكتمال توافقها.
- لإضافة جداول المخزون على قاعدة مطابقة للمخطط السابق، راجع `prisma/manual-inventory-upgrade.sql` وقيوده أولًا. يستخدم أمر `DO` واحدًا لإنشاء الجداول والفهارس والقيود الجديدة في `public` ذريًا، ولا يغيّر الأرصدة أو الأصناف الموجودة. يرفض تعارض الأسماء بدل حذف شيء. يحتاج التنفيذ والنشر إلى موافقة مستقلة؛ لا يعمل تلقائيًا.
- بعد التنفيذ، افحص `prisma/verify-manual-inventory.sql` للقراءة فقط، وقارن أعداد الأصناف والأرصدة بنتائج ما قبل الترحيل. لمراجعة تفاصيل القيود والفهارس، استخدم أيضًا `prisma/inspect-manual-inventory.sql` للقراءة فقط. عند عدم وضوح النتيجة لا تُعِد الترحيل؛ افحص الجداول أولًا.
- لا تستخدم `prisma db push` لترقية قاعدة قائمة دون مراجعة كاملة: فهو لا يضمن إنشاء قيود `CHECK` المخصّصة في ملف SQL، وقد يقترح تغييرات أخرى. لا تستخدم `--accept-data-loss` أو `db:seed` على الإنتاج لهذا الغرض.
- إذا كان التثبيت قديمًا ولم يستكمل تحديث المصادقة، فأكمل ترحيل المصادقة الخاص به أولًا؛ لا تُعِد تطبيقه إذا كان موجودًا. بعد ترحيل المصادقة الأولي سيُطلب من الحسابات تغيير كلماتها وتنتهي الجلسات القديمة. إذا كانت كلمة بداية منشورة قد استُخدمت، أعد تعيين كلمات الحسابات المتأثرة قبل إعادة فتح الدخول كما في قسم الإدارة أدناه؛ مجرد فرض تغييرها لا يبطل الكلمة القديمة.

> كان المستودع عامًا وتضمنت إصدارات سابقة بيانات دخول افتراضية. اجعل المستودع خاصًا، لكن تذكّر أن جعله خاصًا أو حذف النص الحالي لا يمحو ما نُشر سابقًا. غيّر كلمات المرور المتأثرة، وغيّر `AUTH_SECRET` أيضًا إذا اشتبهت في انكشافه؛ تغيير السر يلغي جميع الجلسات. إذا نُسخت قيمة المثال القديمة من `.env.example` كما هي، استبدلها بسر عشوائي قبل النشر؛ يرفضها الإصدار الجديد لأنها منشورة وغير آمنة.

## التشغيل المحلي

```bash
npm ci
cp .env.example .env          # املأ DATABASE_URL وDIRECT_URL وAUTH_SECRET
npx prisma db push            # على قاعدة تجريبية جديدة فقط، وليس لترقية قاعدة قائمة
```

إنشاء قاعدة تجريبية من المخطط مباشرة لا يضيف قيود `CHECK` الموجودة في ترحيل المخزون اليدوي؛ لا تعتبرها نسخة مطابقة للإنتاج. لا تشغّل ترحيل إنشاء الجداول فوق جداول أنشأها `db push` بالفعل.

قبل تهيئة البيانات، اختر كلمة مرور مؤقتة قوية (12 حرفًا على الأقل وبحد أقصى 72 بايت UTF-8) واحفظها خارج Git. في Bash يمكن إدخالها بلا إظهارها أو وضعها في سجل الأوامر:

```bash
read -r -s -p 'كلمة المرور المؤقتة: ' SEED_PASSWORD; echo
export SEED_PASSWORD
npm run db:seed
unset SEED_PASSWORD
npm run dev
```

ينشئ `db:seed` حسابات أولية تجريبية للمدير والمحاسب وكاونتر العريش؛ البريد موجود في `prisma/seed.ts`. تشترك الحسابات الجديدة في الكلمة المؤقتة عند إنشائها، ثم يجب على كل مستخدم اختيار كلمة مختلفة عند أول دخول. **لا يغيّر seed كلمات مرور الحسابات الموجودة** ولا يطبع الكلمة في السجل. لا تضع كلمة حقيقية في ملف متتبَّع في Git.

## إدارة الحسابات والجلسات

لإعادة تعيين كلمة مرور مستخدم، أدخل كلمة مؤقتة قوية في Bash دون إظهارها:

```bash
read -r -s -p 'كلمة المرور المؤقتة: ' TEMP_PASSWORD; echo
export TEMP_PASSWORD
npm run user:reset-password -- manager@selahtone.local
unset TEMP_PASSWORD
```

يستخدم الأمر `DATABASE_URL` و`AUTH_SECRET` المستخدَمين في التطبيق، ويلغي جلسات المستخدم ويفرض تغيير الكلمة عند دخوله التالي. أعِد العملية لكل مستخدم متأثر مع كلمة مؤقتة مختلفة.

لإيقاف حساب أو إعادة تنشيطه مع إلغاء جلساته فورًا:

```bash
npm run user:status -- user@example.com SUSPENDED
npm run user:status -- user@example.com ACTIVE
```

مدة الجلسة العادية 8 ساعات، أو 7 أيام عند اختيار «تذكرني» على جهاز شخصي. تُراجع حالة الحساب وصلاحياته من القاعدة عند كل طلب؛ الخروج يُلغي جلسة الجهاز، وتغيير كلمة المرور يُلغي جلسات الأجهزة الأخرى. عند إيقاف حساب مباشرة في القاعدة بدلًا من الأمر أعلاه، احذف جلساته في المعاملة نفسها لضمان عدم عودتها عند إعادة تنشيطه.

تُحد المحاولات حسب البريد، بما في ذلك العناوين غير المسجلة: بعد 5 محاولات فاشلة يُقفل الطلب مؤقتًا لمدة 15 دقيقة. العدّاد وسجل النتائج مشتركان في قاعدة البيانات، ولا يحفظ السجل كلمات المرور أو البريد الصريح. هذه ليست حماية من الهجمات واسعة النطاق على عناوين كثيرة؛ أضف تحديد المعدل على مستوى الشبكة/المنصة عند النشر. لتنظيف الجلسات المنتهية والسجلات الأقدم من 90 يومًا والعدّادات القديمة، شغّل دوريًا:

```bash
npm run auth:cleanup
```

لا توجد مهمة تنظيف تلقائية مهيّأة حاليًا. قيّد صلاحيات الوصول إلى قاعدة البيانات والسجلات والنسخ الاحتياطية.

## النشر على Netlify

1. استخدم مستودع GitHub **خاصًا** وأكمل تحديث القاعدة أعلاه قبل نشر التطبيق.
2. في Netlify ← Add new site ← Import from Git، اختر المستودع واضبط متغيرات `.env.example` المطلوبة، خصوصًا اتصالات Neon و`AUTH_SECRET` العشوائي. لا يلزم ضبط `SEED_PASSWORD` على الموقع إذا كانت التهيئة تُشغّل محليًا.
3. بعد النشر افحص `/api/health` ثم `/login`. لا تستخدم Vercel Hobby للاستخدام التجاري.

طلبات Server Actions من نفس النطاق مسموحة افتراضيًا. إذا كان وكيل موثوق يغيّر `Host`، اضبط `SERVER_ACTION_ALLOWED_ORIGINS` بأسماء المضيفين العامة الدقيقة فقط مفصولة بفواصل، دون بروتوكول أو نجمة؛ تُستخدم أيضًا للتحويل وتحقق أصل طلب الخروج. خط IBM Plex Sans Arabic مستضاف ضمن حزمة المشروع ومرخّص بـ SIL Open Font License 1.1.

## إدخال المخزون يدويًا

بعد مراجعة الترحيل وتطبيقه على القاعدة المناسبة ونشر الإصدار، يفتح المدير أو المحاسب «المخزون والمستودعات» ثم:

1. **إضافة صنف:** أدخل الاسم والتصنيف والسعر الموحد للفروع، وأي بيانات اختيارية؛ ثم راجع واضغط تأكيد. السماعات تتطلب سيريالًا لكل جهاز؛ يمكن تفعيل ذلك للمستلزمات وقطع الغيار أيضًا. يمكن ترك رمز الصنف ليُنشأ تلقائيًا، ويظهر الرمز في المراجعة قبل الحفظ.
2. **تسجيل رصيد افتتاحي:** اختر الصنف والمستودع والكمية الفعلية ومتوسط تكلفة الوحدة. للسماعات والأصناف المتتبعة أدخل رقمًا واحدًا في كل سطر، بحد 1000 رقم للرصيد الواحد، ثم راجع القائمة وأكد. تُمنع الأرقام المكررة حتى مع اختلاف حالة الأحرف أو الأرقام العربية/الإنجليزية.
3. **سجل السيريالات:** ابحث برقم كامل أو جزئي؛ المدير والمحاسب يريان كل الفروع، وموظف الكاونتر يرى فرعه فقط.

الرصيد الافتتاحي يُسجّل مرة واحدة لكل صنف ومستودع، ولا يستبدل رصيدًا موجودًا **حتى لو كان صفرًا**. لا توجد شاشة تعديل أو تصحيح بعد التأكيد في هذه المرحلة؛ راجع الأرقام بعناية. لا تضيف الواجهة سيريالات إلى أرصدة قديمة مسجلة مسبقًا، ولا تستورد سيريالات قديمة تلقائيًا؛ يلزم فحص هذه الحالات ووضع خطة منفصلة قبل إدخالها. حركات البيع والنقل والتسويات وإصدار الفواتير ليست ضمن هذه الخطوة.

## اختبارات ونسخ احتياطي

- `npm run check:inventory` — اختبارات التحقق من الأصناف والكميات والسيريالات ودقة حساب قيمة المخزون.
- `npm run check:inventory:integration` — اختبارات معاملات وترحيل بقاعدة PGlite محلية في الذاكرة، دون استخدام قاعدة التطبيق. يتطلب الاعتماديات وأداة توليد Prisma؛ لا يغني عن اختبار نسخة منفصلة من قاعدة الإنتاج الفعلية.
- `npm run check:auth` — اختبارات التحقق من المدخلات ومسارات العودة الآمنة.
- `npm run check:auth:http` — اختبارات التحويلات والكوكي والأيقونات بعد تشغيل التطبيق محليًا على المنفذ 3000؛ يمكن تحديد عنوان آخر في `AUTH_TEST_BASE_URL`.
- `npm run check:tax` — اختبارات محرك الضريبة.
- `npm run typecheck` — فحص TypeScript.
- `scripts/backup-to-r2.sh` و`.github/workflows/nightly-backup.yml` — إعداد نسخ `pg_dump` مشفّر إلى R2، ويتطلب ضبط أسرار GitHub: `DATABASE_URL`, `R2_ENDPOINT`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `BACKUP_PASSPHRASE`. تحقق من نجاح كل تشغيل؛ قسم `restore-drill` الحالي مجرد نص توضيحي ولا ينفّذ استعادة فعلية. اختبر الاستعادة على قاعدة منفصلة، ولا تعتمد على وجود مهمة النسخ وحده.

الخطوات اللاحقة المحتملة: **تصحيح وحركات المخزون**، ثم **كاونتر البيع**.
